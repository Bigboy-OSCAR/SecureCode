goal

만들고자 하는 것

사용자가 “이 로그를 보고 버그를 고쳐줘”라고 말하면, 어시스턴트는 로그 전체와 repository 전체를 한 번에 넣는 대신 필요한 조각을 찾아 LLM에게 전달해야 한다.

핵심 목표

큰 정보는 바깥에 보관하고, LLM context에는 “정답을 판단하는 데 필요한 작은 근거”만 넣는다.

사용자 요청 planner
source:// runtime:// memory://symbol
extract / resolve 작은 context
LLM 답변 또는 코드 수정

problem

문제 지점: “그냥 다 넣기”는 작동하지 않는다

1. context window 초과

모델은 한 번에 읽을 수 있는 token 수가 정해져 있다. 로그와 JSON은 small에서도 32k 제한을 넘었다.

2. prompt 평가 시간 증가

입력이 길수록 LLM이 읽는 시간이 늘어난다. symbol full repo는 한 질문에 약 10분이 걸렸다.

3. distractor로 인한 오답

context 안에 들어가도 방해 정보가 많으면 관련 값을 놓친다. source JSON full 주입은 실행됐지만 오답이었다.

Raw 주입 prompt token 비교

why it matters

문제인 이유

코드 어시스턴트는 “많이 읽기”보다 “정확한 위치를 찾기”가 중요하다. 필요한 증거가 빠지면 수정이 틀리고, 너무 많이 넣으면 비용과 시간이 폭발한다.

  • 사용자 경험: 한 질문에 수십 초에서 수분이 걸리면 대화형 도구로 쓰기 어렵다.
  • 정확성: 긴 입력은 답을 보장하지 않는다. 관련 위치를 못 찾으면 오답이 된다.
  • 확장성: 실제 repo, 로그, 테스트 출력은 실험 데이터보다 더 크고 더 지저분하다.
설계 원칙

context는 저장소가 아니라 작업대다

모든 재료를 작업대 위에 올려두는 대신, 창고에는 pointer를 붙이고, 작업대에는 지금 필요한 부품만 가져온다.

solution 1

Source Pointer

disk에 이미 있는 큰 외부 파일을 source://... 주소로 부르고, 파일 형식에 맞는 extraction tool이 필요한 부분만 읽는다.

왜 해결법이 되는가

LLM은 로그 596K, JSON 752K 전체를 읽지 않는다. 대신 source catalog와 “어떤 tool로 어느 부분을 추출할지”만 보고 작은 결과를 받는다.

log: grep 주변 line doc: section 추출 JSON: path 추출

source pointer benchmark

Source Pointer 성능 비교

medium에서 full source는 3개 중 2개가 context overflow였고, pointer 방식은 3개 모두 성공했다.

비교 방식

full_source
외부 파일 전체를 prompt에 직접 넣는 기본 방식
pointer_oracle
필요한 extractor 호출을 이미 안다고 가정한 pointer 최적 조건
pointer_select
LLM이 catalog와 tool spec을 보고 extractor를 직접 고르는 실제형 방식

핵심: 파일 크기와 prompt 크기를 분리했다.

Medium 정확도
Medium prompt token
Medium wall time

solution 2

Runtime Pointer

실행 중 tool이 만든 큰 output을 context에 직접 붙이지 않고, runtime memory store에 저장한 뒤 runtime://... 주소만 다음 단계로 넘긴다.

왜 해결법이 되는가

중간 결과가 커져도 LLM prompt에는 pointer와 추출 결과만 들어간다. 따라서 tool output 크기와 context window 크기를 분리할 수 있다.

producer output 보관 mirrored tool resolve 필요한 field만 회수

runtime pointer benchmark

Runtime Pointer 성능 비교

medium runtime output은 log 608K, JSON 891K까지 커졌지만 pointer mode의 prompt token은 거의 그대로였다.

비교 방식

full_runtime
tool output 전체를 prompt에 붙여 LLM에게 읽히는 방식
runtime_pointer_oracle
정답 extractor 호출을 안다고 가정하고 runtime object 일부만 읽는 방식
runtime_pointer_select
LLM이 runtime catalog에서 tool call을 선택하고 추출 결과로 답하는 방식

핵심: tool output 크기와 context 크기를 분리했다.

Medium 정확도
Medium prompt token
Medium wall time

solution 3

Symbol Index / Selector

repository 전체를 넣는 대신 parser가 함수와 class 목차를 만들고, 질문에 필요한 symbol 본문 또는 bundle만 LLM에게 전달한다.

왜 해결법이 되는가

코드 질문은 보통 전체 repo가 아니라 특정 함수, 상수, helper 주변에서 답이 나온다. symbol URI는 줄 번호보다 안정적인 접근 단위가 된다.

AST parser memory://symbol bundle 확장

symbol benchmark

Symbol Selector 성능 비교

쉬운 질문은 단일 symbol만으로 충분했지만, hard task는 상수와 helper까지 bundle로 확장해야 했다.

비교 방식

full_repo
repository 전체를 prompt에 넣는 방식
full_file / line_span
정답 파일 또는 정답 줄 범위를 이미 안다고 보는 기준선
symbol_oracle
정답 symbol URI를 알고 해당 함수나 class만 읽는 방식
symbol_select
LLM이 symbol index에서 URI를 고르는 방식
filtered bundle
후보를 줄이고 관련 상수와 helper까지 묶어서 읽는 개선 방식
Medium easy wall time
Medium easy prompt token

solution 4

Self-Extend

모델 내부 attention의 위치 처리를 그룹화해서, 원래 학습 context보다 긴 입력을 받아들이게 하는 방법이다.

왜 해결법 후보인가

context overflow 자체를 줄일 수 있다. 하지만 이번 실험에서는 “긴 입력 수용”과 “필요 정보 회수”가 다르다는 점이 드러났다.

4k 초과 입력 수용 retrieval 품질 별도 검증 필요 fallback 후보

conclusion

결론

이번 실험의 방향은 “모델에게 더 많이 읽히기”가 아니라 “필요한 증거를 더 작고 정확하게 전달하기”다.

1

외부 자료는 source://로 접근하고, 형식별 tool이 필요한 부분만 추출한다.

2

실행 중 생긴 큰 output은 runtime://로 저장하고 mirrored tool로 회수한다.

3

코드는 memory://symbol과 bundle 확장으로 함수, 상수, helper를 함께 읽는다.

4

Self-Extend는 기본값이 아니라 긴 배경이 꼭 필요할 때 검증 후 쓰는 fallback이다.

권장 아키텍처

Pointer catalog + retrieval tool + symbol bundle을 기본 경로로 두고, LLM context는 최종 판단에 필요한 근거만 담는다.
