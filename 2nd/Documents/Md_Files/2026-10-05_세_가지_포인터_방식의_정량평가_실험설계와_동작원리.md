# Symbol Index·Source Pointer·Runtime Pointer의 정량평가 실험 설계와 동작 원리

작성일: 2026-10-05  
분석 대상: `/Users/oscar/Desktop/SecureCode/1st`에 저장된 실험 코드, 문제·정답 정의, 기존 실행 결과  
작성 목적: AI에 익숙하지 않은 독자도 세 방식의 효과를 무엇으로, 어떻게 측정했는지 이해할 수 있도록 설명한다.

이 실험들의 공통 질문은 **“AI에게 자료 전체를 읽히는 대신, 필요한 부분을 찾아 전달하면 정답을 유지하면서 입력량과 처리 부담을 줄일 수 있는가?”**이다. 이를 확인하기 위해 같은 문제와 자료를 놓고, AI에게 자료를 전달하는 방법을 바꾸어 비교했다.

분석 결과, 세 실험 모두 정답 여부·입력량·처리 시간을 숫자로 비교할 수 있는 구조를 갖추고 있다. 다만 저장된 자료는 소수의 인공 문제를 사용한 기능 검증에 가깝다. 최초 분석에서 발견한 Symbol Index의 두 채점 결함은 2026-10-05에 수정했다. 아래에서는 기존 답변을 수정된 규칙으로 다시 채점한 결과와, 모델을 새로 실행한 결과를 구분한다. 과거 원본 실행 기록은 보존하고 수정·검증 결과는 별도 파일에 저장했다.

## 1. 세 실험을 이해하기 위한 공통 설명

### 1.1. ‘포인터’와 ‘입력 한도’는 무엇인가?

여기서 AI는 질문을 읽고 답을 만드는 언어모델을 뜻하며, 아래 표에서는 이를 LLM이라고도 표시한다. 언어모델은 한 번에 읽을 수 있는 자료의 양에 한도가 있다. 이를 **문맥 한도(context window)**라고 한다. 이 한도를 넘으면 자료를 입력하는 단계에서 실행이 실패할 수 있다.

포인터는 자료 본문을 대신하는 **찾아가기용 표식**이다. 도서관에서 책 전체를 복사해 전달하는 대신 청구기호를 알려주고, 필요한 쪽만 찾아 읽게 하는 것과 비슷하다. 이 실험의 포인터는 프로그램이 해석하는 문자열이며, 컴퓨터의 실제 메모리 주소를 AI에게 직접 공개하는 방식은 아니다.

| 방식 | 찾아갈 대상 | 쉬운 설명 |
|---|---|---|
| Symbol Index | 소스코드의 함수·클래스·메서드 | 프로그램의 목차에서 필요한 함수 항목을 찾는다. |
| Source Pointer | 디스크에 이미 저장된 로그·문서·JSON 파일 | 파일의 위치를 알려주고 필요한 기록·문단·항목만 꺼낸다. |
| Runtime Pointer | 프로그램을 실행하는 도중 도구가 만들어 낸 값 | 방금 받은 큰 결과물을 보관하고, 보관 번호로 필요한 부분을 꺼낸다. |

포인터 문자열만 짧게 만드는 것으로 실험이 완성되는 것은 아니다. **포인터가 실제 자료로 연결되고, 필요한 내용을 정확하게 추출하며, 그 내용으로 정답을 만들 수 있어야 한다.** 세 실험은 이 과정을 실행해 확인한다.

### 1.2. 무엇을 같게 하고 무엇을 바꾸었는가?

한 문제를 비교할 때에는 질문과 정답, 원본 자료, 사용 모델을 유지하고 **자료를 제공하는 경로와 범위**를 바꾼다. 기본 비교 구조는 다음과 같다.

| 비교 조건 | AI에게 전달하는 자료 | 이 조건으로 확인하는 것 |
|---|---|---|
| 전체 입력 | 원본 자료 전체 | 모든 내용을 직접 읽게 할 때의 성공 여부와 부담 |
| 정답 위치 제공, `oracle` | 실험 프로그램이 미리 알고 있는 위치에서 추출한 자료 | 필요한 자료를 정확히 가져왔다고 가정했을 때 답변이 가능한지 |
| AI가 선택, `select` | 먼저 작은 목록을 제공하고, AI가 선택한 위치에서 추출한 자료 | 위치나 도구를 고르는 과정까지 포함해 작동하는지 |

`oracle`은 AI가 정답을 알고 있다는 뜻이 아니다. **실험 프로그램이 올바른 자료 위치 또는 추출 방법을 미리 지정한다는 뜻**이다. 최종 답은 여전히 AI가 작성한다. 따라서 `oracle`과 `select`의 차이를 보면 선택 단계의 추가 부담과 실패 가능성을 살펴볼 수 있다.

자료는 실험용으로 생성했다. 정답이 들어 있는 부분과 질문을 고정하고, 관계없는 함수·로그·문단·사용자 설정을 추가했다. 이를 통해 “자료가 커져도 필요한 내용만 전달하는 방식은 작은 입력을 유지하는가?”를 확인한다. 실제 운영 서비스에서 수집한 데이터로 검증한 것은 아니다.

### 1.3. 공통 실행 조건과 숫자의 의미

기존 보고서와 실행 로그에서는 Apple M3 Pro 기반 MacBook Pro, llama.cpp의 Metal 실행 환경, Qwen2.5 Coder 7B Instruct의 Q5_K_M 모델이 확인된다. 실행 코드는 답변의 무작위성을 줄이는 설정인 `temperature=0`을 사용하며, 기본 난수 초기값은 `seed=1`이다. 주로 문제별·방식별 1회 실행한 기록을 비교한다.

| 실험 묶음 | 설정한 문맥 한도 | 최대 생성 길이 |
|---|---:|---:|
| Symbol Index 초기 medium 실험 | 65,536 토큰 | 64 토큰 |
| Symbol Index 전체 코드 재시도 1문제 | 131,072 토큰 | 64 토큰 |
| Symbol Index 확장 문제의 후속 bundle 실험 | 8,192 토큰 | 64 토큰 |
| Source Pointer 최종 실험 | 32,768 토큰 | 128 토큰 |
| Runtime Pointer 최종 실험 | 32,768 토큰 | 128 토큰 |

토큰은 AI가 문장을 처리할 때 사용하는 작은 글자·단어 조각이다. **문자 수와 토큰 수는 서로 다른 단위**이며, 자료 내용에 따라 변환 비율이 달라진다.

| 측정 항목 | 실제 측정·판정 방법 | 해석할 때의 주의점 |
|---|---|---|
| 문제 성공률 | 미리 정의한 정답 조건을 최종 답변이 만족했는지 판정 | 아래 표의 `3/3`은 문제 3개를 모두 통과했다는 뜻이다. 동일 문제를 3번 반복한 결과가 아니다. |
| 선택 성공 | 선택한 함수 주소 또는 추출한 내용이 정해진 조건을 만족하는지 판정 | 방식마다 정의가 다르므로 서로 같은 지표처럼 비교하면 안 된다. |
| 구성 입력 길이 | 질문·자료·지시문을 합쳐 만든 입력의 문자 수 | 입력 거부 사례도 길이는 계산할 수 있다. 프로그램이 덧붙이는 대화 역할 표식은 이 문자 수에서 제외된다. |
| 실측 입력 토큰 | llama.cpp 실행 기록의 `prompt_tokens` | 처리가 거부된 경우 누락될 수 있다. 이때 문자 수를 4로 나눈 추정값을 실측값으로 취급하지 않는다. |
| 입력 읽기 시간 | 실행 기록의 `prompt_eval_ms` | AI가 입력을 처리하는 구간의 시간이다. 모든 작업 시간을 뜻하지 않는다. |
| LLM 호출 시간 | 외부 모델 실행 프로그램의 시작부터 종료까지 잰 `wall_seconds` | 실행 프로그램 시작, 모델 적재, 입력 처리, 답변 생성 등이 포함된다. 자료 생성·색인 구축·추출 도구 실행 시간은 포함하지 않는다. |
| 입력 한도 초과 | 실행 종료 상태와 오류 메시지 확인 | 실패까지 짧게 걸린 시간을 빠른 문제 해결로 해석하지 않는다. |

AI가 먼저 위치를 고르고 나중에 답하는 방식은 **AI 호출이 2번**이다. 이 경우 입력 문자 수·입력 토큰·호출 시간을 두 번의 합계로 계산한다. 예를 들어 800토큰이라는 기록은 두 호출의 누적 입력량일 수 있으며, 한 번에 800토큰을 읽었다는 뜻은 아니다.

계산식은 다음과 같다.

- 문제 성공률 = 성공한 문제 수 ÷ 전체 문제 수 × 100
- 입력량 감소율 = (1 − 포인터 방식의 입력량 ÷ 전체 입력 방식의 입력량) × 100
- 호출 시간 감소율 = (1 − 포인터 방식의 호출 시간 ÷ 전체 입력 방식의 호출 시간) × 100

감소율은 같은 문제끼리, 같은 단위로 비교한다. 특히 시간 비교는 두 방식 모두 정상적으로 답한 문제를 사용해야 해석이 명확하다. 본문에서는 Source Pointer와 Runtime Pointer의 문서 문제를 이런 비교 사례로 사용한다.

## 2. Symbol Index: 필요한 코드의 위치를 찾아 읽는 실험

### 2.1. 검증하려는 효과와 문제 설계

이 실험은 코드 전체를 읽히는 대신 함수 단위로 찾아 읽게 했을 때, 입력량을 줄이면서 코드에 관한 질문에 답할 수 있는지 확인한다. 동시에 **함수 하나만으로 충분한지, 그 함수가 참조하는 주변 코드도 필요한지**를 확인한다.

실험용 Python 프로젝트에는 인증, 요금 계산, 보고서 처리 코드가 들어 있다. 여기에 답과 관계없는 코드와 이름이 비슷한 함수를 추가했다. 주요 비교 대상인 medium 자료는 **27개 파일, 638개 심볼**로 구성된다. 심볼은 여기서 함수·클래스·메서드처럼 이름을 가진 코드 단위를 뜻한다.

| 문제 묶음 | 질문의 내용 | 미리 정한 정답·판정 조건 | 설계 의도 |
|---|---|---|---|
| 기본 | 만료된 인증 토큰에서 발생하는 오류 문자열은? | 정확한 값 `TOKEN_EXPIRED` | 함수 밖에 정의된 상수 값까지 확인해야 한다. |
| 기본 | 연체료가 붙지 않는 유예 기간은? | `3` | 함수 안의 조건문을 읽어 값을 찾는다. |
| 기본 | 보고서 캐시 키의 형식은? | 답에 `report:`와 `:v` 포함 | 반환 문자열의 기본 구조를 확인한다. |
| 확장 | 만료 오류의 상수 이름이 아닌 실제 문자열 값은? | `TOKEN_EXPIRED`, 상수 이름은 제외 | 주변 상수 정의가 필요한 상황을 명시한다. |
| 확장 | 공백과 `/`가 포함된 보고서명으로 만들어지는 최종 키는? | `report:team-a:north/east_plan:v12` | 보조 함수까지 읽고 문자열 변환 결과를 계산해야 한다. |
| 확장 | 4일 연체, 금액 10,000일 때 상태와 연체료는? | `status=late, fee=125` | 두 함수의 결과를 종합하고 금액을 계산해야 한다. |

첫 문제의 인증 토큰은 로그인 등의 유효성을 확인하는 정보로, AI 입력량의 단위인 토큰과는 다른 뜻이다. 기본 문제도 모두 단일 함수만으로 해결되는 것은 아니다. 첫 문제의 함수 본문에는 `TOKEN_EXPIRED_MESSAGE`라는 이름만 있고, 실제 값은 함수 밖에 있다. 이 차이를 이용해 “찾은 함수가 맞아도 전달한 정보가 부족할 수 있다”는 점을 시험한다.

확장 문제의 연체료는 코드에 따라 `10,000 × 0.0125 × (4 − 3) = 125`이다. 정답은 AI의 주관적인 평가로 정한 것이 아니라, 생성한 코드의 규칙으로 정한다.

### 2.2. 실제로 어떻게 동작하는가?

먼저 프로그램이 Python 코드를 구문 구조에 따라 분석하여 함수 등의 이름, 파일 경로, 시작·끝 줄 번호를 색인에 저장한다. 각 항목에는 `memory://symbol/services/auth_service.py::validate_token`과 같은 식별자가 붙는다. AI가 이 식별자를 선택하면, 프로그램이 색인에 저장된 위치를 찾아 실제 코드를 읽어 준다.

| 실행 모드 | AI가 읽는 내용과 동작 | AI 호출 수 |
|---|---|---:|
| `full_repo` | 프로젝트의 모든 Python 코드를 읽고 답한다. | 1 |
| `full_file` | 실험 프로그램이 지정한 정답 파일 전체를 읽고 답한다. | 1 |
| `line_span` | 정답 함수의 시작·끝 줄을 미리 알려주고 해당 범위를 읽힌다. | 1 |
| `symbol_oracle` | 정답 심볼 식별자를 미리 지정하여 그 코드만 읽힌다. | 1 |
| `symbol_select` | 전체 심볼 목록을 보고 AI가 하나를 고른 뒤, 해당 코드로 답한다. | 2 |
| `symbol_bundle_oracle` | 정답 심볼과 관련 상수·보조 함수 등을 묶어 읽힌다. | 1 |
| `symbol_filtered_select_bundle` | 질문의 파일명·함수명 등을 이용해 후보를 줄이고, AI가 고른 심볼의 관련 코드까지 묶어 읽힌다. | 2 |

`full_file`과 `line_span`도 필요한 위치를 실험 프로그램이 미리 아는 조건이다. 따라서 이들의 낮은 처리 시간을 “AI가 스스로 정답 파일을 찾은 시간”으로 해석해서는 안 된다.

후속 방식의 동작 순서는 **질문 → 파일명·이름으로 후보 축소 → AI의 심볼 선택 → 관련 코드 보강 → AI의 답변**이다. 후보 수의 기본 상한은 24개다. 관련 코드 묶음은 같은 파일의 상수와 보조 함수, 질문에 언급된 함수 등을 정해진 규칙에 따라 추가한다. 여러 파일에 걸친 모든 의존 관계를 완전하게 추적하는 구현은 아니다.

### 2.3. 무엇을 숫자로 확인했는가?

다음 표는 medium 자료의 **기본 문제 3개에 대한 과거 실행 기록을 수정된 규칙으로 재채점한 결과**다. 입력 토큰과 시간은 문제당 평균이며, 선택 방식은 두 호출을 합산했다. 토큰 수는 반올림했다.

| 모드 | 문제 성공 | 실측 평균 입력 토큰 | 평균 LLM 호출 시간 |
|---|---:|---:|---:|
| 전체 코드 `full_repo`, 65k 설정 | 0/3 — 모두 입력 거부 | 산출 불가 | 성공 처리 시간 없음 |
| 정답 파일 `full_file` | 3/3 | 256 | 2.29초 |
| 정답 줄 범위 `line_span` | 2/3 | 199 | 2.12초 |
| 정답 심볼 `symbol_oracle` | 2/3 | 199 | 2.13초 |
| 전체 색인에서 선택 `symbol_select` | 2/3 | 33,871 | 181.19초 |
| 정답 심볼과 관련 코드 `symbol_bundle_oracle` | 3/3 | 305 | 2.60초 |
| 후보 축소·선택·관련 코드 `symbol_filtered_select_bundle` | 3/3 | 824 | 6.26초 |

전체 코드의 입력은 약 67,188토큰으로 65k 실행 설정을 넘었다. 문맥 한도를 131,072로 늘린 별도 재시도는 **첫 문제 하나만** 실행했으며, 67,188토큰·612.87초를 기록했지만 실제 문자열 대신 상수 이름을 답했다. 이 1문제 결과를 다른 방식의 3문제 평균과 직접 나누어 대표적인 성능 향상률로 삼기는 어렵다.

표의 후속 bundle 방식은 후보 축소와 관련 코드 보강을 함께 적용했다. 기본 bundle 원기록에는 문맥 한도를 포함한 전체 실행 옵션이 저장되어 있지 않아 초기 실험과 모든 설정이 같았는지도 확정하기 어렵다. 별도로 실행한 확장 문제의 bundle 실험은 8,192토큰 설정이 명시되어 있다. 따라서 181.19초에서 6.26초로 줄었다는 관찰은 후속 구현 전체의 결과이며, 후보 축소 한 요소만의 순수한 효과를 분리한 수치는 아니다.

기본 문제에서 `symbol_select`는 정답 심볼을 **3/3 선택**했지만 답변은 2/3만 통과했다. 반면 관련 코드를 추가한 후속 선택 방식은 선택과 답변이 모두 3/3이었다. 이 구분을 통해 **위치 선택의 성공과 필요한 정보 확보의 성공이 서로 다르다**는 것을 확인할 수 있다.

확장 문제의 과거 답변을 수정된 규칙으로 재채점한 결과는 다음과 같다.

| 모드 | 수정 후 재채점한 과거 답변 | 심볼 선택 일치 |
|---|---:|---:|
| `full_file` | 1/3 | 선택 단계 없음 |
| `symbol_oracle` | 0/3 | 위치를 미리 제공 |
| `symbol_select` | 0/3 | 3/3 |
| `symbol_bundle_oracle` | 1/3 | 위치를 미리 제공 |
| `symbol_filtered_select_bundle` | 1/3 | 3/3 |

**이 표에는 수정한 채점 규칙을 적용했다.** 문자열 변환 문제는 최종 문자열을 대소문자까지 정확하게 비교한다. 과거 답변은 `/`를 잘못 바꿨고, 금액 문제는 125 대신 150을 답했으므로 위 성공 건수는 이전과 같다. 채점 오류를 고친 것과 모델이 답을 더 잘하게 된 것은 구분해야 한다. 수정 내용과 검증 결과는 5.2절에 설명한다.

### 2.4. 왜 정량적인 평가가 가능한가?

첫째, 모든 모드에 같은 코드와 문제를 사용하고 정답을 미리 정했다. 따라서 작은 코드 조각을 전달한 것이 실제 답변 성공으로 이어졌는지 비교할 수 있다.

둘째, 심볼 선택 결과를 정해 둔 심볼 식별자와 대조하고, 최종 답변은 별도로 채점한다. 잘못된 위치를 고른 실패와 올바른 위치를 찾고도 답을 틀린 실패를 구분할 수 있다. 다만 초기 `symbol_select`의 종합 성공은 선택과 답변이 모두 맞아야 하고, 후속 선택 방식의 종합 성공은 최종 답변 기준이다. 수정 후에는 두 방식 모두 선택·답변 호출의 정상 종료도 필수 조건이다. 저장된 선택 지표와 답변 지표를 함께 보아야 한다.

## 3. Source Pointer: 저장된 파일에서 필요한 부분만 꺼내는 실험

### 3.1. 검증하려는 효과와 문제 설계

이 실험은 디스크에 이미 있는 외부 파일을 대상으로 한다. 큰 파일 전체를 AI에게 주는 방식과, 파일 위치를 가리키는 표식 및 추출 도구로 필요한 부분만 주는 방식을 비교한다.

실험 자료는 로그, 문서, JSON의 세 종류다. JSON은 항목 이름과 값을 계층적으로 저장하는 데이터 형식으로, 여기서는 고객별 설정을 담고 있다.

| 자료 | small 생성 설정 | medium 생성 설정 | 질문과 정답 |
|---|---:|---:|---|
| 결제 로그 | 650줄 | 5,000줄 | 요청 `REQ-042031`의 실패 원인은 `velocity_limit`, 재시도 대기값은 `7500` |
| 운영 문서 | 48개 절 | 320개 절 | `Payment Gateway Retry Policy` 절의 최대 재시도 횟수는 `4`, 지연 변동 비율은 `17` |
| 고객 설정 JSON | 일반 고객 420개와 목표 고객 1개 | 일반 고객 2,800개와 목표 고객 1개 | `northwind-prod`의 사용 여부는 `true`, 정책은 `pointer-first` |

small은 작은 자료, medium은 더 큰 자료를 뜻하는 실험 구분이다. 두 크기는 정답과 문제 유형을 유지하고 주변 자료량을 늘린 조건이다. 따라서 단순히 쉬운 문제와 어려운 문제를 비교하기보다, **같은 정보를 더 큰 자료에서 찾아야 할 때의 변화**를 살펴보는 설계다.

### 3.2. 실제로 어떻게 동작하는가?

프로그램은 파일별로 위치 표식, 자료 종류, 크기, 사용할 수 있는 도구와 설명을 목록에 저장한다. 예를 들어 로그에는 `source://log/logs/checkout_gateway.log`라는 표식이 붙는다. 이 표식을 해석하면 실제 파일 경로로 연결된다.

| 모드 | 실행 순서 | AI 호출 수 |
|---|---|---:|
| `full_source` | 해당 문제의 정답 파일 전체 → AI 답변 | 1 |
| `pointer_oracle` | 미리 지정한 파일·도구·검색 조건 → 내용 추출 → AI 답변 | 1 |
| `pointer_select` | 질문과 파일 목록·도구 설명 → AI가 도구와 조건 선택 → 내용 추출 → AI 답변 | 2 |

`full_source`는 세 파일을 전부 합치는 방식이 아니다. **그 문제의 정답이 들어 있는 파일 하나 전체**를 제공한다. 여기에서도 정답 파일을 찾는 단계는 이미 해결된 기준 조건이다.

자료 형식에 맞춘 추출 도구는 세 개다.

- 로그 검색 도구는 요청 번호와 일치하는 줄 및 주변 줄을 가져온다.
- 문서 추출 도구는 지정한 제목과 맞는 절을 가져온다.
- JSON 추출 도구는 `tenants.northwind-prod.security`처럼 항목 이름으로 표시한 경로의 값을 가져온다.

AI는 “어느 파일에서 어떤 조건으로 꺼낼 것인지”를 정하고, 실제 파일 읽기와 검색은 일반 프로그램이 수행한다. 이후 AI는 추출된 짧은 내용을 읽고 최종 답을 작성한다. 최종 구현은 AI가 쉼표로 나열한 같은 계층의 JSON 항목도 추출하도록 보완되어 있다.

### 3.3. 무엇을 숫자로 확인했는가?

최종 결과 파일은 각 크기에서 3문제 × 3모드, 즉 9개 실행 사례를 담는다. 다음 표의 입력 길이와 토큰은 문제당 평균이다. `—`는 전체 입력 방식에 처리 거부가 섞여 있어 세 문제 모두에 대한 실측 토큰 평균을 제시하지 않았다는 뜻이다.

| 자료 크기 | 모드 | 문제 성공 | 평균 구성 입력 길이, 문자 | 실측 평균 입력 토큰 |
|---|---|---:|---:|---:|
| small | `full_source` | 1/3 | 67,974 | — |
| small | `pointer_oracle` | 3/3 | 896 | 286 |
| small | `pointer_select` | 3/3 | 2,950 | 778 |
| medium | `full_source` | 1/3 | 477,083 | — |
| medium | `pointer_oracle` | 3/3 | 896 | 286 |
| medium | `pointer_select` | 3/3 | 2,952 | 780 |

small의 전체 입력 방식은 로그에서 입력 한도를 초과했고, 문서에서는 정답을 냈다. JSON은 실행됐지만 `pointer-first` 대신 `pointer-preferred`라고 답했다. medium에서는 로그와 JSON 모두 입력 한도를 초과했고, 문서만 정상적으로 답했다.

최종 `pointer_select`는 두 크기 모두 필요한 값이 들어 있는 내용을 3/3 추출했고, 최종 답변도 3/3 통과했다. 선택과 답변을 합친 평균 LLM 호출 시간은 small 6.43초, medium 6.42초였다. 정답 추출 방법을 미리 제공한 `pointer_oracle`은 각각 2.47초, 2.44초였다.

시간과 토큰을 더 공정하게 비교하려면 **양쪽이 모두 정답을 낸 동일 문서 문제**를 비교하는 것이 좋다.

| 문서 문제 | 전체 입력 토큰 → AI 선택 방식 토큰 | 토큰 감소율 | 전체 입력 호출 시간 → AI 선택 방식 호출 시간 | 호출 시간 감소율 |
|---|---|---:|---|---:|
| small | 2,626 → 706 | 73.1% | 9.18초 → 5.77초 | 37.2% |
| medium | 16,770 → 708 | 95.8% | 63.68초 → 5.76초 | 90.9% |

이 표의 선택 방식에는 첫 번째 선택 호출의 비용도 포함되어 있다. 다만 파일 읽기와 추출 도구 시간은 포함되지 않은 LLM 호출 구간의 비교다.

### 3.4. 왜 정량적인 평가가 가능한가?

정답이 되는 요청 번호·문서 절·고객 항목을 데이터 생성 단계에서 정해 두었다. 따라서 도구가 필요한 값을 가져왔는지와 AI가 그 값을 답했는지를 자동으로 확인할 수 있다. 또 small과 medium에서 정답을 고정했으므로, 자료량 증가가 입력량에 미친 영향을 직접 비교할 수 있다.

실제로 AI 선택 방식의 평균 입력은 약 778토큰에서 780토큰으로 거의 같았다. 이것은 이 시험 조건에서는 원본의 불필요한 부분이 늘어도 AI에게 전달되는 자료는 작게 유지되었다는 뜻이다. 큰 파일 전체를 읽히다가 입력 한도를 넘는 문제에서도 답을 낼 수 있었다.

다만 `selection_correct`는 **“선택한 도구의 추출 결과에 정답 값이 포함되는가”**를 검사한다. 정해진 도구 이름·인자가 유일하게 맞았는지를 엄격하게 비교하는 지표는 아니다. `pointer_oracle`의 선택 성공 표시는 프로그램이 참으로 지정한 값이므로 AI의 선택 능력 점수로 볼 수 없다.

또한 AI가 보는 목록은 세 파일뿐이고, 설명에는 목표 문서 제목이나 JSON 경로가 포함된다. 따라서 이 실험은 안내가 있는 제한된 환경에서의 추출 도구 선택을 검증한다. 수많은 미지의 파일을 스스로 탐색하는 성능까지 측정한 것은 아니다. 추출 도구가 내부적으로 파일 전체를 읽거나 JSON 전체를 해석하는 경우도 있어, 입력 토큰이 일정하다는 사실만으로 파일 처리 시간이나 컴퓨터 메모리 사용량도 일정하다고 말할 수는 없다.

## 4. Runtime Pointer: 실행 중 만들어진 큰 결과를 보관하고 꺼내는 실험

### 4.1. 검증하려는 효과와 문제 설계

Source Pointer가 이미 저장된 파일을 대상으로 한다면, Runtime Pointer는 **도구가 실행 중 반환한 값**을 대상으로 한다. 예를 들어 조회 도구가 거대한 고객 설정 결과를 돌려주었을 때, 그 결과 전체를 다음 AI 입력에 넣을 필요가 있는지를 시험한다.

실험에서는 외부 서비스에 실제로 접속하는 대신 세 종류의 생성 함수를 사용한다. 하나는 결제 로그 문자열, 하나는 운영 문서 문자열, 하나는 고객 설정 객체를 만든다. 생성 규모는 Source Pointer와 같은 small·medium 설정이며, 질문도 요청 번호·문서 정책·고객 설정을 확인하는 세 종류다. 고객 설정 문제의 항목 이름은 `runtime_pointer_enabled`로 바뀌며, 목표 값은 `true`와 `pointer-first`다.

### 4.2. 실제로 어떻게 동작하는가?

1. 실험 프로그램이 문제에 맞는 생성 함수를 실행해 큰 결과물을 만든다.
2. 결과물을 프로그램 내부의 보관소인 `RuntimeStore`에 넣는다.
3. `runtime://json/fetch_tenant_snapshot/0001` 같은 보관 표식을 발급한다.
4. 포인터 방식에서는 AI에게 본문 전체 대신 표식, 자료 종류, 크기, 사용 가능한 추출 도구와 설명을 알려준다.
5. 추출 도구가 표식에 연결된 실제 값을 꺼내 필요한 부분을 추출한다.
6. AI가 짧은 추출 결과로 답한다.

큰 원본 값은 컴퓨터의 메모리에 그대로 존재한다. 효과의 핵심은 **AI의 입력에 원본 전체를 반복해서 펼쳐 넣지 않는 것**이다. 원본 저장에 필요한 메모리 자체를 없애는 기술로 해석해서는 안 된다.

| 모드 | 비교 조건 | AI 호출 수 |

도구는 포인터를 실제 값으로 바꾼 다음 로그 검색, 문서 절 추출, JSON 경로 추출을 수행한다. 현재 구현은 이 세 가지 추출 작업에 맞춘 것이다.

이 시험에서는 **문제·모드마다 보관소를 새로 만들고 결과물 한 개만 저장한다.** 생성 함수를 무엇으로 할지는 실험 프로그램이 이미 정해 놓는다. 따라서 AI가 여러 생산 도구를 계획적으로 연결하거나, 보관된 여러 결과물 중 올바른 하나를 찾아가는 문제까지 포함하지는 않는다.

### 4.4. 왜 정량적인 평가가 가능한가?

또한 원문 길이, 추출 결과 길이, AI의 누적 입력량을 각각 기록한다. 원문이 수십만 문자여도 추출 결과는 짧고 최종 답변은 정답인지를 함께 확인하므로, 단순히 데이터를 빼서 입력만 줄인 경우와 구분할 수 있다.

small에서 medium으로 커져도 AI 선택 방식의 평균 입력이 756토큰에서 약 757토큰으로 유지된 결과는, **이번 질문에 필요한 작은 부분만 모델에 전달하는 구조가 작동했다는 근거**다. 다만 생성 함수 실행·보관·추출 시간은 LLM 호출 시간에서 빠져 있으므로, 전체 시스템 처리 시간이 같은 비율로 줄었다고 주장할 수는 없다.

선택 성공 지표는 Source Pointer와 마찬가지로 추출 결과에 정답 값이 포함됐는지를 확인한다. 보관된 객체가 한 개이고 위치 설명도 제공되는 조건이므로, 이 결과는 복잡한 여러 단계 작업이나 여러 객체 간 참조의 안정성을 검증한 수치가 아니다.

## 5. 정량적 결과를 설명할 때 함께 밝혀야 할 사항

### 5.1. ‘숫자로 측정했다’와 ‘일반적인 성능을 입증했다’는 범위가 다르다

이 실험은 정답·비교 조건·측정 항목이 정해져 있어 수치 평가가 가능하다. 하지만 세 문제에서 3/3을 얻었다고 해서 실제 업무의 모든 질문에서 100% 성공한다고 해석할 수는 없다. 문제 하나의 차이가 성공률 약 33.3%포인트에 해당한다.

Source Pointer와 Runtime Pointer의 small·medium은 같은 세 문제 유형과 목표 값을 공유한다. 두 크기의 결과를 합쳐 서로 독립적인 새로운 여섯 문제를 검증했다고 표현하는 것도 적절하지 않다. 또한 Source Pointer의 선택 지시문과 JSON 추출 처리는 기존 문제에서 관찰한 실패를 바탕으로 보완되었다. 최종 성적은 그 문제들에 맞춰 보완된 구현의 성적이며, 별도로 숨겨 둔 새로운 평가 자료의 성적은 아니다.

세 방식은 대상 자료와 선택 난도가 다르다. Symbol Index는 수백 개의 코드 항목, Source Pointer는 세 파일 목록, Runtime Pointer는 한 개의 실행 결과를 대상으로 했다. 따라서 평균 토큰이나 시간만 나란히 놓고 세 방식의 우열을 정할 수는 없다.

두 번째 수정에서는 코드 블록이나 바깥 인용부호 같은 답변 포장만 제거한다. 문자열 내부의 대소문자·슬래시·공백은 그대로 검사한다. 따라서 올바른 값을 코드 블록에 넣어 답해도 통과하지만, `/`를 `_`로 바꾸거나 `team-a`를 `TEAM-A`로 바꾸면 실패한다. 기준 문제 파일은 보존되는 `symbol_test/tasks/medium_hard_tasks.json`에 두었고, 기존 작업 폴더의 문제 파일도 같은 내용으로 갱신했다.

**채점 검증 테스트: 9개 모두 통과.** 오류 로그에 정답 숫자가 들어 있는 경우, 선택 단계가 실패한 경우, 최종 호출이 실패한 경우를 각각 거부하는지 확인했다. 정상적인 정답은 모든 비교 모드에서 통과하는지도 검사했다. 문자열 정답은 실험용 Python 함수를 실제로 실행한 반환값과 대조했고, 올바른 답·잘못된 슬래시·잘못된 대소문자·추가 설명 등을 구분했다. 이는 모델이 문제를 푼 횟수가 아니라 채점 규칙에 대한 테스트 수다.

**과거 기록 재채점: 43건 중 1건의 판정 변경.** 기본 실험 21건, 확장 실험 21건, 131k 문맥의 별도 1건을 재채점했다. 기본 `full_repo` 유예 기간 문제가 정답에서 오답으로 바뀌어 원기록의 1/3이 0/3으로 바로잡혔다. 나머지 42건의 판정은 유지됐다. 문자열 문제의 과거 답변은 실제 값도 틀렸으므로, 정답을 통과시킬 수 있게 고쳤다고 해서 기존 점수가 올라가지는 않았다. 이전 보고서도 이 실행 오류를 이미 0/3으로 해석했기 때문에, 기본 결과표의 성공 건수는 그대로다.

## 7. 추가 논문 3편에서 실제로 시험하는 것

조사·보강일: 2026-10-05. 아래에서는 각 논문을 **시험 문제 준비 → 비교 방식별 실행 → 답변 채점 → 전체 결과 집계** 순서로 설명한다. 수치 표는 논문 저자들이 보고한 결과이며, 이번 문헌 조사에서 재실행한 결과는 아니다.

먼저 **연구자가 가진 전체 자료와 AI가 한 번에 읽는 입력은 다르다.** 연구자는 긴 문서와 과거 대화, 도구로 조회할 전체 자료를 가지고 있다. 그러나 AI에게는 실험 조건에 따라 그 일부만 보여 준다. 연구자는 정답도 별도로 보관했다가 AI가 답을 낸 뒤 채점한다. 이 구분을 놓치면 “자료에 정답이 있는데 왜 못 맞히는가” 또는 “답을 미리 알려 준 실험인가”라는 혼동이 생긴다.

세 논문에서 AI가 제출해야 하는 답은 다음과 같이 다르다.

| 논문 | AI에게 내는 시험 문제 | AI가 제출하는 것 | 연구자가 바꾸어 보는 조건 |
|---|---|---|---|
| RAPTOR | 긴 글을 근거로 질문에 답하라. | 객관식 선택 또는 서술형 답변 | 원문 조각만 검색 / 원문과 여러 단계의 요약을 함께 검색 |
| MemGPT | 이전 대화에서 언급한 사실을 기억해 답하라. | 과거 사실에 관한 답변 | 과거 대화 요약만 읽기 / 보관한 대화 원문을 다시 검색 |
| ReWOO | 여러 도구를 사용해 알아낸 사실들을 연결하여 답하라. | 근거를 종합한 최종 답변 | 결과를 받을 때마다 다음 행동 결정 / 전체 계획을 먼저 만들고 실행 |

8~10절에서는 각 논문의 대표 실험 하나를 중심으로 **한 문제가 실제로 처리되는 과정**을 따라간다. 이해를 돕는 작은 예시는 그 자리에서 ‘설명용 예시’로 표시한다. 이 예시의 인물·문서·대화는 논문의 실제 평가 문항이나 추가 실행 결과가 아니다. 예시를 통해 절차를 이해한 다음, 논문이 실제 문제집에서 얻은 수치를 읽는 구성이다.

## 8. RAPTOR: 같은 길이의 참고 자료를 주되, 원문만 고른 경우와 요약도 고른 경우를 비교하는 실험

대상 논문: Parth Sarthi 외, **RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval**, ICLR 2024. [학회 원문](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf)

### 8.1. 무엇을 확인하려는 실험인가?

긴 문서에서 질문과 비슷한 문단 하나를 찾았다고 해서 답에 필요한 내용이 모두 모이는 것은 아니다. 원인과 결과가 멀리 떨어진 문단에 적혀 있을 수 있기 때문이다. RAPTOR는 **원문 조각에 더해 여러 부분을 묶은 요약도 검색 대상으로 준비하면, 제한된 입력 안에 더 유용한 근거를 넣을 수 있는지** 시험한다.

**설명용 예시:** 긴 보고서 앞부분에는 ‘배수로 공사가 지연되었다’, 뒷부분에는 ‘폭우 때 물이 빠지지 않아 창고가 침수되었다’고 적혀 있다고 하자. 질문은 ‘창고 피해가 커진 이유는 무엇인가?’이다. 침수 문단만 찾으면 사건은 알 수 있지만 앞의 공사 지연과 연결하기 어려울 수 있다. 두 내용을 포함한 요약은 그 연결을 짧은 자료 안에 담을 수 있다. 이 예시는 요약을 넣는 목적을 설명하며, 실제로 항상 올바른 요약이 생성된다는 가정은 아니다.

### 8.2. 어떤 자료와 문제를 준비하는가?

실제 평가에는 긴 글과 질문·정답이 묶인 공개 문제집을 사용한다. QuALITY는 긴 글을 읽고 객관식 답을 고르는 시험이고, QASPER는 학술 논문의 내용을 묻는 시험이다. 이야기·대본을 대상으로 하는 NarrativeQA도 평가했다. 아래 결과표는 QuALITY와 QASPER에서 동일한 답변 모델을 사용한 비교다. [원문 4절](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=6)

실험자는 **같은 원문으로 두 종류의 검색 자료**를 준비한다. 첫 번째에는 원문을 나눈 조각만 넣는다. 두 번째에는 그 원문 조각들과, 의미가 비슷한 조각들을 묶어 만든 요약을 넣는다. 요약을 다시 묶어 요약하므로 좁은 내용부터 넓은 주제까지 여러 단계의 요약이 생긴다. 질문의 정답을 요약에 미리 써 넣는 것이 아니라, 문서 내용으로 검색 자료를 구성하는 준비 작업이다. [원문 3절](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=3)

### 8.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

| 순서 | 원문 조각만 검색 | RAPTOR의 원문·요약 검색 |
|---|---|---|
| 1. 같은 질문 제시 | 준비한 원문 조각 중 질문과 관련 있는 내용을 찾는다. | 원문 조각과 모든 단계의 요약 중 질문과 관련 있는 내용을 찾는다. |
| 2. 읽힐 분량 제한 | 관련성이 높은 원문 조각들을 정해진 토큰 예산 안에서 고른다. | 관련성이 높은 원문·요약 항목들을 같은 토큰 예산 안에서 고른다. |
| 3. 답변 모델에 전달 | 질문과 선택된 원문을 전달한다. | 같은 질문과 선택된 원문·요약을 전달한다. |
| 4. 답안 제출 | 객관식 선택 또는 질문에 대한 답변을 제출한다. | 같은 형식의 답안을 제출한다. |

‘모든 단계에서 검색한다’는 말은 **요약 전체를 AI에게 한꺼번에 읽힌다**는 뜻이 아니다. 검색 후보에는 모든 단계가 포함되지만, 답변 모델에는 예산 안에서 선택된 내용만 들어간다. 아래 비교에서는 근거 자료를 최대 400토큰까지 주었다. SBERT라는 검색용 모델과 UnifiedQA-3B라는 답변용 모델도 두 조건에서 같게 유지했다. [원문 검색 절차·표 2](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=8)

앞의 창고 예시로 말하면, 실험자가 비교하려는 것은 ‘짧은 자료와 긴 자료 중 어느 쪽이 유리한가’가 아니다. **같은 짧은 분량 안에 개별 사건 문단을 넣었을 때와, 사건들의 관계를 묶은 자료까지 넣었을 때의 차이**다.

### 8.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

QuALITY에서는 고른 보기가 정답 보기와 같으면 성공으로 세어 정답률을 구한다. QASPER에서는 기준 답변과 생성 답변을 대조하는 F1 점수를 집계한다. F1은 답변에 정답 요소가 얼마나 정확하고 빠짐없이 들어 있는지 평가하는 점수로, 아래 표에서는 0~100점으로 표시한다. 모든 문제가 완전히 맞았는지를 세는 정답률과 구분한다.

| 검색 자료 구성 | QuALITY 정답률 | QASPER 답변 F1 |
|---|---:|---:|
| 원문 조각만 준비 | 54.9% | 36.23 |
| 원문과 RAPTOR 요약을 함께 준비 | 56.6% | 36.70 |

같은 모델과 근거 자료 예산에서 객관식 정답률은 1.7%포인트, F1은 0.47점 높아졌다. 이 표에서는 답변 모델을 더 강한 것으로 교체한 효과와 자료 구성의 효과를 섞지 않고 볼 수 있다. [원문 표 2](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=8)

### 8.5. 이 결과로 어디까지 말할 수 있는가?

이 비교는 **AI에게 줄 자료의 양을 제한한 상태에서도 자료의 구성에 따라 답변 품질이 달라질 수 있다**는 근거다. 위 점수 상승만으로 모든 질문에서 요약이 유리하다고 말할 수는 없다. 요약을 사전에 만드는 시간과 비용도 따로 발생한다.

Source Pointer의 문서 시험에 연결하면, 한 절의 숫자를 찾는 문제와 떨어진 여러 절을 종합하는 문제를 구분할 필요가 있다. 같은 입력 예산에서 한 절만 추출할지, 관련 원문 여러 절을 추출할지, 요약도 포함할지 비교할 수 있다. 정확한 설정값을 묻는 문제는 원문 값과 직접 대조해야 한다. 문서 전체 관계를 잘 요약했더라도 특정 숫자를 잘못 옮겼다면 그 질문에는 오답이기 때문이다.

## 9. MemGPT: 과거 대화를 요약만 읽고 답하는 경우와 원문을 다시 찾아 답하는 경우를 비교하는 실험

대상 논문: Charles Packer 외, **MemGPT: Towards LLMs as Operating Systems**, arXiv 2023. 분석 대상은 2024-02-12 수정본 v2다. [논문 정보·버전 이력](https://arxiv.org/abs/2310.08560)

### 9.1. 무엇을 확인하려는 실험인가?

대화가 길어지면 과거 내용을 모두 현재 입력에 넣기 어렵다. 요약으로 줄이면 중요한 세부 사항이 빠질 수 있다. MemGPT는 **원래 기록을 입력 밖에 보관하고 필요할 때 다시 찾아 읽게 하면, 요약만 읽는 경우보다 과거 사실을 잘 답할 수 있는지** 시험한다.

여기서 ‘기억’은 모델이 학습으로 모든 대화를 암기한다는 뜻이 아니다. 현재 읽는 입력과 외부 보관 자료를 구분하고, 도구로 자료를 다시 가져오는 구조다. 논문 제목의 운영체제도 이러한 정보 관리 방식에 관한 비유다. [저자 연구 소개](https://research.memgpt.ai/)

### 9.2. 어떤 자료와 문제를 준비하는가?

대표 시험인 DMR에서는 사람이 만든 **다섯 차례의 대화 기록**을 사용한다. 별도의 AI가 과거 대화의 구체적인 사실을 물어보는 질문과 정답을 만들고, 이를 다음 대화의 질문으로 사용한다. 연구자는 정답을 채점용으로 보관한다. [원문 3.1.1절·부록 6.1.3절](https://arxiv.org/pdf/2310.08560v2#page=5)

**설명용 예시:** 두 번째 대화에 ‘제주 여행에서 파란색 지도책을 샀다’는 말이 있었고, 이후에는 다른 이야기를 나누었다고 하자. 새 질문은 ‘제주 여행에서 무슨 책을 샀지?’이며 정답은 ‘지도책’이다. 요약이 ‘제주 여행을 했다’ 정도로 줄었다고 가정하면, 요약만 읽는 AI에게는 책의 종류가 보이지 않는다.

실험자는 같은 과거 대화를 두 가지 방법으로 준비한다. 한 조건에는 대화 요약을 주고, 다른 조건에는 대화 원문을 외부에 보관하여 검색할 수 있게 한다. **시험하려는 차이 자체가 과거 정보를 다시 확인할 수 있는가**이므로, 두 조건에 처음부터 같은 원문 전체를 입력하는 시험이 아니다.

### 9.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

| 순서 | 대화 요약만 사용하는 GPT-4 | MemGPT를 사용하는 GPT-4 |
|---|---|---|
| 1. 새 질문 제시 | 질문과 과거 대화 요약을 읽는다. | 질문을 읽고, 필요하면 보관 기록을 검색할 수 있다. |
| 2. 근거 확인 | 제공된 요약을 바탕으로 답을 만든다. 원문을 다시 찾는 경로는 없다. | AI가 검색어를 정하면 프로그램이 보관 대화에서 관련 기록을 찾아 현재 입력에 넣는다. |
| 3. 추가 확인 | 원문 재검색 단계 없음 | 필요한 사실을 못 찾았으면 추가 검색이나 다음 결과 확인을 할 수 있다. |
| 4. 최종 제출 | 과거 사실에 대한 답을 제출한다. | 찾아 읽은 내용을 바탕으로 답을 제출한다. |

예시에서 검색이 잘되었다면 현재 입력에 ‘파란색 지도책을 샀다’는 과거 문장이 들어온다. 그제야 답변 모델은 ‘지도책’이라고 답할 근거를 갖는다. 이 문장이 정말 검색되고 최종 답도 맞는지는 평가 결과로 확인해야 하며, 외부에 보관했다는 사실만으로 성공한 것으로 세지는 않는다. 실제 비교에서도 기준 방식은 요약을, MemGPT는 검색 가능한 전체 대화 기록을 사용했다. [원문 3.1.1절](https://arxiv.org/pdf/2310.08560v2#page=5)

### 9.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

답변 후 별도의 GPT-4 채점자에게 **질문, 미리 만든 정답, 제출한 답변**을 준다. 채점자가 맞다고 판단한 문제의 비율을 정확도로 집계한다. 긴 답변에도 정답 사실이 포함될 수 있으므로 단순한 문자열 완전 일치만 사용하지 않았다. 기준 답변의 표현이 생성 답변에 순서를 유지하며 얼마나 포함되는지 보는 ROUGE-L 재현율도 함께 보고했다. 이 보조 점수는 0~1로 표시하며 클수록 기준 답변의 표현을 더 많이 포함한다. [원문 3.1.1절·부록 6.1.2절](https://arxiv.org/pdf/2310.08560v2#page=10)

| 비교 조건 | 채점 AI가 맞다고 판정한 비율 | ROUGE-L 재현율 |
|---|---:|---:|
| GPT-4와 과거 대화 요약 | 32.1% | 0.296 |
| GPT-4와 MemGPT | 92.5% | 0.814 |

이 결과는 **요약만 이용한 답변보다 원래 기록에 재접근한 답변이 해당 채점에서 더 많이 통과했다**는 뜻이다. 92.5%는 외부 저장 성공률이나 검색 도구 실행 성공률이 아니라 최종 답변에 대한 판정 비율이다. [원문 표 2](https://arxiv.org/pdf/2310.08560v2#page=5)

### 9.5. 이 결과로 어디까지 말할 수 있는가?

대화 원문에 다시 접근하는 기능과 그 정보를 관리하는 절차가 함께 달라졌다. 따라서 성적 차이를 식별자 하나의 효과로 분리할 수는 없다. 또 채점 AI가 표현을 유연하게 인정하므로, 실제 코드의 상수 값을 대소문자까지 정확하게 비교한 로컬 실험과 동일한 정답 기준도 아니다.

Source Pointer·Runtime Pointer에 연결할 때에는 자료를 보관하고 다시 가져오는 전체 과정을 시험해야 한다. 예를 들어 첫 로그에서 요청 번호를 얻고, 그 번호로 다음 기록을 찾아 최종 원인을 답하게 할 수 있다. 이때 ‘기록을 찾았는가’와 ‘그 기록으로 정답을 만들었는가’를 나누어 측정하면 실패 위치를 구분할 수 있다.

### 9.6. 같은 논문의 문서 질문·연쇄 조회 시험은 어떻게 진행되는가?

위 대화 기억 성적과 다음 두 시험은 별개다. 자료와 문제를 만드는 방법도 다르다.

**문서 질문 시험:** NaturalQuestions-Open에서 50문제를 뽑고 Wikipedia 문서들을 준비한다. 기준 방식은 같은 검색기로 얻은 상위 문서들을 처음 입력에 넣고 답하게 한다. 실험자는 처음 주는 문서 수를 바꾸어 성적을 본다. MemGPT는 문서들을 외부 저장소에 두고 검색을 여러 번 하거나 검색 결과의 다음 묶음을 확인하여 답한다. 최종 답이 맞고 검색한 문서에 근거하는지를 AI 채점자로 평가한다. 이는 ‘처음 받은 문서 안에서만 답하기’와 ‘필요한 문서를 계속 찾아보기’를 비교하는 시험이다. [원문 3.2.1절·그림 5~6](https://arxiv.org/pdf/2310.08560v2#page=6)

**연쇄 조회 시험:** 식별자와 값 140쌍을 준비한다. 어떤 항목의 값이 다른 항목의 식별자이면 그 항목을 다시 조회해야 한다. 예를 들어 `A의 값=B`, `B의 값=C`, `C의 값=최종값`이라면 A의 값 B에서 멈추지 않고 최종값까지 찾아 제출해야 한다. 연구자는 전체 자료 수를 유지하면서 연결 깊이와 항목 배치를 바꾸고, 30가지 배치를 사용했다. 일반 모델의 답변과 반복 조회를 수행하는 MemGPT의 답변을 미리 정한 최종값과 대조한다. 이는 더 긴 문서를 읽는 능력뿐 아니라 **여러 번의 조회를 끝까지 이어 가는 능력**을 확인하는 시험이다. [원문 3.2.2절·그림 7](https://arxiv.org/pdf/2310.08560v2#page=8)

## 10. ReWOO: 도구 결과가 나올 때마다 계획하는 방식과, 전체 계획을 먼저 만드는 방식을 비교하는 실험

대상 논문: Binfeng Xu 외, **ReWOO: Decoupling Reasoning from Observations for Efficient Augmented Language Models**, arXiv 2023. [논문 정보](https://arxiv.org/abs/2305.18323)

### 10.1. 무엇을 확인하려는 실험인가?

AI가 검색 도구를 여러 번 사용하는 상황을 생각하면, 보통 첫 결과를 읽고 다음 행동을 정한다. 그다음 결과가 나오면 앞의 질문·지시문·도구 결과를 다시 입력해 다음 행동을 정한다. 단계가 늘수록 같은 내용이 반복 입력된다.

ReWOO는 **할 일을 먼저 계획하고, 실행 프로그램이 그 계획대로 결과를 연결한 뒤 마지막에 답을 만들면 반복 입력을 줄일 수 있는지** 시험한다. 도구를 사용하지 않는 방식과 비교하는 것이 아니라, 도구를 사용하는 두 절차를 비교하는 것이다. [원문 2절·그림 2](https://arxiv.org/pdf/2305.18323#page=3)

### 10.2. 어떤 자료와 문제를 준비하는가?

대표 비교는 여러 사실을 연결해야 답할 수 있는 HotpotQA 1,000문제다. 실험자는 두 방식에 같은 GPT-3.5-Turbo, 같은 종류의 도구인 Wikipedia 검색과 LLM 도구, 같은 예제 질문 6개를 제공한다. LLM 도구는 짧은 정보 추출 등을 별도로 AI에게 맡기는 기능이다. 예제 6개는 수행 형식을 보여 주는 자료이며 평가할 1,000문제와 구분한다. 정답은 채점용으로 따로 보관한다. [원문 3.1절·표 1~2](https://arxiv.org/pdf/2305.18323#page=6)

**설명용 예시:** 가상의 작가 ‘해솔’의 아버지가 태어난 도시를 묻는다고 하자. 첫 검색 결과에서 아버지의 이름 ‘민수’를 알아내고, 그 사람을 다시 검색해 출생 도시 ‘태안’을 찾아야 한다. 이 인물·검색 결과는 절차 설명을 위해 만든 것이며 논문의 실제 문항이 아니다.

### 10.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

비교 대상 ReAct는 결과를 받은 다음 행동을 정한다. 위 예시라면 다음과 같이 진행될 수 있다.

1. AI에게 질문과 도구 사용법을 준다. AI가 ‘해솔을 검색하라’고 지시한다.
2. 프로그램이 검색 결과를 가져온다. AI에게 질문·이전 진행 내용·검색 결과를 다시 입력한다. AI가 아버지 이름을 읽고 ‘민수를 검색하라’고 지시한다.
3. 두 번째 검색 결과도 입력에 추가한다. AI가 지금까지의 내용을 읽고 출생 도시를 답한다.

ReWOO에서는 처음 계획을 만들 때 아직 아버지 이름과 출생 도시를 몰라도, **앞 단계 결과가 들어갈 자리에 표식을 넣어** 뒤 작업을 적을 수 있다. 설명용 계획은 다음과 같다.

| 미리 적는 계획 | 실행 프로그램이 나중에 채우는 내용 |
|---|---|
| `#E1`: Wikipedia에서 해솔 검색 | 해솔의 인물 설명이 저장된다. |
| `#E2`: LLM 도구로 `#E1`에서 아버지 이름 추출 | 실제 첫 결과를 도구에 주어 ‘민수’를 얻는다. |
| `#E3`: Wikipedia에서 `#E2` 검색 | `#E2`를 ‘민수’로 바꾸어 검색하고 출생 정보가 있는 결과를 얻는다. |

그 뒤 답변 담당 AI에게 질문, 계획, 실제로 얻은 근거를 주어 ‘태안’이라는 최종 답을 만들게 한다. **`#E2` 자체가 사람 이름을 알고 있는 것은 아니다.** 실행 프로그램이 앞서 저장한 결과를 꺼내 다음 도구의 입력에 대입하는 것이다. 이 대입과 최종 근거 전달은 저자 공개 코드에서도 확인된다. [계획·도구 실행·답변 연결 코드](https://raw.githubusercontent.com/billxbf/ReWOO/main/algos/PWS.py)

두 방식에 허용된 도구는 같아도, 모델이 작성한 계획에 따라 실제 호출 순서와 횟수는 달라질 수 있다. 위 예시에서도 ReWOO는 이름을 추출하는 LLM 도구를 사용했다. 따라서 ‘계획 작성과 최종 답변의 두 단계’라고 해서 **전체 AI 호출이 항상 두 번**인 것은 아니다.

### 10.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

각 문제에서 최종 답을 저장하고 정답과 대조한다. 동시에 계획·답변·LLM 도구 호출에서 사용한 토큰을 합산한다. 이를 1,000문제에 반복해 답변 점수와 문제당 평균 토큰을 집계한다. 토큰은 AI가 읽고 쓰는 글의 처리량을 세는 단위이며, 여기서는 입력뿐 아니라 출력과 LLM 도구 사용분도 포함한다.

| 측정 항목 | ReAct | ReWOO | 무엇을 센 것인가? |
|---|---:|---:|---|
| AI 채점 정확도 | 40.8% | 42.4% | 별도의 GPT-4가 정답과 의미가 맞는다고 판정한 비율 |
| 정확 일치율 EM | 32.2% | 30.4% | 정해진 비교 규칙으로 정답 문자열과 일치한 비율 |
| 문자 기준 F1 | 39.6 | 40.1 | 정답과 답변의 문자 겹침을 이용한 점수 |
| 저자 보고 평균 총토큰 | 9,795.1 | 1,986.2 | 한 문제를 끝내는 동안의 전체 토큰 사용량을 문제들에 걸쳐 평균한 값 |

표는 논문의 HotpotQA 결과다. 예를 들어 AI 채점 정확도 40.8%와 42.4%는 1,000문제 중 각각 408개와 424개가 해당 채점에서 맞았다는 의미다. 반면 F1 40.1은 401개를 맞혔다는 뜻이 아니다. [원문 평가 지표·표 2](https://arxiv.org/pdf/2305.18323#page=7)

토큰 감소율은 `(1 − 1,986.2 ÷ 9,795.1) × 100 ≈ 79.7%`다. 그러나 정답 문자열을 엄격하게 비교한 EM은 1.8%포인트 낮아졌다. 이 때문에 **처리량은 크게 줄었지만, 모든 채점 기준에서 더 정확해진 결과는 아니다**라고 읽어야 한다.

측정 방식에도 구분이 필요하다. 현재 공개 코드에서는 계획·최종 답변의 입력·출력 토큰에 LLM 도구 사용분을 더하는데, 도구 사용분 일부는 문자 수를 4로 나눈 추정값이다. 위 표는 저자 보고값으로 인용하며, 직접 재현할 때는 실측과 추정을 나누어 기록해야 한다. [공개 코드의 토큰 집계](https://raw.githubusercontent.com/billxbf/ReWOO/main/algos/PWS.py)

### 10.5. 이 결과로 어디까지 말할 수 있는가?

이 실험이 확인하는 것은 **같은 종류의 문제와 도구를 쓰더라도, 계획과 결과를 전달하는 절차를 바꾸면 전체 토큰 부담이 달라진다**는 것이다. 실제 답변 점수까지 함께 재므로, 단순히 작업을 덜 해서 토큰이 줄어든 경우와 구분해 판단할 수 있다.

Runtime Pointer와의 공통점은 실행 결과를 이름으로 연결하는 데 있다. 다만 ReWOO도 마지막 답변 단계에는 실제 근거를 읽힌다. 따라서 표식이 있다는 이유만으로 큰 결과물이 끝까지 입력 밖에 남거나 문맥 한도 초과가 모두 방지된다고 볼 수는 없다. 현재 방식의 효과를 시험하려면 결과의 크기와 도구 연결 단계를 늘리면서 **전체 누적 토큰과 한 번의 호출에 들어간 최대 토큰**을 함께 기록해야 한다. 누적량은 반복 부담을, 최대 단일 입력은 한도 초과 가능성을 보여 준다.

## 11. 추가 논문 세 편을 현재 실험에 적용하기 위한 구체적인 실험 설계

설계 보강일: 2026-10-06

이 절에서는 앞에서 소개한 세 방법을 **현재 실험에 추가한다면 무엇을 준비하고, AI에게 어떤 문제를 주며, 어떤 답을 정답으로 처리할지** 정한다. 예를 들어 여러 파일의 코드를 연결해 반환값을 계산할 때 어떤 함수와 설정을 읽는지, 도구를 연결할 때 앞 결과의 어느 값을 다음 도구에 넣는지까지 정한다.

아래는 **앞으로 구현하고 실행할 실험의 설계**다. 예시의 파일·대화·고객·주문은 설명을 위해 새로 구성한 시험 자료이며, 기존 실험에서 관측한 사례가 아니다. 앞 절의 논문 성적을 이 설계의 예상 성적으로 사용하지 않는다. 논문의 핵심 절차를 현재 코드와 모델에 맞춰 적용하므로, 저자의 실험 전체를 동일하게 재현하는 작업과도 구분한다.

### 11.1. 세 실험에서 각각 무엇을 알아내려는가?

| 참고 방법 | 실제로 시킬 일 | 같은 문제에서 비교할 핵심 차이 | 현재 실험에서 확장하는 부분 |
|---|---|---|---|
| RAPTOR 응용 | 프로젝트 코드의 동작·관계·변경 영향을 파악하고 오류를 수정한다. | 현재 코드 전달 구조 / 요약 없는 코드 검색 / 요약과 원문을 연결한 검색 | Symbol Index에 파일 간 연결과 코드 요약을 추가하고, 원문 위치·버전을 함께 관리 |
| MemGPT | 긴 대화를 차례로 처리한 뒤 오래된 사실과 최신 변경 사항에 답한다. | 최근 내용·요약만 기억 / 필요하면 과거 원문도 다시 조회 | Source Pointer·Runtime Pointer에 시간에 따른 기억 관리 추가 |
| ReWOO | 앞 도구에서 받은 번호를 다음 도구에 넣어 최종 설정값을 구한다. | 결과를 볼 때마다 다음 행동 결정 / 처음에 도구 연결 계획 작성 | Runtime Pointer를 여러 단계의 도구 연결로 확장 |

**공통 준비와 기록 원칙.** 문제를 만드는 사람은 정답과 그 근거를 별도 파일에 저장한다. AI에게는 질문과 해당 비교 조건에서 허용한 자료만 준다. 정답 파일과 채점 규칙은 검색 대상에서 제외한다. ‘정답이 있는 자료를 AI가 검색해서 읽는 것’은 정상적인 풀이 과정이지만, ‘채점표를 읽게 하는 것’은 허용하지 않는다.

각 설계에는 설정을 정하는 **개발용 자료**와 마지막 성적을 재는 **평가용 자료**를 둔다. 두 집합은 코드 프로젝트·문서·대화 이력·주문 단위로 먼저 나눈다. 같은 원본의 이름이나 번호만 바꾼 자료를 양쪽에 나누어 넣지 않는다. 개발용 자료에서 검색 설정과 자료 예산을 정한 뒤에는 평가 결과를 보고 바꾸지 않는다.

실행 조건은 다음과 같이 정한다. 숫자는 이번 후속 실험을 위한 설정값이며, 앞 절의 기존 실행 조건이나 논문 설정을 다시 적은 것이 아니다.

| 항목 | 이번 설계의 기준 |
|---|---|
| 기본 모델과 장비 | RAPTOR·MemGPT·ReWOO에는 기존 Qwen2.5 Coder 7B Instruct Q5_K_M과 Apple M3 Pro 환경을 사용한다. 모델 파일·실행기 버전·운영체제 버전을 실행 기록에 남긴다. |
| 생성 설정 | 무작위 선택을 억제하는 설정인 temperature 0, seed 1을 사용한다. 모델별로 실제 적용된 설정을 저장한다. |
| 한 번에 읽고 쓰는 한도 | Qwen은 입력과 출력을 합쳐 8,192토큰으로 고정한다. 일반 최종 JSON 답은 최대 256토큰, 11.2의 코드 수정 내용과 계획·기억 갱신·요약 출력은 최대 512토큰으로 제한한다. 자료별 세부 예산은 각 설계에서 따로 정한다. |
| 실패 처리 | 잘못된 출력 형식, 실행 오류, 허용 횟수 초과, 입력 한도 초과, 시간 초과는 실패로 센다. 오류 문장 안에 정답 숫자가 우연히 포함되어 있어도 통과시키지 않는다. 한도에 맞추려고 ‘전체 입력’ 조건의 자료를 몰래 잘라내지 않는다. |
| 시간 제한 | 개발용 자료로 확인한 뒤 한 문제의 제한 시간을 고정한다. 출발값은 300초이며, 부족하면 평가를 시작하기 전에 같은 실험의 모든 조건에 똑같이 늘린다. 실제 적용값을 보고한다. |
| 시간 측정 | 모델을 한 번 준비한 뒤 질문이 들어온 시점부터 최종 답이 나올 때까지 잰다. 검색·추출·도구 실행·모든 AI 호출을 포함한다. 모델을 처음 불러오는 시간과 사전 자료 준비 시간은 별도로 기록한다. |
| 반복과 초기화 | 조건별로 같은 문제를 세 번 실행하되 매번 상태를 초기화하고 실행 순서를 번갈아 배치한다. 정답률은 각 반복의 전체 성적으로 제시하며, 세 번 중 가장 잘된 답만 골라 채점하지 않는다. 동일한 60문제를 세 번 풀었다고 독립된 180문제로 주장하지 않는다. |

입력량은 최종 답변 단계만 세지 않는다. **한 문제를 푸는 동안 모든 AI 호출의 입력 토큰을 합하고, 출력 토큰은 별도로 합한다.** 같은 자료를 다음 호출에서 다시 읽히면 다시 센다. 한 호출 안에서 이미 계산한 입력을 재사용하는 경우에는 중복 집계하지 않고 재사용 여부를 기록한다. 도구 설명, 자료 위치 표식, 검색 결과의 제목도 실제 입력에 포함되면 센다. 토큰 수를 제공하지 못한 경우에는 ‘미측정’으로 표시하고, 문자 수를 나눈 추정값과 섞지 않는다.

시간은 문제별 세 반복의 중앙값을 구한 뒤, 같은 문제의 조건별 차이를 비교한다. 정답률은 모든 문제에서 계산하고 실패 원인도 남긴다. 정상적인 문제 해결 시간의 비교에는 양쪽 조건이 모두 성공한 문제를 사용하되, 그 문제 수를 함께 적는다. 실패한 실행을 제외한 빠른 시간만 보여 주지 않는다.

사전에 색인·요약·대화 기억을 만들었다면 그 작업량도 남긴다. 예를 들어 문서 하나에 세 질문을 할 때는 ‘요약 생성 1회 + 질문 처리 3회’의 총비용을 함께 제시한다. 질문 처리만 빨라졌다고 전체 비용이 줄었다고 판단하지 않는다.

### 11.2. RAPTOR의 아이디어를 코드에 적용하는 실험: 현재 Symbol Index의 한계와 효과적인 프로젝트 요약 구조를 함께 찾기

#### 11.2.1. 확인할 것은 ‘현재 코드 이해 수준’과 ‘요약으로 얻는 추가 효과’다

이번 실험의 대상은 운영 문서가 아니라 **실제로 실행할 수 있는 Python 프로젝트**다. AI에게 코드의 반환값, 함수 사이의 관계, 설정 변경의 영향, 오류 수정 방법을 묻는다. 정답은 가능한 범위에서 실제 코드 실행과 동작 검사로 확인한다. 질문이나 요약을 사람이 읽는 문장으로 쓰더라도, 평가 대상은 프로그램의 동작이다.

확인할 질문은 두 가지다.

1. **현재 수준:** 지금의 Symbol Index와 관련 코드 묶음만으로, 여러 파일에 걸친 코딩 질문을 어디까지 풀 수 있는가?
2. **요약 구조의 효과:** 같은 입력량에서 코드의 어떤 정보를 남기고 어떤 단위로 묶어야, 프로젝트를 더 정확하게 이해하고 수정할 수 있는가?

RAPTOR에서 가져오는 것은 ‘자료를 작은 단위로 나누고, 관련 자료를 묶어 여러 단계로 요약하며, 질문에 맞는 수준의 자료를 읽힌다’는 절차다. 원 논문의 자연어 문서 성적을 코드에서도 성립하는 결과로 간주하지 않는다. 아래는 **RAPTOR의 원리를 코드에 맞게 바꾼 후속 실험 설계**다. [원 논문의 자료 구성·검색 방법](https://arxiv.org/html/2401.18059v1#S3)

여기서 ‘좋은 프로젝트 요약’은 짧고 매끄러운 소개문을 뜻하지 않는다. **필요한 코드로 찾아갈 수 있고, 계산식·분기 조건·호출 관계를 잘못 바꾸지 않으며, 코드를 수정한 뒤에도 현재 버전과 맞는 요약**을 뜻한다. 가장 높은 추상도의 프로젝트 소개부터 정확한 함수 본문까지 연결하는 구조를 비교한다.

이 절에서 제시하는 문제 수와 비교 조건은 앞으로 실행할 설계다. 이번 문서 보강에서는 현재 코드 구조를 확인하고 아래 예시의 계산과 코드 묶음 동작을 점검했으며, 새 언어모델 성적을 측정하지는 않았다.

#### 11.2.2. 현재 구조로 할 수 있는 것과 새로 필요한 것을 먼저 구분한다

현재 구현을 확인한 결과는 다음과 같다. 이름과 위치를 간추린 색인은 코드에 접근하는 데 유용하지만, 코드의 동작까지 설명하는 요약과는 구분해야 한다.

| 기능 | 현재 구현에서 확인한 범위 | 이번 실험에서 필요한 보완 |
|---|---|---|
| 코드의 위치 찾기 | 함수·클래스·메서드의 이름, 파일, 시작·끝 줄, 심볼 식별자를 저장한다. | 기존 기능을 재사용한다. |
| 의미를 설명하는 요약 | 색인에는 함수의 목적, 입력·출력 규약, 계산식, 부작용에 대한 요약이 없다. | 원문에 근거한 요약을 만들고 별도 자료로 저장한다. |
| 관련 코드 묶기 | 선택한 심볼이 있는 **같은 파일**에서 참조 이름, 상수, 보조 함수를 찾아 묶는다. | 가져오기 문장을 따라 다른 파일의 함수·상수까지 연결하는 기능을 추가한다. |
| 프로젝트 전체의 관계 | 현재 묶음 생성에는 파일을 넘는 호출 관계표와 상위 기능 요약이 없다. | 함수 → 기능 또는 모듈 → 프로젝트 수준의 연결을 만든다. |
| 답 채점 | 기존 문제의 최종 문자열·값과 실행 성공 여부를 판정한다. | 복수 근거, 변경 영향 집합, 수정 코드의 동작 검사에 맞는 채점기를 추가한다. |

#### 11.2.3. 한 프로젝트에서 어떤 문제를 낼 것인가?

다음은 기존 연체료 문제에서 착안한 **새 실험용 예시**다. 원래 프로젝트 파일을 수정했다는 뜻은 아니다. 계산 규칙을 여러 파일에 나누고, 이름은 비슷하지만 별도로 동작하는 함수도 둔다. 금액은 0 이상의 정수 단위이고, 연체일도 0 이상의 정수로 제한한다.

```python
# settings.py
GRACE_DAYS = 3       # 무료 유예 기간
DAILY_BPS = 125      # 하루 요율: 125 / 10000
```

```python
# billing/fees.py
from settings import GRACE_DAYS, DAILY_BPS

def late_fee(amount, days):
    charge_days = min(max(days - GRACE_DAYS, 0), 21)
    return amount * DAILY_BPS * charge_days // 10000
```

```python
# api/invoice.py
from billing.fees import late_fee

def invoice_total(amount, days):
    return amount + late_fee(amount, days)
```

```python
# billing/status.py
def overdue_label(days):
    return "late" if days > 0 else "current"
```

설명에서는 `C1=GRACE_DAYS`, `C2=DAILY_BPS`, `F1=late_fee`, `F2=invoice_total`, `F3=overdue_label`로 줄여 부른다. 실제 기록에는 심볼 식별자 또는 상수가 있는 파일·행 번호와 연결한다. C1·C2는 현재 함수 색인에 독립 심볼로 들어 있지 않으므로, 확장 실험에서는 상수 위치도 별도로 등록해야 한다.

| 유형 | AI에게 줄 문제 예 | 정답과 확인 방법 |
|---|---|---|
| ① 한 함수 이해 | `overdue_label(4)`의 반환값은? | `late`. 해당 함수를 실행해 확인한다. |
| ② 여러 파일의 계산 결합 | `invoice_total(10000, 4)`의 반환값은? | `10125`. 유료 연체일은 `4−3=1`, 연체료는 `10000×125×1÷10000=125`이므로 총액은 10,125다. |
| ③ 경계 조건 이해 | `late_fee(10000, 25)`의 반환값은? | `2625`. `25−3=22`지만 과금일 상한이 21일이므로 2,750이 아니다. |
| ④ 변경 영향 파악 | C1을 3에서 5로 바꾸면 F1·F2·F3 중 어떤 함수의 반환값이 달라질 수 있는가? | `{F1, F2}`. 예를 들어 4일 연체에서 F1은 `125→0`, F2는 `10125→10000`이 된다. F3은 계속 `late`다. |
| ⑤ 기능 전체의 구조 이해 | 청구 총액의 진입 함수, 계산 함수로 이어지는 호출, 정책값 위치를 제시하라. 상태 표시 함수도 같은 유예 정책을 사용하는가? | 진입점 F2, 호출 `F2→F1`, 정책 C1·C2, F3의 유예 정책 사용 여부는 `false`. 미리 정한 항목을 갖춘 JSON으로 채점한다. |
| ⑥ 오류 수정 | 오류가 삽입된 버전에서 `invoice_total(10000, 3)`이 10,375를 반환한다. 3일까지 무료이고 과금일 상한은 21일이라는 요구를 만족하도록 수정하라. | 아래의 오류 줄을 수정하고, 숨겨 둔 동작 검사를 모두 통과해야 한다. |

예를 들어 ②의 제출 형식은 `{"answer":10125,"evidence":["F2","F1","C1","C2"]}`다. 답의 숫자뿐 아니라 어떤 코드와 설정을 근거로 삼았는지도 남긴다. 실제 위치는 기록된 식별자로 확인한다.

⑥의 오류 버전에서는 F1의 첫 줄만 `charge_days = min(days, 21)`로 바꾼다. 정답 수정의 한 예는 `charge_days = min(max(days - GRACE_DAYS, 0), 21)`로 복구하는 것이다. 이 정답 코드는 AI에게 미리 주지 않는다. 요약도 **오류가 실제로 들어 있는 버전에서 새로 생성**한다. 정상 버전의 요약을 주면 오류 위치나 바람직한 동작을 미리 알려 주는 효과가 섞이기 때문이다.

수정 채점에는 연체일 `0, 3, 4, 24, 25`와 금액 `0, 99, 10000, 25000`의 조합인 20개 검사를 사용하고, F3 등 수정과 관계없는 함수의 기존 검사도 유지한다. 출력은 수정할 위치와 수정 내용을 담은 JSON으로 받는다. **설명만 맞는 답은 수정 성공으로 세지 않는다.** 문법 오류 없이 적용되고 모든 검사가 통과해야 한다. 정답 예시와 코드 문장이 달라도 같은 규칙을 만족하면 통과한다.

이 예시에서 ‘연체 관련 코드를 처리한다’는 요약만으로는 ②·③을 풀 수 없다. ‘연체’라는 단어가 비슷하다는 이유로 F3을 F1과 같은 정책으로 설명하면 ④·⑤를 틀린다. 그래서 계산 세부사항과 실제 연결 관계를 함께 시험해야 한다.

#### 11.2.4. 자료는 현재 문제, 개발용 코드, 평가용 코드로 나눈다

먼저 기존 기본 3문제와 확장 3문제는 **기존 동작이 유지되는지 확인하는 자료**로 남긴다. 같은 함수에서 파생한 문제도 있으므로 이것만으로 새 구조의 일반적인 성능을 판단하지 않는다.

새 설계의 개발용은 5개 Python 프로젝트에서 위 여섯 유형을 하나씩 만든 30문제다. 평가용은 개발에 쓰지 않은 10개 프로젝트에서 6개씩 만든 60문제다. 인증·청구·보고서 등 여러 기능을 포함하고, 함수의 계산식·분기·호출 구조도 다르게 만든다. 변수 이름이나 요율만 바꾼 동일한 코드를 별도 프로젝트로 세지 않는다. 프로젝트는 현재 medium 자료와 비슷한 약 600개 심볼 규모를 기준으로 하고, 정확한 파일·심볼 수와 원문 토큰 수를 기록한다.

개발 단계의 30문제에는 **동작은 같고 배치만 다른 두 버전**도 만든다. 하나는 필요한 함수와 상수를 한 파일에 두고, 다른 하나는 위 예시처럼 여러 파일에 나눈다. 두 버전의 동작 검사 결과가 같음을 먼저 확인한다. 같은 질문에서 파일을 나눈 경우에만 실패한다면, 계산 문제가 어려워진 것이 아니라 자료 연결이 부족해졌을 가능성을 확인할 수 있다. 이 두 버전을 독립된 문제 두 개로 세지는 않는다.

모든 비교 조건은 동일한 코드 버전과 질문을 사용한다. 정답표, 채점용 검사, 실험자의 해설은 검색·요약 대상에서 제외한다. 반대로 프로그램 자체의 주석과 공개 설명은 실제 코드의 일부로 취급한다. 요약은 질문을 공개하기 전에 프로젝트 전체를 대상으로 만든다. 정답 함수만 골라 좋은 요약을 만드는 방식은 사용하지 않는다.

첫 단계에서는 요약을 추가하지 않는다. 아래 비교로 현재 전달 구조의 수준을 측정한다.

|---|---|---|
| A. 현재 방식 | 기존 `symbol_filtered_select_bundle`로 후보 최대 24개를 제시 → AI가 심볼 하나 선택 → 같은 파일의 관련 코드 묶음 → 답변 | 현재 구현을 기준선으로 둔다. 묶음 깊이 1, 최대 심볼 8 등 실제 설정을 기록한다. |

B는 최초 선택을 A와 공유하며, 파일 간 참조를 최대 2단계, 함수·메서드는 최대 8개까지 따라가고 직접 참조하는 상수를 함께 가져온다. 예시에서는 F2에서 F1로 한 단계, F1에서 C1·C2로 한 단계면 필요한 코드가 모인다. 이름이 같은 함수라는 이유만으로 연결하지 않고 가져오기 경로와 정의 위치를 확인한다. 해석할 수 없는 동적 호출은 ‘연결 미확인’으로 남긴다. 선택 결과를 공유하더라도 각 조건의 비용에는 선택 단계 한 번을 포함한다.

A의 선택·묶음 로직은 유지한다. 새로운 질문 유형에 맞춘 출력 형식과 채점 연결만 추가한다. 여러 근거를 사용하는 문제에서는 ‘선택한 식별자가 정답 식별자 하나와 같아야 통과’라는 규칙을 공통 성공 기준으로 사용하지 않는다. 다른 시작점에서도 필요한 근거를 모아 정답에 도달할 수 있기 때문이다.

#### 11.2.6. 두 번째 실험의 첫 축: 요약에 어떤 정보를 남길 것인가?

요약 후보는 다음 세 가지다. 같은 함수 본문, 직접 참조한 상수, 가져오기 정보, 확인된 호출 대상을 입력으로 주되 결과를 만드는 규칙을 바꾼다. 아직 읽지 않은 하위 함수의 동작은 추측하지 않고 ‘하위 함수 원문 확인 필요’로 표시한다.

| 요약 방식 | 만드는 방법 | 확인할 가설 |
|---|---|---|
| S0. 일반 문장 요약 | AI가 코드의 역할과 동작을 짧은 문장으로 설명한다. | 간단한 설명만으로도 충분한가? 숫자와 예외 조건이 빠지는가? |
| S1. 항목을 정한 요약 | AI가 목적, 입력·출력, 분기·계산, 의존 관계, 부작용, 미확인 사항을 같은 순서로 작성한다. | 빠뜨리기 쉬운 정보를 항목으로 지정하면 코드 이해가 좋아지는가? |
| S2. 코드에서 확인한 사실과 설명을 결합 | S1과 같은 항목을 사용하되 경로·함수 서명·상수값·명확한 참조 대상은 코드 분석기가 채운다. AI는 그 사실들을 연결하는 동작 설명을 작성한다. | 코드에서 확정할 수 있는 값을 AI의 자유로운 서술에 맡기지 않는 것이 도움이 되는가? |

S2에서 ‘분석기가 확인했다’고 표시할 수 있는 것은 직접 읽은 정의와 해석 가능한 참조다. 예를 들어 C1의 값이 3인 것은 직접 확인할 수 있지만, 임의의 외부 라이브러리 호출에 부작용이 없다고 자동 단정할 수는 없다. 미확인 내용을 빈칸이나 추정 사실로 감추지 않고 표시한다. **S1과 S2의 차이는 문장 모양뿐 아니라 사실 추출·검증 기능을 추가한 효과**로 해석한다.

F1에 대해 남기고 싶은 정보의 예는 다음과 같다. 아래는 바람직한 정보 구성을 설명하는 예시이며, 실제 시험의 생성 요약을 이 내용으로 수동 교체하지 않는다.

| 요약 항목 | F1에서 보존할 정보의 예 |
|---|---|
| 역할과 반환값 | 원금이 아니라 추가 연체료를 정수로 반환한다. |
| 입력과 조건 | `amount`는 금액, `days`는 연체일이다. `days ≤ GRACE_DAYS`이면 0이다. |
| 계산 규칙 | 과금일은 `min(max(days−GRACE_DAYS, 0), 21)`. 금액 계산은 `amount×DAILY_BPS×과금일//10000`. |
| 의존 관계 | C1·C2를 사용한다. F2가 F1의 반환값을 원금에 더한다는 정보는 호출 관계와 F2의 원문을 근거로 상위 요약에서 설명한다. |
| 원문으로 돌아갈 위치 | F1의 심볼 식별자, C1·C2의 위치, 해당 코드 버전 |

‘연체료를 계산한다’는 짧은 설명은 역할을 알려 주지만 과금 상한과 계산식은 보존하지 못한다. 그렇다고 S0가 반드시 이런 부실한 요약을 만든다고 가정하지 않는다. 실제 생성 결과에서 어떤 조건이 남았고 빠졌는지 확인한다.

요약의 길이도 같게 제한한다. 함수 요약은 최대 192토큰, 상위 요약은 노드마다 최대 384토큰으로 시작하고, 원문 위치를 표시하는 문구도 포함해 센다. 짧은 함수를 더 긴 문장으로 풀어 쓰는 경우에는 압축에 성공했다고 기록하지 않는다. 요약이 한도를 넘으면 동일한 규칙으로 한 번 더 줄이도록 요청하고 그 비용을 센다. 그래도 한도를 넘거나 형식이 깨지면 생성 실패로 남기고, 해당 위치의 원문을 사용하는 대체 경로를 기록한다.

#### 11.2.7. 두 번째 실험의 둘째 축: 어떤 코드끼리 묶을 것인가?

프로젝트 전체를 처음부터 한 문장으로 요약하면 세부 규칙이 사라지기 쉽다. 아래 네 구조를 비교해 함수 수준과 프로젝트 수준을 어떻게 연결할지 정한다.

| 묶는 방식 | 구성 과정 | 위 예시에서 확인할 점 |
|---|---|---|
| G0. 함수별 요약만 사용 | 각 함수의 요약과 원문을 보관하고, 상위 요약은 만들지 않는다. | 계층 없이도 필요한 함수 요약들을 찾으면 충분한가? |
| G1. 파일·폴더 기준 | 함수 요약 → 같은 파일의 요약 → 같은 폴더의 요약 순으로 묶는다. | 구현하기 쉬운 파일 구조만으로 F2와 F1의 관계를 찾을 수 있는가? |
| G2. 내용의 의미 기준 | 내용이 비슷한 코드 요약을 묶고, 묶음 요약들을 다시 묶는다. RAPTOR의 의미 기반 군집화 절차를 코드 자료에 적용한다. | 서로 다른 파일의 관련 기능을 모으는가? ‘연체’라는 단어가 비슷한 F3을 같은 정책으로 혼동하는가? |
| G3. 실제 참조 관계 기준 | 확인된 호출·상수 참조로 연결된 함수와 설정을 묶고, 연결된 묶음들을 상위에서 설명한다. | F2→F1→C1·C2를 함께 담고, 독립적인 F3의 규칙은 구별하는가? |

G3의 묶음은 질문을 보고 정답 경로를 선택하는 방식으로 만들지 않는다. 프로젝트의 진입점과 호출 관계에서 자동으로 시작점을 정한다. 순환 호출은 하나의 묶음으로 먼저 정리하고, 진입점에서 닿지 않는 코드도 별도 묶음에 포함한다. 공통 보조 함수가 여러 기능에서 쓰이면 여러 묶음이 그 함수를 참조할 수 있게 한다. 각 묶음에 어떤 코드가 포함됐는지 보관해 누락과 중복을 센다.

내용 비교에서 묶음 구성까지 달라지는 것을 막기 위해, 각 G의 구성원은 S0~S2 요약을 생성하기 전에 고정한다. G2에서는 공통 원문 자료의 벡터로 첫 묶음을 정하고, 상위에서는 하위 벡터의 평균으로 묶는다. 이는 새 요약을 다시 벡터로 바꾸는 원 RAPTOR 절차를 **요약 내용의 효과를 분리하기 위해 변형한 부분**이다. 같은 구성원의 요약을 S0·S1·S2로 각각 작성해 비교한다.

G1~G3의 요약 생성 입력은 한 번에 2,048토큰, 하위 자료는 최대 4개로 제한한다. 묶음은 같은 구성원을 유지하도록 미리 나누고, 나뉜 관계도 기록한다. 노드당 최대 384토큰의 하위 요약 네 개와 연결 설명이 이 입력 한도에 들어가는지 확인한다. 실제 입력이 넘으면 일부를 몰래 생략하지 않고 생성 실패로 남긴다. 함수 요약 위에 상위 요약을 최대 3층까지 만들되, 묶어도 노드 수가 줄지 않으면 중단한다. 그 안에 최상위 노드 하나로 합쳐지지 않으면 여러 노드를 프로젝트 목차로 유지한다. 모든 코드를 한 문단에 억지로 넣지는 않는다. 순서, 무작위 초기값, 묶음 설정은 개발 단계에서 고정한다.

S0~S2의 세 요약 방식과 G0~G3의 네 묶음 방식을 조합하면 **12개 구조**가 된다. 예를 들어 S2+G3은 ‘코드에서 확인한 사실을 보존하면서 실제 참조 관계로 묶는 구조’다. 유망한 후보로 볼 수 있지만 미리 최선으로 정하지 않는다. 같은 G에서 S만 바꾸면 요약 내용의 효과를, 같은 S에서 G만 바꾸면 묶는 방식의 효과를 확인할 수 있다.

각 노드는 요약문 외에 원문 식별자, 하위 노드 목록, 코드 버전, 내용의 변경 여부를 확인하는 해시값을 가진다. 해시값은 내용이 바뀌었는지 대조하는 표식이다. 전체 목록은 외부에 저장하고, 모델이 읽는 위치 표식의 길이는 입력량에 포함한다. 어떤 요약도 원문과의 연결을 잃지 않도록 한다.

#### 11.2.8. 읽히는 양과 검색 방법을 맞춰 요약 효과만 비교한다

두 번째 실험에는 **R0: 요약 없는 원문 검색**을 반드시 둔다. R0와 12개 요약 구조는 같은 함수·상수 분할 결과, 파일 간 참조 정보, 검색기, 답변 모델을 사용한다. R0는 원문 자료를 검색하고, 요약 구조는 원문과 각 단계의 요약을 함께 검색한다. 모든 단계의 후보를 한 번에 비교하는 RAPTOR의 검색 아이디어를 적용한다. G3은 묶는 기준을 바꾼 별도 응용이며 원 논문과 동일한 방법이라고 표시하지 않는다.

공통 원문 자료에는 함수·메서드뿐 아니라 클래스 선언, 모듈 상수와 초기화 코드도 등록한다. 겹치는 코드 범위는 중복을 표시하고, 코드가 없다는 이유와 처리하지 못했다는 이유를 구분한다. 각 조각의 경로, 확인된 참조와 직접 읽은 상수 등 **기계가 추출한 기초 정보는 R0에도 동일하게 제공**한다. 요약 생성에 쓴 원문 묶음도 R0에서 검색할 수 있게 한다. 그래야 S2에만 상수나 연결 정보를 몰래 추가한 비교가 되지 않는다. 이번 포함 범위는 현재 실행기가 다루는 Python 코드로 한정하고, 다른 언어나 설정 파일까지 자동으로 이해한다고 주장하지 않는다.

검색에는 코드와 영어 설명을 같은 수치 공간에서 비교할 수 있는 `microsoft/unixcoder-base`의 인코더 기능을 고정해 사용한다. 여기서 인코더는 답을 작성하는 모델이 아니라 비슷한 코드와 설명을 찾기 위한 도구다. 공식 예시에 코드·설명의 벡터와 유사도를 구하는 방식이 제공되어 있다. 기존 실행기에 새로 연결할 구성 요소이므로 설치·호환성을 개발 단계에서 확인하고 버전을 고정한다. [공식 모델의 코드·설명 검색 예시](https://huggingface.co/microsoft/unixcoder-base)

현재 코드 문제와 맞춰 기계에 입력하는 질문·요약 지시는 영어로 통일하고, 보고서에는 한국어 설명을 함께 둔다. 한국어 질의 지원 성능은 이 시험 결과와 구분한다. 검색용 입력은 형식 표식을 포함해 512토큰 이내로 만들며, 긴 코드는 문장·분기 경계에서 나누고 어느 함수의 일부인지 표시한다. 내용이 잘린 사실을 숨기지 않는다. 나눠도 처리할 수 없는 경우에는 자료 처리 실패로 집계한다. 검색용 토큰과 Qwen 답변용 토큰은 별도로 센다.

답변 모델에 주는 **근거 자료 예산은 Qwen 기준 512, 1,024, 2,048토큰** 세 가지다. 후보는 같은 유사도 계산으로 정렬하고 동점은 식별자 순으로 처리한다. 조각은 통째로 넣으며, 남은 예산을 넘는 조각은 건너뛴다. 원문 위치 표식도 예산에 포함한다. 실제 사용량이 한도보다 적으면 그대로 기록한다.

처음에는 1,024토큰에서 R0와 12개 구조를 비교한다. 그다음 개발용 자료에서 남긴 상위 두 후보와 R0를 세 예산에서 비교한다. **현재 A와 새 구조의 차이에는 검색기와 자료 전달 구조의 변화도 들어 있다.** 요약 자체의 효과는 같은 새 검색기를 쓰는 R0와 요약 구조 사이에서 판단한다.

마지막으로 남긴 요약 후보에서는 다음 두 읽기 절차도 개발용 자료로 비교한다.

| 읽기 절차 | 1,024토큰 예산의 사용 예 | 확인할 것 |
|---|---|---|
| 요약·원문 혼합 검색 | 모든 단계의 후보를 점수순으로 최대 1,024토큰 선택한 뒤 답한다. | 요약 자체가 필요한 계산·조건을 충분히 담는가? |
| 요약으로 범위를 좁힌 뒤 원문 확인 | 처음 최대 512토큰으로 후보를 선택하고, 선택된 요약이 참조하는 원문을 같은 검색기로 다시 정렬해 남은 예산에 넣는다. 이미 읽은 원문은 중복하지 않는다. | 요약을 길잡이로 사용하고 정확한 식·조건은 코드에서 확인하는 편이 좋은가? |

다른 예산에서도 앞 단계에 최대 절반을 배정하고 남은 양을 원문 확인에 쓴다. 두 번째 절차가 원문을 더 읽었다면 그 양을 합산하며, 한도를 넘어 추가 자료를 주지 않는다. 두 절차 모두 최종 답변 모델은 한 번 호출한다. 추가 검색·추출 시간은 전체 시간에 포함한다. 오류 수정 문제의 수정 내용 출력은 최대 512토큰으로 하며, 이 문제만 11.1의 일반 답변 256토큰 제한에서 예외로 둔다.

예시의 ②에서는 상위 요약이 ‘F2가 F1의 연체료를 더한다’는 관계를 알려 주고, 원문 확인으로 C1=3, C2=125와 정확한 계산식을 확보할 수 있다. 반대로 요약이 이미 이 사실들을 정확하게 담았다면 추가 원문 확인의 이득은 적을 수 있다. 실제 성공률과 비용을 보고 어느 절차를 선택할지 정한다.

한 문제의 실행 기록은 ‘고정된 프로젝트에서 질문과 무관하게 요약 준비 → `invoice_total(10000, 4)` 질문 입력 → 선택된 원문·요약과 토큰 수 저장 → 모델의 JSON 답 저장 → 원본 함수를 실행해 얻은 10,125와 대조 → 읽힌 자료에 계산 근거가 있었는지 확인’ 순서로 남긴다. 검색이 F2만 가져왔는지, F1의 요약까지 가져왔는지, 정책값이 빠졌는지는 실제 입력 기록으로 확인한다. 실험자가 중간에 정답 자료를 끼워 넣지 않는다.

#### 11.2.9. 요약의 ‘효과’를 어떤 수치로 판정할 것인가?

정답표는 프로젝트를 실행하고 코드를 검토하여 요약 생성 전에 확정한다. 유형 ①~⑤는 값, 함수 집합, 호출 관계 등 문제에서 요구한 항목을 비교한다. 함수 집합은 순서를 무시하고, 호출 순서는 방향과 순서를 구분한다. ④의 변경 영향은 정해 둔 후보 함수와 입력 범위에서 변경 전후 실행을 대조한 결과로 정의한다. 임의의 모든 실행 경로를 완전히 분석했다고 주장하지 않는다. ⑥은 수정 적용과 동작 검사 통과로 판정한다.

| 지표 | 구체적으로 세는 것 | 이 지표가 필요한 이유 |
|---|---|---|
| 작업 성공 수 | 최종 평가의 여섯 유형별 10문제 중 성공 수와 전체 60문제 중 성공 수 | 요약이 실제 코드 이해·수정에 도움이 되는가? |
| 근거가 충분한 성공 수 | 정답을 맞혔고, 실제 읽은 자료에 필수 규칙과 관계도 있었던 문제 수 | 값을 추측해서 맞힌 경우와 근거를 갖고 푼 경우를 구분한다. |
| 조건 보존율 | 원문에 있는 필수 조건 중 요약에 정확히 남은 조건 수 ÷ 확인 대상 조건 수 | 유예 기간, 과금 상한, 정수 계산 등이 빠지거나 변하지 않았는가? |
| 잘못 추가한 사실 | 원문에 없는 조건·호출·부작용을 요약에 적은 건수 | 그럴듯하지만 틀린 설명을 별도로 잡는다. |
| 프로젝트 포함 범위 | 원문 위치로 연결된 함수·상수 수와 누락 수, 연결 미확인 수 | 질문에 나온 몇 함수만 잘 요약한 것을 전체 프로젝트 요약으로 오해하지 않는다. |
| 질의 비용 | 입력·출력 토큰, 최대 단일 입력, 검색·추출·답변을 합한 시간 | 같은 성공률에서 읽는 양과 시간이 줄었는가? |
| 구축·수정 비용 | 전체 요약을 처음 만드는 시간·토큰·저장량과, 코드 변경 후 다시 만드는 양 | 답변 비용을 줄이려고 과도한 사전 비용을 쓰지는 않는가? |

근거는 요약의 출처 목록에 F1이 있다는 이유만으로 충분하다고 판정하지 않는다. 예를 들어 ③에 답하려면 실제 읽은 원문이나 요약 안에 과금일 상한 21이 있어야 한다. 정답표에는 필요한 사실과 허용 가능한 근거 조합을 적어 둔다. 숫자·경로·버전은 자동 대조하고, 행동 설명과 조건 보존 여부는 비교 조건 이름을 가린 자료를 검토자가 확인한다. 별도의 AI가 좋다고 평가했다는 이유만으로 통과시키지 않는다.

비교 결과는 다음처럼 해석한다.

- B가 A보다 좋아졌지만 요약 구조가 R0보다 좋아지지 않았다면, 이번 개선의 주된 근거는 파일 간 코드 접근이며 요약의 추가 효과는 확인되지 않은 것이다.
- 같은 G에서 S2가 S1보다 좋아졌다면, 코드에서 확인한 사실을 보존하는 장치가 도움이 되었는지 오류 사례와 함께 확인한다.
- 같은 S에서 상위 요약이 있는 G1~G3이 G0보다 좋아졌다면, 함수별 설명을 넘어 관계를 묶은 효과를 뒷받침한다.
- ⑤의 구조 설명은 좋아져도 ③의 경계값이나 ⑥의 수정이 나빠졌다면, 프로젝트 이해에는 유용하지만 세부 코드 작업에 필요한 정보는 잃은 것이다. 전체 평균 하나로 숨기지 않는다.

#### 11.2.10. 코드를 바꾼 뒤에도 요약이 맞는지 시험한다

프로젝트에서 코드는 계속 바뀐다. 처음 만든 요약의 성적만 좋아서는 실제 코딩 어시스턴스에 충분하지 않다. 최종 후보에 대해 평가용 10개 프로젝트에서 정책값 또는 보조 함수 하나를 변경하고, 그 변경의 영향을 받는 질문 두 개씩 총 20문제를 추가로 푼다. 이는 원래 프로젝트에서 파생한 변경 시험이며 독립된 새 프로젝트 20개로 세지 않는다.

예시에서는 C1을 3에서 5로 바꾼다. 새 정답은 `invoice_total(10000, 4)=10000`, `late_fee(10000, 25)=2500`이다. 파일과 함수 이름은 같아도 과거의 10,125와 2,625를 답하면 틀린다.

| 갱신 조건 | 실제로 하는 일 | 확인할 점 |
|---|---|---|
| 이전 요약을 그대로 사용 | 원문만 새 버전으로 바꾸고 요약은 과거 것을 둔다. | 오래된 요약이 어떤 오류를 만드는지 보는 진단 조건이다. |
| 전체 재생성 | 바뀐 프로젝트에서 모든 요약을 다시 만든다. | 최신 자료로 모두 준비했을 때의 정확도와 비용을 기준으로 둔다. |
| 영향받은 부분만 갱신 | 바뀐 원문, 이를 참조한 함수 요약, 관련 상위 요약을 찾아 다시 만든다. | 전체 재생성과 비슷한 정확도를 더 적은 작업으로 유지할 수 있는가? |

부분 갱신에서는 함수 본문만 비교하면 안 된다. F1의 본문은 같아도 가져온 C1의 값이 바뀌었으므로, **직접·간접으로 읽은 원문의 버전도 추적**해야 한다. 의미 기준으로 묶는 G2에서는 내용 변경으로 묶음 구성 자체가 달라질 수 있다. 이 경우 변경된 벡터를 반영해 묶음도 다시 계산하고, 구성원과 내용이 모두 같은 묶음의 요약만 재사용한다. 모든 경우에 소수의 요약만 바꾸면 된다고 가정하지 않는다.

새 정답 성공 수, 오래된 사실을 실제 입력에 전달한 횟수, 재생성한 노드 수, 갱신 시간·토큰을 기록한다. 원문 버전과 맞지 않는 요약을 감지하면 원문을 읽는 경로도 별도로 기록하고 비용에 포함한다. ‘수정된 원문을 가리킨다’와 ‘요약문도 최신이다’를 구분하는 시험이다.

#### 11.2.11. 어떤 순서로 최종 구조를 선택하는가?

| 순서 | 수행할 실험 | 이 단계가 끝나면 알 수 있는 것 |
|---|---|---|
| 1. 현재 수준 진단 | 기존 6문제의 동작 확인, 개발용 30문제의 한 파일·여러 파일 버전에 A·B·O 적용 | 현재 선택·코드 연결·답변 중 어디가 부족한가? |
| 2. 요약 내용과 묶음 비교 | 개발용 분산 코드 30문제에서 R0와 12개 구조를 1,024토큰으로 비교 | 어떤 정보 구성과 묶음 방식이 유망한가? |
| 3. 읽는 양과 원문 확인 비교 | 개발용 자료에서 상위 두 후보와 R0를 세 입력 예산으로 비교하고, 요약 후보의 두 읽기 절차도 비교 | 입력량에 따른 성능 변화와 원문 확인의 가치가 무엇인가? |
| 4. 새 프로젝트 평가 | 구조·길이·검색·읽기 규칙을 고정하고 평가용 60문제에 적용 | 개발 자료에서만 잘된 결과인지 확인한다. 현재 A·B의 성적도 함께 제시한다. |
| 5. 유지 관리 평가 | 20개의 변경 후 질문에 세 갱신 조건을 적용 | 코드가 바뀌어도 정확도를 유지하는가? |

현재 A·B의 비용은 실제 전달량 그대로 보고하고, 고정된 근거 예산을 쓰는 새 구조와의 차이를 명시한다. 요약의 효과를 직접 비교하는 쌍은 동일 예산의 R0와 요약 후보다. 요약은 고정된 생성 설정으로 한 번 만들어 조건별 반복에 재사용하며, 질문을 세 번 실행했다고 요약 구축 비용을 세 번의 독립적인 품질 검증으로 간주하지 않는다.

개발 단계의 선택 순서도 먼저 정한다. **근거가 충분한 작업 성공 수가 많은 구조를 우선**하고, 동점에서는 전체 작업 성공 수, 질문 처리 입력·출력 토큰의 합, 전체 시간 순으로 비교한다. 단일 함수 문제·경계값 문제에서 R0가 맞힌 것을 추가로 틀린 사례와 요약의 잘못된 사실은 별도로 표시한다. 구축·갱신 비용도 함께 제시하며, 한 번 준비한 뒤 질문 1개·10개·100개를 처리하는 경우의 총비용을 각각 계산해 사용량에 따라 선택이 달라지는지 보여 준다. 이것은 측정한 평균 질문 비용을 이용한 계산이며, 100개의 새 질문을 실제로 시험한 성적으로 표시하지 않는다. 평가용 답을 본 뒤 요약 규칙을 고쳐 같은 자료에서 다시 우승 구조를 고르지 않는다.

마지막에는 인공 프로젝트 밖의 적용 가능성도 확인한다. 현재 작업 공간의 실제 실험 프로그램인 [Source Pointer 구현](/Users/oscar/Desktop/SecureCode/1st/source_pointer_test/source_pointer_bench)과 [Runtime Pointer 구현](/Users/oscar/Desktop/SecureCode/1st/runtime_pointer_test/runtime_pointer_bench)의 버전을 고정하고, 각각 코드 경로·반환값·오류 처리를 묻는 10문제를 별도로 만든다. 외부 모델 호출은 고정된 모의 응답으로 바꾸어 실행 정답을 확인한다. 이 자료는 요약 규칙을 고르는 데 쓰지 않는다. 두 구현은 같은 연구 프로젝트의 일부이므로, 서로 무관한 현업 프로젝트에 대한 검증으로 확대해서 설명하지 않는다.

최종 산출물은 ‘프로젝트 소개문 하나’가 아니라 **심볼·상수 색인, 확인된 파일 간 연결, 선택된 방식의 요약 계층, 원문으로 돌아가는 위치, 변경에 따른 갱신 규칙**이다. 실험 결과가 요약보다 원문 검색을 지지하면 그 결과를 받아들인다. 이 과정을 통해 선정하는 것은 시험한 프로젝트·모델·입력 예산에서 유리한 구조이며, 모든 프로젝트에서 항상 최적인 요약을 증명하는 것은 아니다.

### 11.3. MemGPT 적용 실험: 잊힌 과거와 최신 변경을 구별해 다시 찾는가?

#### 11.3.1. 한 번에 주는 문서 대신 시간순 대화 이력을 만든다

이 실험에서 AI는 여러 차례의 대화를 순서대로 처리한다. 앞의 대화 전체를 매번 넣어 주지 않고, 제한된 작업 기억만 다음 단계로 가져간다. 마지막 질문에서 필요한 과거 사실을 원문에서 다시 찾을 수 있는지 확인한다.

개발용 대화 이력은 5개, 평가용은 별도의 20개다. 이력 하나에는 약 2,000토큰인 대화가 5회, 합계 약 10,000토큰 들어간다. 여러 고객의 설정·변경·일반 문의를 섞고, 각 문장에 대화 회차·시각·기록 번호를 붙인다. 고객 이름만 바꾼 동일한 대화를 반복하지 않는다. 시각이 같아 변경 순서가 모호한 사례는 만들지 않는다.

각 이력에서 ‘마지막 시점의 값’, ‘처음 기록된 값’, ‘기록에 없는 사실’을 묻는 질문을 하나씩 만들어 개발용 15문제, 평가용 60문제로 구성한다. 질문은 다섯 번째 대화까지 처리한 뒤에 공개한다. 기억을 작성할 때 나중에 물어볼 세 질문을 미리 보여 주지 않는다.

#### 11.3.2. 변경 전후가 다른 문제와 정답의 예

다음은 한 대화 이력의 일부다. 아래 세 줄 외에도 다른 고객에 관한 대화가 충분히 들어가도록 구성한다.

| 시점과 기록 번호 | 원문 내용 |
|---|---|
| 첫 번째 대화 T1-04 | “고객 C14의 알림 수신 방식은 EMAIL입니다.” |
| 세 번째 대화 T3-08 | “고객 C14의 알림 수신 방식을 SMS로 변경했습니다. 기존 설정을 대체합니다.” |
| 네 번째 대화 T4-12 | “고객 C14의 고객지원 담당자는 이민수입니다.” 알림 방식에 관한 변경은 아니다. |
| 다섯 번째 대화 | 다른 고객의 기록이 이어진다. C14의 알림 방식은 다시 바뀌지 않는다. |

| 마지막에 주는 질문 | 정답 예 | 무엇을 확인하는가? |
|---|---|---|
| 다섯 번째 대화가 끝난 현재, C14의 알림 수신 방식은? | `{"value":"SMS","evidence":["T3-08"]}` | 변경된 최신값을 아는가? |
| C14의 알림 수신 방식으로 가장 처음 기록된 값은? | `{"value":"EMAIL","evidence":["T1-04"]}` | 최신값만 남긴 기억에서 과거값을 복구하는가? |
| C14의 출생 연도는? | `{"value":"NOT_FOUND","evidence":[]}` | 어디에도 없는 사실을 만들어 내지 않는가? |

원문 전체에 출생 연도가 없다는 것은 자료를 만드는 단계에서 확인한다. 반면 최신 질문에 EMAIL이라고 답하면 실제 과거에 있던 값이어도 오답이다. 이 실험에서 정답은 단순히 ‘어딘가에서 본 값’이 아니라 **질문의 시점 조건에 맞는 값**이다.

#### 11.3.3. 기억을 유지하고 과거를 읽는 세 조건

모델 자체의 입력·출력 한도는 공통 설정의 8,192토큰을 유지한다. 그 안에서 **이전 대화에서 가져올 수 있는 자료의 양을 1,536토큰**으로 제한한다. 이 1,536은 모델의 원래 문맥 한도가 아니라 기억 전략의 차이를 관찰하려고 둔 실험 예산이다. 지금 들어온 대화나 질문, 공통 도구 설명의 토큰은 따로 기록한다.

| 조건 | 다음 대화로 가져갈 내용 | 과거 원문 재조회 |
|---|---|---|
| A. 최근 내용만 유지 | 가장 최근 대화의 끝부분부터 최대 1,536토큰 | 허용하지 않음 |
| B. 요약과 최근 내용 유지 | 요약 최대 512토큰 + 최근 원문 최대 1,024토큰 | 허용하지 않음 |
| C. 요약·최근 내용·외부 기억 사용 | B와 같은 출발 예산에서, 필요하면 원문을 찾아 일부를 교체 | 허용 |

B와 C는 매 대화가 끝날 때 같은 지시로 한 번씩 요약을 갱신한다. 요약에는 유지할 가치가 있다고 판단한 사실·시점·출처 번호를 적도록 한다. 대화를 축적하는 단계에서는 B와 C의 요약을 동일하게 유지한다. C의 추가 조회와 기억 수정은 마지막 질문을 받은 뒤에 허용한다. 이렇게 해야 B와 C의 차이를 과거 원문 재조회에서 찾을 수 있다. 자동으로 과거 사실을 모두 요약에 보존해 주거나, 반대로 평가할 사실만 골라 지우지는 않는다. A는 모델이 요약하지 않고 프로그램이 최근 부분만 보존한다.

전체 원문은 대화가 들어올 때마다 외부 저장소에 기록한다. 각 기록에는 `이력 번호/대화 회차/문장 번호`로 찾아갈 수 있는 Source Pointer를 붙인다. C의 검색 도구는 검색 결과 목록을 Runtime Pointer로 보관하고, 요청한 페이지만 꺼내 모델에 전달한다. A와 B에서도 같은 원본 기록은 보존하되, 모델에는 재조회 기능을 제공하지 않는다.

C의 조회 도구는 `search_history(query, page)`다. 고객 번호와 검색어가 포함된 원문 조각을 최신 시각 순으로 돌려주며, 한 페이지는 출처·시각을 포함해 최대 512토큰이다. 자료를 미리 256토큰 이하 조각으로 나누고, 한 페이지에는 최대 두 조각을 넣는다. 페이지를 바꾸어 이전 검색 결과를 더 읽을 수 있다. 도구가 ‘최신 정답은 SMS’처럼 답을 계산해 주지는 않는다. 변경 문장과 시각을 읽고 어떤 값이 질문에 맞는지 결정하는 일은 AI가 한다.

질문당 조회는 최대 4회, 512토큰 요약의 수정은 최대 2회, 최종 답변을 포함한 AI 호출은 최대 8회다. 조회한 과거 원문도 1,536토큰 예산에 포함한다. 새 결과를 넣을 때 오래된 최근 원문부터 밀어내고, 요약과 남은 원문·조회 결과·그 결과를 옮겨 적은 메모의 합계가 한도를 넘지 않게 한다. 도구 호출 기록에 과거 본문이 남아서 예산 밖의 추가 기억이 되는 경우도 막는다. 각 단계에서 실제로 모델에 들어간 과거 자료를 저장해 이 규칙을 확인한다.

#### 11.3.4. 한 이력을 처리하는 순서와 채점 방법

실행 프로그램은 다음 순서로 진행한다.

1. 빈 기억에서 첫 번째 대화를 입력하고, 조건에 맞게 최근 내용이나 요약을 저장한다.
2. 두 번째부터 다섯 번째까지도 ‘유지한 기억 + 새 대화’를 입력하고 기억을 갱신한다. 모델이 이전 호출의 대화를 자동으로 기억한다고 가정하지 않는다.
3. 다섯 번째 대화 직후의 상태를 저장한다. 이 상태를 각각 복제하여 세 질문을 별도로 푼다. 첫 질문에서 찾은 SMS 기록이 다음 질문에 공짜로 남지 않도록 한다.
4. 각 질문에서 A와 B는 보유 기억으로 답한다. C는 필요하면 원문을 검색하고 페이지를 넘긴 뒤 답한다. 답할 근거가 없으면 `NOT_FOUND`를 제출할 수 있다.
5. 값과 근거 기록 번호를 정답표와 대조하고, 사용한 기억·검색 결과·최종 답을 함께 저장한다.

예시에서 C14가 나오는 원문이 위 세 기록뿐이고 각 기록이 한 조각에 들어 있다면, `search_history("C14", 1)`은 최신 두 기록 T4-12와 T3-08을 반환한다. 현재값 질문에는 SMS라고 답할 수 있지만 처음값은 아직 확인하지 못했다. 이어서 `search_history("C14", 2)`를 호출하면 T1-04를 읽고 EMAIL을 제출할 수 있다. 이처럼 조회 번호와 반환 문장을 실제 기록에서 따라갈 수 있어야 한다. B가 요약에 처음값과 최신값을 모두 잘 남겨 두었다면 재검색 없이도 같은 정답을 낼 수 있다. 외부 검색이 항상 필요한 것처럼 결과를 미리 정하지 않는다.

최신값 20문제, 과거값 20문제, 정보 없음 20문제의 성공 수를 각각 낸다. 값과 근거가 모두 맞아야 성공이며, 기록에 없는 문제는 `NOT_FOUND`와 빈 근거 목록이 정답이다. 최신 질문에 과거값을 쓴 횟수, 원문에 없는 값을 만든 횟수, 조회 횟수와 토큰도 따로 집계한다. 전체 시간은 대화 다섯 회를 처리한 비용과 질문 처리 비용을 구분하여 보고한다.

**기존 실험과 다른 이유.** 기존 Source Pointer·Runtime Pointer는 한 번의 질문에서 이미 있는 파일이나 방금 생성된 큰 객체를 조회했다. 이번 설계는 여러 차례 입력을 받는 동안 무엇을 남길지 결정하고, 나중에 다른 시점의 사실을 되찾게 한다. 그래서 단순 추출 정확도에 더해 ‘과거값과 최신값을 구별했는가’, ‘요약에서 빠진 사실을 복구했는가’를 측정할 수 있다. MemGPT의 기억 관리 원리를 현재 도구로 적용한 시험이며, 논문의 모델·대화 자료를 그대로 재현하는 것은 아니다.

### 11.4. ReWOO 적용 실험: 도구 연결을 먼저 계획하면 반복 입력이 줄어드는가?

#### 11.4.1. 한 번의 큰 결과에서 여러 번 이어지는 조회로 바꾼다

이 실험에서는 첫 번째 도구가 준 번호가 두 번째 도구의 입력이 된다. 다음 도구를 부르기 위해 필요한 번호를 AI가 직접 여러 번 읽을 수도 있고, AI가 처음 작성한 계획에 따라 실행 프로그램이 대입할 수도 있다. **사전 계획의 효과와 Runtime Pointer의 효과를 따로 측정**하는 것이 핵심이다.

외부 서비스의 변동을 없애기 위해 로컬 시험 도구를 만든다. 이 도구들은 고정된 주문·고객·계정·계약·정책 자료를 읽어 결과를 돌려주며, 실제 주문을 변경하지 않는다. 모든 비교 조건에서 질문·원본 자료·도구 설명·호출 제한을 같게 둔다.

개발용은 5개 주문에 대해 아래 조건을 조합한 30개 실행 시나리오, 평가용은 별도의 10개 주문으로 60개 시나리오를 만든다.

| 변화시킬 요소 | 값 | 구체적인 뜻 |
|---|---|---|
| 연결 단계 수 | 2, 3, 5단계 | 주문→정책 / 주문→고객→정책 / 주문→고객→계정→계약→정책 |
| 도구 결과 크기 | 호출당 약 1,000 또는 6,000토큰 | 필수 번호와 설정은 유지하고, 무관한 과거 내역을 덧붙여 크기를 바꾼다. |

평가 시나리오 수는 `10개 주문 × 3종류 연결 길이 × 2종류 크기 = 60`이다. 같은 주문에서 파생한 여섯 시나리오는 독립된 주문 여섯 개로 세지 않는다. 결과 크기는 Qwen의 실제 토큰 계산으로 확인하고 정확한 값을 기록한다. 도구 설명에는 반환 자료의 항목 구조를 공개하지만, 특정 주문의 실제 번호나 정답값은 공개하지 않는다.

연결 길이별 자료는 별도 상태로 만든다. 2단계에서는 주문 결과에 정책 번호가 있지만, 5단계에서는 주문에 고객 번호, 고객에 계정 번호, 계정에 계약 번호, 계약에 정책 번호만 둔다. 5단계 자료의 주문에 정책 번호까지 넣어 지름길이 생기지 않게 한다. 내부 번호는 주문 번호에서 추측할 수 없도록 생성하고, 정답과 무관한 내용에서도 그 연결이 새어 나오지 않는지 확인한다.

#### 11.4.2. 문제와 정답, 세 번의 조회 예

**문제:** “주문 ORD-017에 적용되는 결제 재시도 정책의 최대 재시도 횟수와 기본 대기시간을 구하라. `max_retries`와 `base_delay_ms` 두 항목으로 답하라.”

아래 표에는 결과 중 필요한 항목만 보였다. 실제 시험 도구 결과에는 정해진 크기만큼 무관한 내역도 포함한다.

| 호출 | 반환되는 필수 항목 | 다음 단계에서 하는 일 |
|---|---|---|
| `get_order("ORD-017")` | `{"customer_id":"C014"}` | C014의 고객 자료를 조회한다. |
| `get_customer("C014")` | `{"policy_id":"P07"}` | P07 정책을 조회한다. |
| `get_policy("P07")` | `{"max_retries":4,"base_delay_ms":7500}` | 두 설정값을 최종 답으로 제출한다. |

**정답:** `{"max_retries":4,"base_delay_ms":7500}`

처음 문제를 받은 모델의 입력에는 정답 4와 7,500이 들어 있지 않다. 앞서 조회한 결과의 번호를 올바르게 연결해야 마지막 정책을 읽을 수 있다. 다른 고객과 정책도 자료에 넣어, C014 대신 다른 고객을 조회하면 다른 값이 나오게 한다.

#### 11.4.3. 사전 계획과 포인터를 네 조건으로 나누어 비교한다

| 조건 | 다음 행동을 정하는 방법 | 도구 결과를 모델에 전달하는 방법 |
|---|---|---|
| A. 단계별 판단 + 전체 본문 | 결과를 읽은 뒤 다음 도구를 결정 | 실제 결과 전체를 대화에 누적 |
| B. 사전 계획 + 전체 본문 | 처음에 도구 연결 계획을 작성하고 실행 프로그램이 수행 | 실행 중에는 모델을 다시 부르지 않고, 마지막 답변 단계에 전체 결과를 전달 |
| C. 단계별 판단 + 포인터 | 결과가 생길 때마다 다음 행동을 결정 | 작은 결과 설명과 보관 번호를 받고, 필요한 항목만 읽음 |
| D. 사전 계획 + 포인터 | 처음 작성한 계획의 참조를 실행 프로그램이 해석 | 큰 본문은 외부에 두고, 최종 답에 필요한 항목만 읽음 |

예시에서 B와 D의 계획은 다음처럼 작성할 수 있다. 이 계획도 실제로는 AI가 만들어야 하며 정답 계획을 대신 넣어 주지 않는다.

```text
#E1 = get_order("ORD-017")
#E2 = get_customer(#E1.customer_id)
#E3 = get_policy(#E2.policy_id)
최종 답에 사용할 항목 = #E3.max_retries, #E3.base_delay_ms
```

실행 프로그램은 먼저 `#E1`에 첫 결과를 저장한다. 다음 줄의 `#E1.customer_id`를 실제 값 C014로 바꾸어 두 번째 도구에 넣는다. 이어서 `#E2.policy_id`를 P07로 바꾸어 세 번째 도구에 넣는다. **중간 번호를 대입할 때마다 AI에게 큰 결과를 다시 읽힐 필요가 없다.** 마지막에는 답변 모델이 실제로 읽은 값을 정해진 JSON 형식으로 제출한다.

`#E1.customer_id`처럼 JSON 안의 특정 항목을 참조하는 문법은 이번 실험에서 추가하는 규칙이다. 논문의 표기 전체를 그대로 옮긴 것으로 설명하지 않는다. 네 조건 모두 같은 항목 참조 문법과 실행 프로그램을 사용할 수 있게 하여, 사전 계획 조건에만 더 강력한 도구를 주는 차이를 줄인다.

C와 D에서 도구는 `보관 번호, 결과 종류, 조회 가능한 항목 이름`을 반환한다. 필요한 본문을 읽는 `read_result(보관번호, 항목경로)`는 요청한 항목만 최대 256토큰으로 반환한다. 도구 연결용 항목은 참조 해석기가 직접 읽어 다음 호출에 대입할 수 있다. 최종 답에 들어갈 두 값은 답변 모델에 실제로 전달하며 그 입력량도 센다. 숫자를 보지 않은 모델이 포인터만으로 답했다고 처리하지 않는다.

A와 C에서는 매 단계 AI가 다음 행동을 정한다. B와 D에서는 전체 연결 계획을 먼저 작성한 뒤 도구들을 실행하고 마지막 답을 만든다. 공통으로 업무 조회 최대 5회, 항목 읽기를 포함한 전체 도구 호출 최대 20회, AI 호출 최대 12회를 허용한다. 잘못된 계획이나 도구 오류는 기록하며, 정답을 아는 실험자가 중간 계획을 고치지 않는다. 이번 기본 시험에는 별도의 계획 재작성 절차를 넣지 않는다.

#### 11.4.4. 입력량이 어디서 달라지는지 한 문제로 확인한다

세 번의 결과가 각각 약 1,000토큰이라고 가정하자. 다음은 **자료 본문만 계산한 설명용 예**이며 실제 전체 토큰 측정값이 아니다.

| 단계 | A. 단계별 판단 + 전체 본문 | B. 사전 계획 + 전체 본문 |
|---|---:|---:|
| 첫 도구 결과 뒤 다음 행동 결정 | 첫 결과 1,000토큰을 읽음 | 실행 프로그램이 다음 참조를 대입하므로 이 시점의 AI 호출 없음 |
| 두 번째 결과 뒤 다음 행동 결정 | 첫째·둘째 결과 합계 2,000토큰을 읽음 | 이 시점의 AI 호출 없음 |
| 마지막 답 작성 | 세 결과 합계 3,000토큰을 읽음 | 세 결과 합계 3,000토큰을 읽음 |
| 결과 본문을 읽힌 누적량 | 약 6,000토큰 | 약 3,000토큰 |

실측에서는 이 표에 없는 질문, 도구 설명, 계획, 이전 행동 문장, 출력도 모두 센다. C와 D는 큰 결과 대신 작은 설명과 선택한 항목을 읽으므로 본문 양이 달라지지만, 그만큼 추가된 항목 읽기와 판단 비용도 포함한다. **B는 누적 읽기를 줄여도 마지막에 3개 결과를 한꺼번에 읽는 부담이 남는다.** 결과가 각각 6,000토큰이면 전체 본문 조건은 8,192토큰 한도에서 실패할 수 있다. 이를 삭제된 사례로 숨기지 않고 입력 한도 초과로 집계한다.

#### 11.4.5. 어떤 비교로 어떤 효과를 주장할 수 있는가?

최종 JSON의 두 값과 자료형이 모두 맞는지를 먼저 채점하고, 실제 조회 경로가 질문한 주문의 정책으로 이어졌는지도 확인한다. 주요 성공 기준은 둘을 모두 충족하는 것이다. 조회 없이 값을 우연히 맞힌 경우는 값만 맞은 사례로 분리한다. 정답을 포함한 오류 메시지, 한 항목만 맞은 답, 잘못된 고객의 정책은 실패다. 각 연결 길이·결과 크기별로 성공 수, 잘못 연결한 번호, 계획 형식 오류, 호출 제한 초과, 입력 한도 초과를 분리한다. 모든 AI 호출의 누적 입력·출력량, 한 번의 호출에서 가장 컸던 입력량, 전체 시간도 기록한다.

| 비교 | 해석할 수 있는 차이 |
|---|---|
| A와 B | 전체 본문을 사용하는 상황에서 사전 계획이 반복 판단·입력을 줄이는가? |
| C와 D | 포인터를 이미 사용하는 상황에서도 사전 계획이 추가로 도움이 되는가? |
| A와 C | 단계별로 판단할 때 포인터가 본문 입력과 한도 초과를 줄이는가? |
| B와 D | 사전 계획이 있을 때도 필요한 항목만 전달하는 것이 별도의 효과를 내는가? |

A와 D만 비교하면 두 변경의 효과가 섞인다. 위 네 비교를 함께 봐야 ‘계획을 먼저 세워서 좋아졌는지’, ‘읽는 자료를 줄여서 좋아졌는지’를 구별할 수 있다. 시간은 모든 조건의 실패율과 함께 제시하고, 정상 완료 시간의 직접 비교는 양쪽 모두 성공한 같은 시나리오끼리 수행한다. 빠르게 오류가 난 실행을 빠른 문제 해결로 해석하지 않는다.

**기존 실험과 다른 이유.** 기존 Runtime Pointer는 큰 결과 한 개에서 필요한 값을 꺼내 최종 답을 만드는 구조였다. 여기서는 중간 결과의 번호가 다음 도구를 결정하므로, 각 추출이 맞아도 연결을 틀리면 마지막 답이 틀린다. 기존 결과 보관·추출 기능에 여러 도구의 자료, 참조 해석기, 계획 실행기, 단계별 비교 실행기를 추가해야 한다. 이 기본 시험이 검증하는 범위는 미리 설명된 도구 구조를 따라가는 연결이며, 도중에 예외를 발견해 계획을 크게 바꿔야 하는 실제 서비스의 모든 상황까지 포함하지는 않는다.

### 11.5. 이 설계를 구현하고 결과를 읽는 순서

먼저 위의 문제 예시를 자료 파일과 정답 파일로 옮기고, **AI를 사용하지 않는 정답 확인 프로그램으로 예시의 계산·조회 결과부터 검증**한다. 이후 개발용 자료에서 입력 예산, 검색 설정, 도구 형식, 실행 제한을 고정한다. 마지막으로 분리해 둔 평가용 자료를 실행한다. 정답표와 검색 자료가 섞이지 않았는지도 이 순서에서 확인한다.

한 문제의 실행 기록은 최소한 다음 항목을 담아야 한다. ‘정답률 80%’만 남기면 어떤 단계가 좋아졌는지 다시 확인하기 어렵다.

| 기록 항목 | 남길 내용의 예 |
|---|---|
| 문제와 정답 | 질문 원문, 허용 입력, 정답값, 필수 근거, 값·근거 비교 규칙, 코드 수정 검사 |
| 자료가 선택된 과정 | 검색어, 선택된 함수·문단·기록 번호, 검색 점수, 도구 연결 계획 |
| AI가 실제 읽은 것 | 각 호출의 전체 입력과 자료 예산, 요약·포인터·추출 결과 |
| AI가 제출한 것 | 최종 JSON, 수정 코드, 생성한 요약·기억, 도구 호출·연결 계획 |
| 채점과 실패 원인 | 값·근거의 일치 여부, 도구 연결의 정확성, 오류·한도 초과 |
| 비용 | 사전 준비 시간, 질문 처리 시간, 입력·출력 토큰, 호출 횟수, 최대 단일 입력 |

성적표는 각 방법 안의 비교 조건별로 만든다. 예를 들어 60문제에서는 한 문제 차이가 약 1.67%포인트이므로, 백분율만 쓰지 않고 ‘몇 개 중 몇 개’도 함께 쓴다. 같은 코드 프로젝트·문서·대화 이력·주문에서 파생된 문제의 관련성을 유지해 결과를 해석하고, 범위를 추정할 때에도 이 원본 단위로 묶는다. 작은 인공 자료에서의 차이를 모든 실제 프로젝트에 적용되는 성능 차이로 확대하지 않는다.

이 세 실험의 성과는 하나의 순위로 합치기보다 다음 질문에 각각 답하는 형태로 정리한다. **RAPTOR 응용은 코드의 규칙과 관계를 보존한 요약으로 프로젝트 이해와 수정을 개선했는지, MemGPT는 시점에 맞는 과거 기록을 복구했는지, ReWOO는 도구 연결을 유지하면서 반복 입력을 줄였는지**를 확인한다. 이렇게 해야 현재 세 포인터 방식에 어느 기능을 추가할 근거가 생겼는지 구체적으로 판단할 수 있다.
