# Symbol Index·Source Pointer·Runtime Pointer의 정량평가 실험 설계와 동작 원리

작성일: 2026-10-05  
분석 대상: `/Users/oscar/Desktop/SecureCode/1st`에 저장된 실험 코드, 문제·정답 정의, 기존 실행 결과  
작성 목적: AI에 익숙하지 않은 독자도 세 방식의 효과를 무엇으로, 어떻게 측정했는지 이해할 수 있도록 설명한다.

이 실험들의 공통 질문은 **“AI에게 자료 전체를 읽히는 대신, 필요한 부분을 찾아 전달하면 정답을 유지하면서 입력량과 처리 부담을 줄일 수 있는가?”**이다. 이를 확인하기 위해 같은 문제와 자료를 놓고, AI에게 자료를 전달하는 방법을 바꾸어 비교했다.

분석 결과, 세 실험 모두 정답 여부·입력량·처리 시간을 숫자로 비교할 수 있는 구조를 갖추고 있다. 다만 저장된 자료는 소수의 인공 문제를 사용한 기능 검증에 가깝다. 최초 분석에서 발견한 Symbol Index의 두 채점 결함은 2026-10-05에 수정했다. 아래에서는 기존 답변을 수정된 규칙으로 다시 채점한 결과와, 모델을 새로 실행한 결과를 구분한다. 과거 원본 실행 기록은 보존하고 수정·검증 결과는 별도 파일에 저장했다.

## 1. 세 실험을 이해하기 위한 공통 설명

### 1.1. ‘포인터’와 ‘입력 한도’는 무엇인가?

여기서 AI는 질문을 읽고 답을 만드는 언어모델을 뜻하며, 아래 표에서는 이를 LLM이라고도 표시한다. 언어모델은 한 번에 읽을 수 있는 자료의 양에 한도가 있다. 이를 **문맥 한도(context window)**라고 한다. 이 한도를 넘으면 자료를 입력하는 단계에서 실행이 실패할 수 있다.

포인터는 자료 본문을 대신하는 **찾아가기용 표식**이다. 도서관에서 책 전체를 복사해 전달하는 대신 청구기호를 알려주고, 필요한 쪽만 찾아 읽게 하는 것과 비슷하다. 이 실험의 포인터는 프로그램이 해석하는 문자열이며, 컴퓨터의 실제 메모리 주소를 AI에게 직접 공개하는 방식은 아니다.

| 방식 | 찾아갈 대상 | 쉬운 설명 |
|---|---|---|
| Symbol Index | 소스코드의 함수·클래스·메서드 | 프로그램의 목차에서 필요한 함수 항목을 찾는다. |
| Source Pointer | 디스크에 이미 저장된 로그·문서·JSON 파일 | 파일의 위치를 알려주고 필요한 기록·문단·항목만 꺼낸다. |
| Runtime Pointer | 프로그램을 실행하는 도중 도구가 만들어 낸 값 | 방금 받은 큰 결과물을 보관하고, 보관 번호로 필요한 부분을 꺼낸다. |

포인터 문자열만 짧게 만드는 것으로 실험이 완성되는 것은 아니다. **포인터가 실제 자료로 연결되고, 필요한 내용을 정확하게 추출하며, 그 내용으로 정답을 만들 수 있어야 한다.** 세 실험은 이 과정을 실행해 확인한다.

### 1.2. 무엇을 같게 하고 무엇을 바꾸었는가?

한 문제를 비교할 때에는 질문과 정답, 원본 자료, 사용 모델을 유지하고 **자료를 제공하는 경로와 범위**를 바꾼다. 기본 비교 구조는 다음과 같다.

| 비교 조건 | AI에게 전달하는 자료 | 이 조건으로 확인하는 것 |
|---|---|---|
| 전체 입력 | 원본 자료 전체 | 모든 내용을 직접 읽게 할 때의 성공 여부와 부담 |
| 정답 위치 제공, `oracle` | 실험 프로그램이 미리 알고 있는 위치에서 추출한 자료 | 필요한 자료를 정확히 가져왔다고 가정했을 때 답변이 가능한지 |
| AI가 선택, `select` | 먼저 작은 목록을 제공하고, AI가 선택한 위치에서 추출한 자료 | 위치나 도구를 고르는 과정까지 포함해 작동하는지 |

`oracle`은 AI가 정답을 알고 있다는 뜻이 아니다. **실험 프로그램이 올바른 자료 위치 또는 추출 방법을 미리 지정한다는 뜻**이다. 최종 답은 여전히 AI가 작성한다. 따라서 `oracle`과 `select`의 차이를 보면 선택 단계의 추가 부담과 실패 가능성을 살펴볼 수 있다.

자료는 실험용으로 생성했다. 정답이 들어 있는 부분과 질문을 고정하고, 관계없는 함수·로그·문단·사용자 설정을 추가했다. 이를 통해 “자료가 커져도 필요한 내용만 전달하는 방식은 작은 입력을 유지하는가?”를 확인한다. 실제 운영 서비스에서 수집한 데이터로 검증한 것은 아니다.

### 1.3. 공통 실행 조건과 숫자의 의미

기존 보고서와 실행 로그에서는 Apple M3 Pro 기반 MacBook Pro, llama.cpp의 Metal 실행 환경, Qwen2.5 Coder 7B Instruct의 Q5_K_M 모델이 확인된다. 실행 코드는 답변의 무작위성을 줄이는 설정인 `temperature=0`을 사용하며, 기본 난수 초기값은 `seed=1`이다. 주로 문제별·방식별 1회 실행한 기록을 비교한다.

| 실험 묶음 | 설정한 문맥 한도 | 최대 생성 길이 |
|---|---:|---:|
| Symbol Index 초기 medium 실험 | 65,536 토큰 | 64 토큰 |
| Symbol Index 전체 코드 재시도 1문제 | 131,072 토큰 | 64 토큰 |
| Symbol Index 확장 문제의 후속 bundle 실험 | 8,192 토큰 | 64 토큰 |
| Source Pointer 최종 실험 | 32,768 토큰 | 128 토큰 |
| Runtime Pointer 최종 실험 | 32,768 토큰 | 128 토큰 |

토큰은 AI가 문장을 처리할 때 사용하는 작은 글자·단어 조각이다. **문자 수와 토큰 수는 서로 다른 단위**이며, 자료 내용에 따라 변환 비율이 달라진다.

| 측정 항목 | 실제 측정·판정 방법 | 해석할 때의 주의점 |
|---|---|---|
| 문제 성공률 | 미리 정의한 정답 조건을 최종 답변이 만족했는지 판정 | 아래 표의 `3/3`은 문제 3개를 모두 통과했다는 뜻이다. 동일 문제를 3번 반복한 결과가 아니다. |
| 선택 성공 | 선택한 함수 주소 또는 추출한 내용이 정해진 조건을 만족하는지 판정 | 방식마다 정의가 다르므로 서로 같은 지표처럼 비교하면 안 된다. |
| 구성 입력 길이 | 질문·자료·지시문을 합쳐 만든 입력의 문자 수 | 입력 거부 사례도 길이는 계산할 수 있다. 프로그램이 덧붙이는 대화 역할 표식은 이 문자 수에서 제외된다. |
| 실측 입력 토큰 | llama.cpp 실행 기록의 `prompt_tokens` | 처리가 거부된 경우 누락될 수 있다. 이때 문자 수를 4로 나눈 추정값을 실측값으로 취급하지 않는다. |
| 입력 읽기 시간 | 실행 기록의 `prompt_eval_ms` | AI가 입력을 처리하는 구간의 시간이다. 모든 작업 시간을 뜻하지 않는다. |
| LLM 호출 시간 | 외부 모델 실행 프로그램의 시작부터 종료까지 잰 `wall_seconds` | 실행 프로그램 시작, 모델 적재, 입력 처리, 답변 생성 등이 포함된다. 자료 생성·색인 구축·추출 도구 실행 시간은 포함하지 않는다. |
| 입력 한도 초과 | 실행 종료 상태와 오류 메시지 확인 | 실패까지 짧게 걸린 시간을 빠른 문제 해결로 해석하지 않는다. |

AI가 먼저 위치를 고르고 나중에 답하는 방식은 **AI 호출이 2번**이다. 이 경우 입력 문자 수·입력 토큰·호출 시간을 두 번의 합계로 계산한다. 예를 들어 800토큰이라는 기록은 두 호출의 누적 입력량일 수 있으며, 한 번에 800토큰을 읽었다는 뜻은 아니다.

계산식은 다음과 같다.

- 문제 성공률 = 성공한 문제 수 ÷ 전체 문제 수 × 100
- 입력량 감소율 = (1 − 포인터 방식의 입력량 ÷ 전체 입력 방식의 입력량) × 100
- 호출 시간 감소율 = (1 − 포인터 방식의 호출 시간 ÷ 전체 입력 방식의 호출 시간) × 100

감소율은 같은 문제끼리, 같은 단위로 비교한다. 특히 시간 비교는 두 방식 모두 정상적으로 답한 문제를 사용해야 해석이 명확하다. 본문에서는 Source Pointer와 Runtime Pointer의 문서 문제를 이런 비교 사례로 사용한다.

## 2. Symbol Index: 필요한 코드의 위치를 찾아 읽는 실험

### 2.1. 검증하려는 효과와 문제 설계

이 실험은 코드 전체를 읽히는 대신 함수 단위로 찾아 읽게 했을 때, 입력량을 줄이면서 코드에 관한 질문에 답할 수 있는지 확인한다. 동시에 **함수 하나만으로 충분한지, 그 함수가 참조하는 주변 코드도 필요한지**를 확인한다.

실험용 Python 프로젝트에는 인증, 요금 계산, 보고서 처리 코드가 들어 있다. 여기에 답과 관계없는 코드와 이름이 비슷한 함수를 추가했다. 주요 비교 대상인 medium 자료는 **27개 파일, 638개 심볼**로 구성된다. 심볼은 여기서 함수·클래스·메서드처럼 이름을 가진 코드 단위를 뜻한다.

| 문제 묶음 | 질문의 내용 | 미리 정한 정답·판정 조건 | 설계 의도 |
|---|---|---|---|
| 기본 | 만료된 인증 토큰에서 발생하는 오류 문자열은? | 정확한 값 `TOKEN_EXPIRED` | 함수 밖에 정의된 상수 값까지 확인해야 한다. |
| 기본 | 연체료가 붙지 않는 유예 기간은? | `3` | 함수 안의 조건문을 읽어 값을 찾는다. |
| 기본 | 보고서 캐시 키의 형식은? | 답에 `report:`와 `:v` 포함 | 반환 문자열의 기본 구조를 확인한다. |
| 확장 | 만료 오류의 상수 이름이 아닌 실제 문자열 값은? | `TOKEN_EXPIRED`, 상수 이름은 제외 | 주변 상수 정의가 필요한 상황을 명시한다. |
| 확장 | 공백과 `/`가 포함된 보고서명으로 만들어지는 최종 키는? | `report:team-a:north/east_plan:v12` | 보조 함수까지 읽고 문자열 변환 결과를 계산해야 한다. |
| 확장 | 4일 연체, 금액 10,000일 때 상태와 연체료는? | `status=late, fee=125` | 두 함수의 결과를 종합하고 금액을 계산해야 한다. |

첫 문제의 인증 토큰은 로그인 등의 유효성을 확인하는 정보로, AI 입력량의 단위인 토큰과는 다른 뜻이다. 기본 문제도 모두 단일 함수만으로 해결되는 것은 아니다. 첫 문제의 함수 본문에는 `TOKEN_EXPIRED_MESSAGE`라는 이름만 있고, 실제 값은 함수 밖에 있다. 이 차이를 이용해 “찾은 함수가 맞아도 전달한 정보가 부족할 수 있다”는 점을 시험한다.

확장 문제의 연체료는 코드에 따라 `10,000 × 0.0125 × (4 − 3) = 125`이다. 정답은 AI의 주관적인 평가로 정한 것이 아니라, 생성한 코드의 규칙으로 정한다.

### 2.2. 실제로 어떻게 동작하는가?

먼저 프로그램이 Python 코드를 구문 구조에 따라 분석하여 함수 등의 이름, 파일 경로, 시작·끝 줄 번호를 색인에 저장한다. 각 항목에는 `memory://symbol/services/auth_service.py::validate_token`과 같은 식별자가 붙는다. AI가 이 식별자를 선택하면, 프로그램이 색인에 저장된 위치를 찾아 실제 코드를 읽어 준다.

| 실행 모드 | AI가 읽는 내용과 동작 | AI 호출 수 |
|---|---|---:|
| `full_repo` | 프로젝트의 모든 Python 코드를 읽고 답한다. | 1 |
| `full_file` | 실험 프로그램이 지정한 정답 파일 전체를 읽고 답한다. | 1 |
| `line_span` | 정답 함수의 시작·끝 줄을 미리 알려주고 해당 범위를 읽힌다. | 1 |
| `symbol_oracle` | 정답 심볼 식별자를 미리 지정하여 그 코드만 읽힌다. | 1 |
| `symbol_select` | 전체 심볼 목록을 보고 AI가 하나를 고른 뒤, 해당 코드로 답한다. | 2 |
| `symbol_bundle_oracle` | 정답 심볼과 관련 상수·보조 함수 등을 묶어 읽힌다. | 1 |
| `symbol_filtered_select_bundle` | 질문의 파일명·함수명 등을 이용해 후보를 줄이고, AI가 고른 심볼의 관련 코드까지 묶어 읽힌다. | 2 |

`full_file`과 `line_span`도 필요한 위치를 실험 프로그램이 미리 아는 조건이다. 따라서 이들의 낮은 처리 시간을 “AI가 스스로 정답 파일을 찾은 시간”으로 해석해서는 안 된다.

후속 방식의 동작 순서는 **질문 → 파일명·이름으로 후보 축소 → AI의 심볼 선택 → 관련 코드 보강 → AI의 답변**이다. 후보 수의 기본 상한은 24개다. 관련 코드 묶음은 같은 파일의 상수와 보조 함수, 질문에 언급된 함수 등을 정해진 규칙에 따라 추가한다. 여러 파일에 걸친 모든 의존 관계를 완전하게 추적하는 구현은 아니다.

### 2.3. 무엇을 숫자로 확인했는가?

다음 표는 medium 자료의 **기본 문제 3개에 대한 과거 실행 기록을 수정된 규칙으로 재채점한 결과**다. 입력 토큰과 시간은 문제당 평균이며, 선택 방식은 두 호출을 합산했다. 토큰 수는 반올림했다.

| 모드 | 문제 성공 | 실측 평균 입력 토큰 | 평균 LLM 호출 시간 |
|---|---:|---:|---:|
| 전체 코드 `full_repo`, 65k 설정 | 0/3 — 모두 입력 거부 | 산출 불가 | 성공 처리 시간 없음 |
| 정답 파일 `full_file` | 3/3 | 256 | 2.29초 |
| 정답 줄 범위 `line_span` | 2/3 | 199 | 2.12초 |
| 정답 심볼 `symbol_oracle` | 2/3 | 199 | 2.13초 |
| 전체 색인에서 선택 `symbol_select` | 2/3 | 33,871 | 181.19초 |
| 정답 심볼과 관련 코드 `symbol_bundle_oracle` | 3/3 | 305 | 2.60초 |
| 후보 축소·선택·관련 코드 `symbol_filtered_select_bundle` | 3/3 | 824 | 6.26초 |

전체 코드의 입력은 약 67,188토큰으로 65k 실행 설정을 넘었다. 문맥 한도를 131,072로 늘린 별도 재시도는 **첫 문제 하나만** 실행했으며, 67,188토큰·612.87초를 기록했지만 실제 문자열 대신 상수 이름을 답했다. 이 1문제 결과를 다른 방식의 3문제 평균과 직접 나누어 대표적인 성능 향상률로 삼기는 어렵다.

표의 후속 bundle 방식은 후보 축소와 관련 코드 보강을 함께 적용했다. 기본 bundle 원기록에는 문맥 한도를 포함한 전체 실행 옵션이 저장되어 있지 않아 초기 실험과 모든 설정이 같았는지도 확정하기 어렵다. 별도로 실행한 확장 문제의 bundle 실험은 8,192토큰 설정이 명시되어 있다. 따라서 181.19초에서 6.26초로 줄었다는 관찰은 후속 구현 전체의 결과이며, 후보 축소 한 요소만의 순수한 효과를 분리한 수치는 아니다.

기본 문제에서 `symbol_select`는 정답 심볼을 **3/3 선택**했지만 답변은 2/3만 통과했다. 반면 관련 코드를 추가한 후속 선택 방식은 선택과 답변이 모두 3/3이었다. 이 구분을 통해 **위치 선택의 성공과 필요한 정보 확보의 성공이 서로 다르다**는 것을 확인할 수 있다.

확장 문제의 과거 답변을 수정된 규칙으로 재채점한 결과는 다음과 같다.

| 모드 | 수정 후 재채점한 과거 답변 | 심볼 선택 일치 |
|---|---:|---:|
| `full_file` | 1/3 | 선택 단계 없음 |
| `symbol_oracle` | 0/3 | 위치를 미리 제공 |
| `symbol_select` | 0/3 | 3/3 |
| `symbol_bundle_oracle` | 1/3 | 위치를 미리 제공 |
| `symbol_filtered_select_bundle` | 1/3 | 3/3 |

**이 표에는 수정한 채점 규칙을 적용했다.** 문자열 변환 문제는 최종 문자열을 대소문자까지 정확하게 비교한다. 과거 답변은 `/`를 잘못 바꿨고, 금액 문제는 125 대신 150을 답했으므로 위 성공 건수는 이전과 같다. 채점 오류를 고친 것과 모델이 답을 더 잘하게 된 것은 구분해야 한다. 수정 내용과 검증 결과는 5.2절에 설명한다.

### 2.4. 왜 정량적인 평가가 가능한가?

첫째, 모든 모드에 같은 코드와 문제를 사용하고 정답을 미리 정했다. 따라서 작은 코드 조각을 전달한 것이 실제 답변 성공으로 이어졌는지 비교할 수 있다.

둘째, 심볼 선택 결과를 정해 둔 심볼 식별자와 대조하고, 최종 답변은 별도로 채점한다. 잘못된 위치를 고른 실패와 올바른 위치를 찾고도 답을 틀린 실패를 구분할 수 있다. 다만 초기 `symbol_select`의 종합 성공은 선택과 답변이 모두 맞아야 하고, 후속 선택 방식의 종합 성공은 최종 답변 기준이다. 수정 후에는 두 방식 모두 선택·답변 호출의 정상 종료도 필수 조건이다. 저장된 선택 지표와 답변 지표를 함께 보아야 한다.

## 3. Source Pointer: 저장된 파일에서 필요한 부분만 꺼내는 실험

### 3.1. 검증하려는 효과와 문제 설계

이 실험은 디스크에 이미 있는 외부 파일을 대상으로 한다. 큰 파일 전체를 AI에게 주는 방식과, 파일 위치를 가리키는 표식 및 추출 도구로 필요한 부분만 주는 방식을 비교한다.

실험 자료는 로그, 문서, JSON의 세 종류다. JSON은 항목 이름과 값을 계층적으로 저장하는 데이터 형식으로, 여기서는 고객별 설정을 담고 있다.

| 자료 | small 생성 설정 | medium 생성 설정 | 질문과 정답 |
|---|---:|---:|---|
| 결제 로그 | 650줄 | 5,000줄 | 요청 `REQ-042031`의 실패 원인은 `velocity_limit`, 재시도 대기값은 `7500` |
| 운영 문서 | 48개 절 | 320개 절 | `Payment Gateway Retry Policy` 절의 최대 재시도 횟수는 `4`, 지연 변동 비율은 `17` |
| 고객 설정 JSON | 일반 고객 420개와 목표 고객 1개 | 일반 고객 2,800개와 목표 고객 1개 | `northwind-prod`의 사용 여부는 `true`, 정책은 `pointer-first` |

small은 작은 자료, medium은 더 큰 자료를 뜻하는 실험 구분이다. 두 크기는 정답과 문제 유형을 유지하고 주변 자료량을 늘린 조건이다. 따라서 단순히 쉬운 문제와 어려운 문제를 비교하기보다, **같은 정보를 더 큰 자료에서 찾아야 할 때의 변화**를 살펴보는 설계다.

### 3.2. 실제로 어떻게 동작하는가?

프로그램은 파일별로 위치 표식, 자료 종류, 크기, 사용할 수 있는 도구와 설명을 목록에 저장한다. 예를 들어 로그에는 `source://log/logs/checkout_gateway.log`라는 표식이 붙는다. 이 표식을 해석하면 실제 파일 경로로 연결된다.

| 모드 | 실행 순서 | AI 호출 수 |
|---|---|---:|
| `full_source` | 해당 문제의 정답 파일 전체 → AI 답변 | 1 |
| `pointer_oracle` | 미리 지정한 파일·도구·검색 조건 → 내용 추출 → AI 답변 | 1 |
| `pointer_select` | 질문과 파일 목록·도구 설명 → AI가 도구와 조건 선택 → 내용 추출 → AI 답변 | 2 |

`full_source`는 세 파일을 전부 합치는 방식이 아니다. **그 문제의 정답이 들어 있는 파일 하나 전체**를 제공한다. 여기에서도 정답 파일을 찾는 단계는 이미 해결된 기준 조건이다.

자료 형식에 맞춘 추출 도구는 세 개다.

- 로그 검색 도구는 요청 번호와 일치하는 줄 및 주변 줄을 가져온다.
- 문서 추출 도구는 지정한 제목과 맞는 절을 가져온다.
- JSON 추출 도구는 `tenants.northwind-prod.security`처럼 항목 이름으로 표시한 경로의 값을 가져온다.

AI는 “어느 파일에서 어떤 조건으로 꺼낼 것인지”를 정하고, 실제 파일 읽기와 검색은 일반 프로그램이 수행한다. 이후 AI는 추출된 짧은 내용을 읽고 최종 답을 작성한다. 최종 구현은 AI가 쉼표로 나열한 같은 계층의 JSON 항목도 추출하도록 보완되어 있다.

### 3.3. 무엇을 숫자로 확인했는가?

최종 결과 파일은 각 크기에서 3문제 × 3모드, 즉 9개 실행 사례를 담는다. 다음 표의 입력 길이와 토큰은 문제당 평균이다. `—`는 전체 입력 방식에 처리 거부가 섞여 있어 세 문제 모두에 대한 실측 토큰 평균을 제시하지 않았다는 뜻이다.

| 자료 크기 | 모드 | 문제 성공 | 평균 구성 입력 길이, 문자 | 실측 평균 입력 토큰 |
|---|---|---:|---:|---:|
| small | `full_source` | 1/3 | 67,974 | — |
| small | `pointer_oracle` | 3/3 | 896 | 286 |
| small | `pointer_select` | 3/3 | 2,950 | 778 |
| medium | `full_source` | 1/3 | 477,083 | — |
| medium | `pointer_oracle` | 3/3 | 896 | 286 |
| medium | `pointer_select` | 3/3 | 2,952 | 780 |

small의 전체 입력 방식은 로그에서 입력 한도를 초과했고, 문서에서는 정답을 냈다. JSON은 실행됐지만 `pointer-first` 대신 `pointer-preferred`라고 답했다. medium에서는 로그와 JSON 모두 입력 한도를 초과했고, 문서만 정상적으로 답했다.

최종 `pointer_select`는 두 크기 모두 필요한 값이 들어 있는 내용을 3/3 추출했고, 최종 답변도 3/3 통과했다. 선택과 답변을 합친 평균 LLM 호출 시간은 small 6.43초, medium 6.42초였다. 정답 추출 방법을 미리 제공한 `pointer_oracle`은 각각 2.47초, 2.44초였다.

시간과 토큰을 더 공정하게 비교하려면 **양쪽이 모두 정답을 낸 동일 문서 문제**를 비교하는 것이 좋다.

| 문서 문제 | 전체 입력 토큰 → AI 선택 방식 토큰 | 토큰 감소율 | 전체 입력 호출 시간 → AI 선택 방식 호출 시간 | 호출 시간 감소율 |
|---|---|---:|---|---:|
| small | 2,626 → 706 | 73.1% | 9.18초 → 5.77초 | 37.2% |
| medium | 16,770 → 708 | 95.8% | 63.68초 → 5.76초 | 90.9% |

이 표의 선택 방식에는 첫 번째 선택 호출의 비용도 포함되어 있다. 다만 파일 읽기와 추출 도구 시간은 포함되지 않은 LLM 호출 구간의 비교다.

### 3.4. 왜 정량적인 평가가 가능한가?

정답이 되는 요청 번호·문서 절·고객 항목을 데이터 생성 단계에서 정해 두었다. 따라서 도구가 필요한 값을 가져왔는지와 AI가 그 값을 답했는지를 자동으로 확인할 수 있다. 또 small과 medium에서 정답을 고정했으므로, 자료량 증가가 입력량에 미친 영향을 직접 비교할 수 있다.

실제로 AI 선택 방식의 평균 입력은 약 778토큰에서 780토큰으로 거의 같았다. 이것은 이 시험 조건에서는 원본의 불필요한 부분이 늘어도 AI에게 전달되는 자료는 작게 유지되었다는 뜻이다. 큰 파일 전체를 읽히다가 입력 한도를 넘는 문제에서도 답을 낼 수 있었다.

다만 `selection_correct`는 **“선택한 도구의 추출 결과에 정답 값이 포함되는가”**를 검사한다. 정해진 도구 이름·인자가 유일하게 맞았는지를 엄격하게 비교하는 지표는 아니다. `pointer_oracle`의 선택 성공 표시는 프로그램이 참으로 지정한 값이므로 AI의 선택 능력 점수로 볼 수 없다.

또한 AI가 보는 목록은 세 파일뿐이고, 설명에는 목표 문서 제목이나 JSON 경로가 포함된다. 따라서 이 실험은 안내가 있는 제한된 환경에서의 추출 도구 선택을 검증한다. 수많은 미지의 파일을 스스로 탐색하는 성능까지 측정한 것은 아니다. 추출 도구가 내부적으로 파일 전체를 읽거나 JSON 전체를 해석하는 경우도 있어, 입력 토큰이 일정하다는 사실만으로 파일 처리 시간이나 컴퓨터 메모리 사용량도 일정하다고 말할 수는 없다.

## 4. Runtime Pointer: 실행 중 만들어진 큰 결과를 보관하고 꺼내는 실험

### 4.1. 검증하려는 효과와 문제 설계

Source Pointer가 이미 저장된 파일을 대상으로 한다면, Runtime Pointer는 **도구가 실행 중 반환한 값**을 대상으로 한다. 예를 들어 조회 도구가 거대한 고객 설정 결과를 돌려주었을 때, 그 결과 전체를 다음 AI 입력에 넣을 필요가 있는지를 시험한다.

실험에서는 외부 서비스에 실제로 접속하는 대신 세 종류의 생성 함수를 사용한다. 하나는 결제 로그 문자열, 하나는 운영 문서 문자열, 하나는 고객 설정 객체를 만든다. 생성 규모는 Source Pointer와 같은 small·medium 설정이며, 질문도 요청 번호·문서 정책·고객 설정을 확인하는 세 종류다. 고객 설정 문제의 항목 이름은 `runtime_pointer_enabled`로 바뀌며, 목표 값은 `true`와 `pointer-first`다.

### 4.2. 실제로 어떻게 동작하는가?

1. 실험 프로그램이 문제에 맞는 생성 함수를 실행해 큰 결과물을 만든다.
2. 결과물을 프로그램 내부의 보관소인 `RuntimeStore`에 넣는다.
3. `runtime://json/fetch_tenant_snapshot/0001` 같은 보관 표식을 발급한다.
4. 포인터 방식에서는 AI에게 본문 전체 대신 표식, 자료 종류, 크기, 사용 가능한 추출 도구와 설명을 알려준다.
5. 추출 도구가 표식에 연결된 실제 값을 꺼내 필요한 부분을 추출한다.
6. AI가 짧은 추출 결과로 답한다.

큰 원본 값은 컴퓨터의 메모리에 그대로 존재한다. 효과의 핵심은 **AI의 입력에 원본 전체를 반복해서 펼쳐 넣지 않는 것**이다. 원본 저장에 필요한 메모리 자체를 없애는 기술로 해석해서는 안 된다.

| 모드 | 비교 조건 | AI 호출 수 |

도구는 포인터를 실제 값으로 바꾼 다음 로그 검색, 문서 절 추출, JSON 경로 추출을 수행한다. 현재 구현은 이 세 가지 추출 작업에 맞춘 것이다.

이 시험에서는 **문제·모드마다 보관소를 새로 만들고 결과물 한 개만 저장한다.** 생성 함수를 무엇으로 할지는 실험 프로그램이 이미 정해 놓는다. 따라서 AI가 여러 생산 도구를 계획적으로 연결하거나, 보관된 여러 결과물 중 올바른 하나를 찾아가는 문제까지 포함하지는 않는다.

### 4.4. 왜 정량적인 평가가 가능한가?

또한 원문 길이, 추출 결과 길이, AI의 누적 입력량을 각각 기록한다. 원문이 수십만 문자여도 추출 결과는 짧고 최종 답변은 정답인지를 함께 확인하므로, 단순히 데이터를 빼서 입력만 줄인 경우와 구분할 수 있다.

small에서 medium으로 커져도 AI 선택 방식의 평균 입력이 756토큰에서 약 757토큰으로 유지된 결과는, **이번 질문에 필요한 작은 부분만 모델에 전달하는 구조가 작동했다는 근거**다. 다만 생성 함수 실행·보관·추출 시간은 LLM 호출 시간에서 빠져 있으므로, 전체 시스템 처리 시간이 같은 비율로 줄었다고 주장할 수는 없다.

선택 성공 지표는 Source Pointer와 마찬가지로 추출 결과에 정답 값이 포함됐는지를 확인한다. 보관된 객체가 한 개이고 위치 설명도 제공되는 조건이므로, 이 결과는 복잡한 여러 단계 작업이나 여러 객체 간 참조의 안정성을 검증한 수치가 아니다.

## 5. 정량적 결과를 설명할 때 함께 밝혀야 할 사항

### 5.1. ‘숫자로 측정했다’와 ‘일반적인 성능을 입증했다’는 범위가 다르다

이 실험은 정답·비교 조건·측정 항목이 정해져 있어 수치 평가가 가능하다. 하지만 세 문제에서 3/3을 얻었다고 해서 실제 업무의 모든 질문에서 100% 성공한다고 해석할 수는 없다. 문제 하나의 차이가 성공률 약 33.3%포인트에 해당한다.

Source Pointer와 Runtime Pointer의 small·medium은 같은 세 문제 유형과 목표 값을 공유한다. 두 크기의 결과를 합쳐 서로 독립적인 새로운 여섯 문제를 검증했다고 표현하는 것도 적절하지 않다. 또한 Source Pointer의 선택 지시문과 JSON 추출 처리는 기존 문제에서 관찰한 실패를 바탕으로 보완되었다. 최종 성적은 그 문제들에 맞춰 보완된 구현의 성적이며, 별도로 숨겨 둔 새로운 평가 자료의 성적은 아니다.

세 방식은 대상 자료와 선택 난도가 다르다. Symbol Index는 수백 개의 코드 항목, Source Pointer는 세 파일 목록, Runtime Pointer는 한 개의 실행 결과를 대상으로 했다. 따라서 평균 토큰이나 시간만 나란히 놓고 세 방식의 우열을 정할 수는 없다.

두 번째 수정에서는 코드 블록이나 바깥 인용부호 같은 답변 포장만 제거한다. 문자열 내부의 대소문자·슬래시·공백은 그대로 검사한다. 따라서 올바른 값을 코드 블록에 넣어 답해도 통과하지만, `/`를 `_`로 바꾸거나 `team-a`를 `TEAM-A`로 바꾸면 실패한다. 기준 문제 파일은 보존되는 `symbol_test/tasks/medium_hard_tasks.json`에 두었고, 기존 작업 폴더의 문제 파일도 같은 내용으로 갱신했다.

**채점 검증 테스트: 9개 모두 통과.** 오류 로그에 정답 숫자가 들어 있는 경우, 선택 단계가 실패한 경우, 최종 호출이 실패한 경우를 각각 거부하는지 확인했다. 정상적인 정답은 모든 비교 모드에서 통과하는지도 검사했다. 문자열 정답은 실험용 Python 함수를 실제로 실행한 반환값과 대조했고, 올바른 답·잘못된 슬래시·잘못된 대소문자·추가 설명 등을 구분했다. 이는 모델이 문제를 푼 횟수가 아니라 채점 규칙에 대한 테스트 수다.

**과거 기록 재채점: 43건 중 1건의 판정 변경.** 기본 실험 21건, 확장 실험 21건, 131k 문맥의 별도 1건을 재채점했다. 기본 `full_repo` 유예 기간 문제가 정답에서 오답으로 바뀌어 원기록의 1/3이 0/3으로 바로잡혔다. 나머지 42건의 판정은 유지됐다. 문자열 문제의 과거 답변은 실제 값도 틀렸으므로, 정답을 통과시킬 수 있게 고쳤다고 해서 기존 점수가 올라가지는 않았다. 이전 보고서도 이 실행 오류를 이미 0/3으로 해석했기 때문에, 기본 결과표의 성공 건수는 그대로다.

## 8. RepoCoder: 같은 코드 빈칸을 ‘검색 한 번’과 ‘재검색’으로 각각 채워 보는 실험

대상 논문: Fengji Zhang 외, **RepoCoder: Repository-Level Code Completion Through Iterative Retrieval and Generation**, EMNLP 2023. [학회 논문 정보](https://aclanthology.org/2023.emnlp-main.151/)

### 8.1. 무엇을 확인하려는 실험인가?

AI에게 프로그램의 일부를 작성시키려면 그 프로그램만의 함수 이름과 사용 규칙을 알아야 한다. 그런데 필요한 규칙이 다른 파일에 있을 수 있다. RepoCoder는 관련 코드를 찾아 읽힌 뒤 작성하게 하고, **한 번 작성한 초안을 다음 검색의 단서로 쓰면 더 적절한 코드를 찾을 수 있는지** 시험한다.

이 실험에서 AI가 하는 일은 기존 코드에 관한 설명을 쓰는 것이 아니라 **가려진 코드 부분을 채우는 것**이다. 연구자는 그 코드가 실제로 작동하는지 확인한다. 아래에서는 논문에 있는 여러 시험 중 ‘함수 본문 완성’ 시험을 중심으로 설명한다. [원문 2~3절](https://aclanthology.org/2023.emnlp-main.151.pdf#page=3)

### 8.2. 어떤 자료와 문제를 준비하는가?

실험자는 실제 Python 프로젝트에서 함수를 골라, 원래 본문을 정답 자료로 따로 보관하고 본문 앞까지의 코드를 입력 문제로 만든다. 또한 같은 프로젝트에서 검색할 수 있는 코드 조각과, 완성한 함수의 동작을 검사할 테스트를 준비한다. 함수 시험은 6개 프로젝트의 **373문제**다. 전체 연구는 14개 프로젝트를 사용했고, 별도로 한 줄 완성과 API 호출 완성을 각각 1,600문제씩 시험했다. API 호출은 다른 기능을 불러 쓰는 코드다. [원문 3절·표 1](https://aclanthology.org/2023.emnlp-main.151.pdf#page=4)

**설명용 예시:** 회원의 최종 결제 금액을 계산하는 함수의 본문을 가렸다고 하자. 다른 파일에는 회원 할인율과 그 할인 기능을 쓰는 코드가 있다. 시험용 검사에는 ‘가격 10,000원인 회원의 결제 금액은 9,000원’이라는 조건이 준비되어 있다.

| 이 예시에서 준비한 것 | 역할 |
|---|---|
| 결제 함수의 이름·인자·그 앞의 코드 | AI가 처음 받는 작성 문제 |
| 다른 파일의 할인 함수와 사용 예 | 검색으로 추가할 수 있는 참고 자료 |
| 가려 둔 원래 본문과 동작 검사 | 답을 제출한 뒤 평가할 때 사용하는 자료 |

일반 비교 조건에서는 가려 둔 정답 본문을 그대로 검색해 복사하게 해서는 안 된다. 공개 구현도 대상 파일에서 문제 위치와 검색 후보의 범위를 구분한다. [저자 공개 검색 코드](https://raw.githubusercontent.com/microsoft/CodeT/main/RepoCoder/search_code.py)

### 8.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

실험자는 같은 빈칸 문제를 세 조건에 각각 넣는다. 세 조건이 다른 문제를 푸는 것이 아니다.

| 실행 순서 | 현재 파일만 제공 | 검색·생성 1회 | 검색·생성 2회 |
|---|---|---|---|
| 1. 첫 입력 준비 | 본문 앞까지의 코드만 준다. | 작성 중인 코드와 비슷한 참고 코드 조각을 검색한다. | 왼쪽의 ‘검색·생성 1회’와 같은 첫 검색을 한다. |
| 2. 첫 코드 작성 | AI가 본문을 작성하고 제출한다. | AI에게 원래 문제와 검색한 코드 조각을 함께 주어 본문을 작성하게 한다. 여기서 제출한다. | 같은 방식으로 첫 본문을 작성하되, 이를 다음 검색에 쓸 초안으로 둔다. |
| 3. 두 번째 검색 | 없음 | 없음 | 원래 코드와 초안의 일부를 합쳐 새 검색 단서를 만든다. 그 단서로 참고 코드를 다시 찾는다. |
| 4. 최종 제출 | 처음 작성한 본문 | 처음 작성한 본문 | 원래 문제와 새로 검색한 참고 코드를 AI에게 주어 본문을 다시 작성하게 하고 제출한다. |

핵심은 **두 번째 검색의 단서가 달라진다**는 점이다. 결제 함수 예시라면 첫 초안에 등장한 할인 관련 이름이 새 검색 단서가 될 수 있다. 이것이 항상 더 좋은 자료를 찾아 준다고 가정하지 않고, 실제 점수로 확인한다. 공개 구현에서도 검색한 코드와 원래 미완성 코드를 합쳐 새 입력을 구성한다. [원문 2절](https://aclanthology.org/2023.emnlp-main.151.pdf#page=3), [입력 구성 코드](https://raw.githubusercontent.com/microsoft/CodeT/main/RepoCoder/build_prompt.py)

이때 ‘2회’는 **같은 빈칸을 완성하기 위해 검색과 작성을 두 차례 한다**는 뜻이다. 채점 결과를 알려 주면서 정답이 나올 때까지 고치는 절차가 아니다. 위 일반 조건에서 재검색에 사용하는 것은 모델의 초안이며, 실험자가 보관한 정답은 아니다.

### 8.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

제출한 본문을 함수에 넣고 준비된 실행 테스트를 돌린다. 해당 검사들을 모두 통과하면 그 문제는 성공, 하나라도 통과하지 못하면 실패로 센다. 이 과정을 373문제에 적용하여 `성공 문제 수 ÷ 373 × 100`을 계산한다. 따라서 한 문제에 여러 검사가 있어도 아래 표의 분모는 검사 수가 아니라 **함수 완성 문제 수**다. [원문 4.3절·표 3](https://aclanthology.org/2023.emnlp-main.151.pdf#page=6)

GPT-3.5-Turbo를 사용한 결과는 다음과 같다.

| 조건 | 실행 테스트 통과율 | 이 수치를 읽는 방법 |
|---|---:|---|
| 현재 파일만 제공 | 23.32% | 373문제 중 약 87문제를 통과한 수준이다. |
| 검색·생성 1회 | 38.34% | 참고 코드를 한 번 추가하자 통과율이 높아졌다. |
| 검색·생성 2회 | 42.63% | 초안을 이용한 재검색을 더하자 1회 조건보다 4.29%포인트 높아졌다. |
| 정답을 검색 단서에 사용한 참고 조건, `oracle` | 42.63% | 정답 일부를 검색 단계에 제공하는 유리한 조건과 비교한 값이다. 일반 사용 절차가 아니다. |

한 줄·API 호출 시험에서는 완성 코드가 정답 문자열과 정확히 일치하는 비율과 글자 수준의 유사도도 측정했다. 함수 실행 테스트와 문자열 유사도는 서로 다른 채점 방법이다. [원문 표 2~3](https://aclanthology.org/2023.emnlp-main.151.pdf#page=6)

### 8.5. 이 결과로 어디까지 말할 수 있는가?

이 표가 보여 주는 것은 **같은 모델의 코드 작성 결과가 참고 자료와 재검색에 따라 개선되었다**는 것이다. 검색·생성 2회에는 추가 작업이 있으므로, 통과율만 보고 시간이나 비용도 줄었다고 말할 수는 없다. 또한 준비된 테스트에 없는 오류까지 모두 검사했다는 뜻도 아니다.

Symbol Index에 연결하면, 함수 하나를 골라 읽힌 뒤 정보가 부족할 때 관련 코드를 더 찾아 읽히는 시험을 설계할 수 있다. 다만 현재 로컬 실험은 코드에 관한 질문에 답하는 시험이고, RepoCoder는 코드를 작성해 검사하는 시험이다. 두 성적을 직접 같은 정답률로 비교하기보다 **추가 자료를 찾은 효과를 어떤 동작 검사로 확인했는지** 참고하는 것이 적절하다.

함수 평가를 그대로 재현하려면 별도 준비가 필요하다. 저자들은 함수 실행·평가에 사용한 내부 라이브러리는 라이선스 때문에 공개하지 않았다고 밝혔다. [공개 구현의 함수 평가 안내](https://github.com/microsoft/CodeT/tree/main/RepoCoder)

## 9. Repoformer: 같은 코드 문제에서 ‘항상 검색’과 ‘필요할 때 검색’을 비교하는 실험

대상 논문: Di Wu 외, **Repoformer: Selective Retrieval for Repository-Level Code Completion**, ICML 2024. [학회 논문 정보](https://proceedings.mlr.press/v235/wu24a.html)

### 9.1. 무엇을 확인하려는 실험인가?

빈칸을 채우는 데 현재 파일만으로 충분한 문제도 있고, 다른 파일에 정의된 함수의 사용법이 필요한 문제도 있다. 모두 같은 방식으로 검색하면 불필요한 대기 시간이 생긴다. Repoformer는 **검색하지 않아도 되는 문제를 미리 구별해도 코드 품질을 유지할 수 있는지** 확인한다.

RepoCoder가 ‘검색을 더 해 볼 것인가’를 다뤘다면, 여기서는 ‘이번 문제에 검색을 사용할 것인가’를 판단하는 장치를 시험한다. 이 장치는 미리 학습시킨 모델이다. 따라서 **판단법을 가르치는 학습 단계와, 새 문제로 성능을 재는 평가 단계**를 나누어 이해해야 한다. [원문 3절](https://raw.githubusercontent.com/mlresearch/v235/main/assets/wu24a/wu24a.pdf#page=3)

### 9.2. 어떤 자료와 문제를 준비하는가?

실제 프로젝트의 코드 일부를 가려 빈칸 문제를 만든다. 학습 자료를 만드는 동안에는 연구자가 정답 코드를 알고 있다. 같은 학습 문제를 검색 없이도 풀게 하고 검색한 코드를 제공해서도 풀게 한 뒤, 각각의 답이 정답 코드와 얼마나 비슷한지 비교한다. 검색했을 때 점수가 더 좋아지면 ‘검색이 도움이 된 경우’로 표시한다. 이 사례들을 이용해 모델에 검색 필요 여부와 코드 작성을 함께 학습시킨다. [저자 연구 소개의 학습 절차](https://repoformer.github.io/)

**설명용 예시:** ‘현재 파일에 보이는 숫자에 1을 더하라’는 빈칸은 외부 자료가 필요 없을 수 있다. 반면 ‘다른 파일에 있는 고객 조회 함수를 올바른 인자 순서로 호출하라’는 빈칸은 그 함수 정의를 읽어야 할 수 있다. 학습은 이런 차이를 알아보게 하는 준비 과정이다.

평가할 때에는 모델에 정답을 주지 않는다. 코드의 빈칸 앞뒤 부분을 주고 검색 여부와 완성 코드를 내게 한다. 여기서는 **RepoEval의 API 호출 완성 1,600문제**를 비교한 결과를 중심으로 설명한다. 이 논문은 한 줄 1,600문제·함수 455문제와 다른 평가 자료도 사용했다. 함수 455문제는 앞 절 RepoCoder의 373문제와 구분한다. [원문 4절·부록 D 표 6](https://raw.githubusercontent.com/mlresearch/v235/main/assets/wu24a/wu24a.pdf#page=18)

### 9.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

비교에는 학습이 끝난 동일한 Repoformer-1B 모델을 사용한다. `1B`는 모델 크기를 나타내는 이름이다. 실험자는 모델을 바꾸는 대신 검색을 허용하는 규칙을 바꾼다.

| 순서 | 항상 검색 | 필요 여부를 판단해 검색 |
|---|---|---|
| 1. 문제 제시 | 빈칸 앞뒤 코드를 준다. | 같은 빈칸 앞뒤 코드를 준다. |
| 2. 참고 자료 선택 | 무조건 다른 파일의 관련 코드를 검색한다. | 모델이 현재 코드를 보고 검색 필요성을 판단한다. |
| 3. 코드 작성 | 원래 코드와 검색 자료를 함께 읽고 빈칸을 채운다. | 검색을 선택하면 참고 코드를 추가하고, 생략하면 현재 파일만으로 빈칸을 채운다. |
| 4. 결과 저장 | 완성 코드를 저장한다. | 완성 코드와 검색 사용 여부를 저장한다. |

선택 규칙은 두 가지다. `G`는 모델의 기본 선택을 따른다. `T`는 모델이 내놓은 검색 필요성 점수에 기준값을 적용한다. 둘 다 **정답을 채점한 뒤 더 잘된 답을 고르는 규칙이 아니라, 평가 문제에서 검색 사용 여부를 결정하는 규칙**이다. [원문 3.2절·5.2~5.3절](https://raw.githubusercontent.com/mlresearch/v235/main/assets/wu24a/wu24a.pdf#page=4)

### 9.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

각 문제의 완성 코드를 보관해 둔 정답 코드와 비교한다. 아래 표의 ES는 글자를 얼마나 고치면 정답 코드가 되는지를 바탕으로 계산한 **0~100점의 문자열 유사도 점수**다. 점수가 높을수록 정답 코드와 비슷하지만, ES 72점이 100문제 중 72문제의 실행 성공을 뜻하지는 않는다.

또한 전체 문제 중 검색 결과를 사용한 비율과 응답 대기 시간을 함께 집계한다. API 완성 시험의 결과는 다음과 같다. [원문 표 3](https://raw.githubusercontent.com/mlresearch/v235/main/assets/wu24a/wu24a.pdf#page=7)

| 검색 규칙 | 평균 코드 유사도 ES | 검색 결과를 사용한 문제 비율 | 논문이 보고한 속도 향상 SU |
|---|---:|---:|---:|
| 항상 검색 | 72.02 | 100% | 기준, 0% |
| 선택적 검색 G | 71.04 | 18% | 69% |
| 선택적 검색 T | 72.72 | 61% | 28% |

T의 61%는 **시험 문제의 약 61%에서 검색한 코드를 사용하고, 나머지에서는 현재 파일의 코드로 답했다**는 뜻이다. 그렇게 해도 평균 ES는 항상 검색한 경우보다 0.70점 높았다. 반면 G는 검색 사용이 더 적고 속도 향상 값도 크지만 ES는 0.98점 낮았다.

시간 시험에는 별도의 실행 가정이 있다. 검색 색인은 미리 만들어 둔다. 그리고 검색 필요 판단, 검색 없이 작성, 검색해서 작성을 병렬로 시작할 수 있다고 놓는다. 판단이 ‘생략’이면 검색 없이 만든 답이 완료되는 시간을, ‘검색’이면 검색을 사용한 답이 완료되는 시간을 기준으로 지연을 평가한다. 논문은 이 모형과 NVIDIA A100 80GB 한 대의 vLLM 실행 환경으로 시간을 평가했다. 따라서 SU는 **사용자가 답을 기다리는 시간에 관한 지표**이며, 사용하지 않은 경로의 계산까지 포함한 전체 계산량 절감률로 읽으면 안 된다. [원문 5.3절](https://raw.githubusercontent.com/mlresearch/v235/main/assets/wu24a/wu24a.pdf#page=6)

### 9.5. 이 결과로 어디까지 말할 수 있는가?

이 실험은 ‘검색을 줄였다’는 사실만 확인한 것이 아니다. **검색을 줄인 조건에서 코드 품질이 얼마나 바뀌었는지** 동시에 비교했다. 같은 모델을 사용했기 때문에 위 표의 차이를 단순히 더 큰 모델을 사용한 효과로 설명할 수는 없다. 다만 글자 유사도의 작은 상승을 실제 프로그램 오류가 그만큼 줄었다는 뜻으로 해석해서도 안 된다.

Symbol Index에 적용하려면 외부 함수를 읽어야 하는 문제와 현재 자료만으로 풀리는 문제를 섞고, 항상 선택 도구를 호출하는 방식과 필요 여부를 판단하는 방식을 비교할 수 있다. 이때 검색을 생략한 비율뿐 아니라 **필요한 검색을 잘못 생략해 틀린 문제 수**도 기록해야 한다.

## 10. RAPTOR: 같은 길이의 참고 자료를 주되, 원문만 고른 경우와 요약도 고른 경우를 비교하는 실험

대상 논문: Parth Sarthi 외, **RAPTOR: Recursive Abstractive Processing for Tree-Organized Retrieval**, ICLR 2024. [학회 원문](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf)

### 10.1. 무엇을 확인하려는 실험인가?

긴 문서에서 질문과 비슷한 문단 하나를 찾았다고 해서 답에 필요한 내용이 모두 모이는 것은 아니다. 원인과 결과가 멀리 떨어진 문단에 적혀 있을 수 있기 때문이다. RAPTOR는 **원문 조각에 더해 여러 부분을 묶은 요약도 검색 대상으로 준비하면, 제한된 입력 안에 더 유용한 근거를 넣을 수 있는지** 시험한다.

**설명용 예시:** 긴 보고서 앞부분에는 ‘배수로 공사가 지연되었다’, 뒷부분에는 ‘폭우 때 물이 빠지지 않아 창고가 침수되었다’고 적혀 있다고 하자. 질문은 ‘창고 피해가 커진 이유는 무엇인가?’이다. 침수 문단만 찾으면 사건은 알 수 있지만 앞의 공사 지연과 연결하기 어려울 수 있다. 두 내용을 포함한 요약은 그 연결을 짧은 자료 안에 담을 수 있다. 이 예시는 요약을 넣는 목적을 설명하며, 실제로 항상 올바른 요약이 생성된다는 가정은 아니다.

### 10.2. 어떤 자료와 문제를 준비하는가?

실제 평가에는 긴 글과 질문·정답이 묶인 공개 문제집을 사용한다. QuALITY는 긴 글을 읽고 객관식 답을 고르는 시험이고, QASPER는 학술 논문의 내용을 묻는 시험이다. 이야기·대본을 대상으로 하는 NarrativeQA도 평가했다. 아래 결과표는 QuALITY와 QASPER에서 동일한 답변 모델을 사용한 비교다. [원문 4절](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=6)

실험자는 **같은 원문으로 두 종류의 검색 자료**를 준비한다. 첫 번째에는 원문을 나눈 조각만 넣는다. 두 번째에는 그 원문 조각들과, 의미가 비슷한 조각들을 묶어 만든 요약을 넣는다. 요약을 다시 묶어 요약하므로 좁은 내용부터 넓은 주제까지 여러 단계의 요약이 생긴다. 질문의 정답을 요약에 미리 써 넣는 것이 아니라, 문서 내용으로 검색 자료를 구성하는 준비 작업이다. [원문 3절](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=3)

### 10.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

| 순서 | 원문 조각만 검색 | RAPTOR의 원문·요약 검색 |
|---|---|---|
| 1. 같은 질문 제시 | 준비한 원문 조각 중 질문과 관련 있는 내용을 찾는다. | 원문 조각과 모든 단계의 요약 중 질문과 관련 있는 내용을 찾는다. |
| 2. 읽힐 분량 제한 | 관련성이 높은 원문 조각들을 정해진 토큰 예산 안에서 고른다. | 관련성이 높은 원문·요약 항목들을 같은 토큰 예산 안에서 고른다. |
| 3. 답변 모델에 전달 | 질문과 선택된 원문을 전달한다. | 같은 질문과 선택된 원문·요약을 전달한다. |
| 4. 답안 제출 | 객관식 선택 또는 질문에 대한 답변을 제출한다. | 같은 형식의 답안을 제출한다. |

‘모든 단계에서 검색한다’는 말은 **요약 전체를 AI에게 한꺼번에 읽힌다**는 뜻이 아니다. 검색 후보에는 모든 단계가 포함되지만, 답변 모델에는 예산 안에서 선택된 내용만 들어간다. 아래 비교에서는 근거 자료를 최대 400토큰까지 주었다. SBERT라는 검색용 모델과 UnifiedQA-3B라는 답변용 모델도 두 조건에서 같게 유지했다. [원문 검색 절차·표 2](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=8)

앞의 창고 예시로 말하면, 실험자가 비교하려는 것은 ‘짧은 자료와 긴 자료 중 어느 쪽이 유리한가’가 아니다. **같은 짧은 분량 안에 개별 사건 문단을 넣었을 때와, 사건들의 관계를 묶은 자료까지 넣었을 때의 차이**다.

### 10.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

QuALITY에서는 고른 보기가 정답 보기와 같으면 성공으로 세어 정답률을 구한다. QASPER에서는 기준 답변과 생성 답변을 대조하는 F1 점수를 집계한다. F1은 답변에 정답 요소가 얼마나 정확하고 빠짐없이 들어 있는지 평가하는 점수로, 아래 표에서는 0~100점으로 표시한다. 모든 문제가 완전히 맞았는지를 세는 정답률과 구분한다.

| 검색 자료 구성 | QuALITY 정답률 | QASPER 답변 F1 |
|---|---:|---:|
| 원문 조각만 준비 | 54.9% | 36.23 |
| 원문과 RAPTOR 요약을 함께 준비 | 56.6% | 36.70 |

같은 모델과 근거 자료 예산에서 객관식 정답률은 1.7%포인트, F1은 0.47점 높아졌다. 이 표에서는 답변 모델을 더 강한 것으로 교체한 효과와 자료 구성의 효과를 섞지 않고 볼 수 있다. [원문 표 2](https://proceedings.iclr.cc/paper_files/paper/2024/file/8a2acd174940dbca361a6398a4f9df91-Paper-Conference.pdf#page=8)

### 10.5. 이 결과로 어디까지 말할 수 있는가?

이 비교는 **AI에게 줄 자료의 양을 제한한 상태에서도 자료의 구성에 따라 답변 품질이 달라질 수 있다**는 근거다. 위 점수 상승만으로 모든 질문에서 요약이 유리하다고 말할 수는 없다. 요약을 사전에 만드는 시간과 비용도 따로 발생한다.

Source Pointer의 문서 시험에 연결하면, 한 절의 숫자를 찾는 문제와 떨어진 여러 절을 종합하는 문제를 구분할 필요가 있다. 같은 입력 예산에서 한 절만 추출할지, 관련 원문 여러 절을 추출할지, 요약도 포함할지 비교할 수 있다. 정확한 설정값을 묻는 문제는 원문 값과 직접 대조해야 한다. 문서 전체 관계를 잘 요약했더라도 특정 숫자를 잘못 옮겼다면 그 질문에는 오답이기 때문이다.

## 11. MemGPT: 과거 대화를 요약만 읽고 답하는 경우와 원문을 다시 찾아 답하는 경우를 비교하는 실험

대상 논문: Charles Packer 외, **MemGPT: Towards LLMs as Operating Systems**, arXiv 2023. 분석 대상은 2024-02-12 수정본 v2다. [논문 정보·버전 이력](https://arxiv.org/abs/2310.08560)

### 11.1. 무엇을 확인하려는 실험인가?

대화가 길어지면 과거 내용을 모두 현재 입력에 넣기 어렵다. 요약으로 줄이면 중요한 세부 사항이 빠질 수 있다. MemGPT는 **원래 기록을 입력 밖에 보관하고 필요할 때 다시 찾아 읽게 하면, 요약만 읽는 경우보다 과거 사실을 잘 답할 수 있는지** 시험한다.

여기서 ‘기억’은 모델이 학습으로 모든 대화를 암기한다는 뜻이 아니다. 현재 읽는 입력과 외부 보관 자료를 구분하고, 도구로 자료를 다시 가져오는 구조다. 논문 제목의 운영체제도 이러한 정보 관리 방식에 관한 비유다. [저자 연구 소개](https://research.memgpt.ai/)

### 11.2. 어떤 자료와 문제를 준비하는가?

대표 시험인 DMR에서는 사람이 만든 **다섯 차례의 대화 기록**을 사용한다. 별도의 AI가 과거 대화의 구체적인 사실을 물어보는 질문과 정답을 만들고, 이를 다음 대화의 질문으로 사용한다. 연구자는 정답을 채점용으로 보관한다. [원문 3.1.1절·부록 6.1.3절](https://arxiv.org/pdf/2310.08560v2#page=5)

**설명용 예시:** 두 번째 대화에 ‘제주 여행에서 파란색 지도책을 샀다’는 말이 있었고, 이후에는 다른 이야기를 나누었다고 하자. 새 질문은 ‘제주 여행에서 무슨 책을 샀지?’이며 정답은 ‘지도책’이다. 요약이 ‘제주 여행을 했다’ 정도로 줄었다고 가정하면, 요약만 읽는 AI에게는 책의 종류가 보이지 않는다.

실험자는 같은 과거 대화를 두 가지 방법으로 준비한다. 한 조건에는 대화 요약을 주고, 다른 조건에는 대화 원문을 외부에 보관하여 검색할 수 있게 한다. **시험하려는 차이 자체가 과거 정보를 다시 확인할 수 있는가**이므로, 두 조건에 처음부터 같은 원문 전체를 입력하는 시험이 아니다.

### 11.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

| 순서 | 대화 요약만 사용하는 GPT-4 | MemGPT를 사용하는 GPT-4 |
|---|---|---|
| 1. 새 질문 제시 | 질문과 과거 대화 요약을 읽는다. | 질문을 읽고, 필요하면 보관 기록을 검색할 수 있다. |
| 2. 근거 확인 | 제공된 요약을 바탕으로 답을 만든다. 원문을 다시 찾는 경로는 없다. | AI가 검색어를 정하면 프로그램이 보관 대화에서 관련 기록을 찾아 현재 입력에 넣는다. |
| 3. 추가 확인 | 원문 재검색 단계 없음 | 필요한 사실을 못 찾았으면 추가 검색이나 다음 결과 확인을 할 수 있다. |
| 4. 최종 제출 | 과거 사실에 대한 답을 제출한다. | 찾아 읽은 내용을 바탕으로 답을 제출한다. |

예시에서 검색이 잘되었다면 현재 입력에 ‘파란색 지도책을 샀다’는 과거 문장이 들어온다. 그제야 답변 모델은 ‘지도책’이라고 답할 근거를 갖는다. 이 문장이 정말 검색되고 최종 답도 맞는지는 평가 결과로 확인해야 하며, 외부에 보관했다는 사실만으로 성공한 것으로 세지는 않는다. 실제 비교에서도 기준 방식은 요약을, MemGPT는 검색 가능한 전체 대화 기록을 사용했다. [원문 3.1.1절](https://arxiv.org/pdf/2310.08560v2#page=5)

### 11.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

답변 후 별도의 GPT-4 채점자에게 **질문, 미리 만든 정답, 제출한 답변**을 준다. 채점자가 맞다고 판단한 문제의 비율을 정확도로 집계한다. 긴 답변에도 정답 사실이 포함될 수 있으므로 단순한 문자열 완전 일치만 사용하지 않았다. 기준 답변의 표현이 생성 답변에 순서를 유지하며 얼마나 포함되는지 보는 ROUGE-L 재현율도 함께 보고했다. 이 보조 점수는 0~1로 표시하며 클수록 기준 답변의 표현을 더 많이 포함한다. [원문 3.1.1절·부록 6.1.2절](https://arxiv.org/pdf/2310.08560v2#page=10)

| 비교 조건 | 채점 AI가 맞다고 판정한 비율 | ROUGE-L 재현율 |
|---|---:|---:|
| GPT-4와 과거 대화 요약 | 32.1% | 0.296 |
| GPT-4와 MemGPT | 92.5% | 0.814 |

이 결과는 **요약만 이용한 답변보다 원래 기록에 재접근한 답변이 해당 채점에서 더 많이 통과했다**는 뜻이다. 92.5%는 외부 저장 성공률이나 검색 도구 실행 성공률이 아니라 최종 답변에 대한 판정 비율이다. [원문 표 2](https://arxiv.org/pdf/2310.08560v2#page=5)

### 11.5. 이 결과로 어디까지 말할 수 있는가?

대화 원문에 다시 접근하는 기능과 그 정보를 관리하는 절차가 함께 달라졌다. 따라서 성적 차이를 식별자 하나의 효과로 분리할 수는 없다. 또 채점 AI가 표현을 유연하게 인정하므로, 실제 코드의 상수 값을 대소문자까지 정확하게 비교한 로컬 실험과 동일한 정답 기준도 아니다.

Source Pointer·Runtime Pointer에 연결할 때에는 자료를 보관하고 다시 가져오는 전체 과정을 시험해야 한다. 예를 들어 첫 로그에서 요청 번호를 얻고, 그 번호로 다음 기록을 찾아 최종 원인을 답하게 할 수 있다. 이때 ‘기록을 찾았는가’와 ‘그 기록으로 정답을 만들었는가’를 나누어 측정하면 실패 위치를 구분할 수 있다.

### 11.6. 같은 논문의 문서 질문·연쇄 조회 시험은 어떻게 진행되는가?

위 대화 기억 성적과 다음 두 시험은 별개다. 자료와 문제를 만드는 방법도 다르다.

**문서 질문 시험:** NaturalQuestions-Open에서 50문제를 뽑고 Wikipedia 문서들을 준비한다. 기준 방식은 같은 검색기로 얻은 상위 문서들을 처음 입력에 넣고 답하게 한다. 실험자는 처음 주는 문서 수를 바꾸어 성적을 본다. MemGPT는 문서들을 외부 저장소에 두고 검색을 여러 번 하거나 검색 결과의 다음 묶음을 확인하여 답한다. 최종 답이 맞고 검색한 문서에 근거하는지를 AI 채점자로 평가한다. 이는 ‘처음 받은 문서 안에서만 답하기’와 ‘필요한 문서를 계속 찾아보기’를 비교하는 시험이다. [원문 3.2.1절·그림 5~6](https://arxiv.org/pdf/2310.08560v2#page=6)

**연쇄 조회 시험:** 식별자와 값 140쌍을 준비한다. 어떤 항목의 값이 다른 항목의 식별자이면 그 항목을 다시 조회해야 한다. 예를 들어 `A의 값=B`, `B의 값=C`, `C의 값=최종값`이라면 A의 값 B에서 멈추지 않고 최종값까지 찾아 제출해야 한다. 연구자는 전체 자료 수를 유지하면서 연결 깊이와 항목 배치를 바꾸고, 30가지 배치를 사용했다. 일반 모델의 답변과 반복 조회를 수행하는 MemGPT의 답변을 미리 정한 최종값과 대조한다. 이는 더 긴 문서를 읽는 능력뿐 아니라 **여러 번의 조회를 끝까지 이어 가는 능력**을 확인하는 시험이다. [원문 3.2.2절·그림 7](https://arxiv.org/pdf/2310.08560v2#page=8)

## 12. ReWOO: 도구 결과가 나올 때마다 계획하는 방식과, 전체 계획을 먼저 만드는 방식을 비교하는 실험

대상 논문: Binfeng Xu 외, **ReWOO: Decoupling Reasoning from Observations for Efficient Augmented Language Models**, arXiv 2023. [논문 정보](https://arxiv.org/abs/2305.18323)

### 12.1. 무엇을 확인하려는 실험인가?

AI가 검색 도구를 여러 번 사용하는 상황을 생각하면, 보통 첫 결과를 읽고 다음 행동을 정한다. 그다음 결과가 나오면 앞의 질문·지시문·도구 결과를 다시 입력해 다음 행동을 정한다. 단계가 늘수록 같은 내용이 반복 입력된다.

ReWOO는 **할 일을 먼저 계획하고, 실행 프로그램이 그 계획대로 결과를 연결한 뒤 마지막에 답을 만들면 반복 입력을 줄일 수 있는지** 시험한다. 도구를 사용하지 않는 방식과 비교하는 것이 아니라, 도구를 사용하는 두 절차를 비교하는 것이다. [원문 2절·그림 2](https://arxiv.org/pdf/2305.18323#page=3)

### 12.2. 어떤 자료와 문제를 준비하는가?

대표 비교는 여러 사실을 연결해야 답할 수 있는 HotpotQA 1,000문제다. 실험자는 두 방식에 같은 GPT-3.5-Turbo, 같은 종류의 도구인 Wikipedia 검색과 LLM 도구, 같은 예제 질문 6개를 제공한다. LLM 도구는 짧은 정보 추출 등을 별도로 AI에게 맡기는 기능이다. 예제 6개는 수행 형식을 보여 주는 자료이며 평가할 1,000문제와 구분한다. 정답은 채점용으로 따로 보관한다. [원문 3.1절·표 1~2](https://arxiv.org/pdf/2305.18323#page=6)

**설명용 예시:** 가상의 작가 ‘해솔’의 아버지가 태어난 도시를 묻는다고 하자. 첫 검색 결과에서 아버지의 이름 ‘민수’를 알아내고, 그 사람을 다시 검색해 출생 도시 ‘태안’을 찾아야 한다. 이 인물·검색 결과는 절차 설명을 위해 만든 것이며 논문의 실제 문항이 아니다.

### 12.3. 같은 문제를 각 방식에 어떻게 풀게 하는가?

비교 대상 ReAct는 결과를 받은 다음 행동을 정한다. 위 예시라면 다음과 같이 진행될 수 있다.

1. AI에게 질문과 도구 사용법을 준다. AI가 ‘해솔을 검색하라’고 지시한다.
2. 프로그램이 검색 결과를 가져온다. AI에게 질문·이전 진행 내용·검색 결과를 다시 입력한다. AI가 아버지 이름을 읽고 ‘민수를 검색하라’고 지시한다.
3. 두 번째 검색 결과도 입력에 추가한다. AI가 지금까지의 내용을 읽고 출생 도시를 답한다.

ReWOO에서는 처음 계획을 만들 때 아직 아버지 이름과 출생 도시를 몰라도, **앞 단계 결과가 들어갈 자리에 표식을 넣어** 뒤 작업을 적을 수 있다. 설명용 계획은 다음과 같다.

| 미리 적는 계획 | 실행 프로그램이 나중에 채우는 내용 |
|---|---|
| `#E1`: Wikipedia에서 해솔 검색 | 해솔의 인물 설명이 저장된다. |
| `#E2`: LLM 도구로 `#E1`에서 아버지 이름 추출 | 실제 첫 결과를 도구에 주어 ‘민수’를 얻는다. |
| `#E3`: Wikipedia에서 `#E2` 검색 | `#E2`를 ‘민수’로 바꾸어 검색하고 출생 정보가 있는 결과를 얻는다. |

그 뒤 답변 담당 AI에게 질문, 계획, 실제로 얻은 근거를 주어 ‘태안’이라는 최종 답을 만들게 한다. **`#E2` 자체가 사람 이름을 알고 있는 것은 아니다.** 실행 프로그램이 앞서 저장한 결과를 꺼내 다음 도구의 입력에 대입하는 것이다. 이 대입과 최종 근거 전달은 저자 공개 코드에서도 확인된다. [계획·도구 실행·답변 연결 코드](https://raw.githubusercontent.com/billxbf/ReWOO/main/algos/PWS.py)

두 방식에 허용된 도구는 같아도, 모델이 작성한 계획에 따라 실제 호출 순서와 횟수는 달라질 수 있다. 위 예시에서도 ReWOO는 이름을 추출하는 LLM 도구를 사용했다. 따라서 ‘계획 작성과 최종 답변의 두 단계’라고 해서 **전체 AI 호출이 항상 두 번**인 것은 아니다.

### 12.4. 답을 어떻게 채점하고, 어떤 결과가 나왔는가?

각 문제에서 최종 답을 저장하고 정답과 대조한다. 동시에 계획·답변·LLM 도구 호출에서 사용한 토큰을 합산한다. 이를 1,000문제에 반복해 답변 점수와 문제당 평균 토큰을 집계한다. 토큰은 AI가 읽고 쓰는 글의 처리량을 세는 단위이며, 여기서는 입력뿐 아니라 출력과 LLM 도구 사용분도 포함한다.

| 측정 항목 | ReAct | ReWOO | 무엇을 센 것인가? |
|---|---:|---:|---|
| AI 채점 정확도 | 40.8% | 42.4% | 별도의 GPT-4가 정답과 의미가 맞는다고 판정한 비율 |
| 정확 일치율 EM | 32.2% | 30.4% | 정해진 비교 규칙으로 정답 문자열과 일치한 비율 |
| 문자 기준 F1 | 39.6 | 40.1 | 정답과 답변의 문자 겹침을 이용한 점수 |
| 저자 보고 평균 총토큰 | 9,795.1 | 1,986.2 | 한 문제를 끝내는 동안의 전체 토큰 사용량을 문제들에 걸쳐 평균한 값 |

표는 논문의 HotpotQA 결과다. 예를 들어 AI 채점 정확도 40.8%와 42.4%는 1,000문제 중 각각 408개와 424개가 해당 채점에서 맞았다는 의미다. 반면 F1 40.1은 401개를 맞혔다는 뜻이 아니다. [원문 평가 지표·표 2](https://arxiv.org/pdf/2305.18323#page=7)

토큰 감소율은 `(1 − 1,986.2 ÷ 9,795.1) × 100 ≈ 79.7%`다. 그러나 정답 문자열을 엄격하게 비교한 EM은 1.8%포인트 낮아졌다. 이 때문에 **처리량은 크게 줄었지만, 모든 채점 기준에서 더 정확해진 결과는 아니다**라고 읽어야 한다.

측정 방식에도 구분이 필요하다. 현재 공개 코드에서는 계획·최종 답변의 입력·출력 토큰에 LLM 도구 사용분을 더하는데, 도구 사용분 일부는 문자 수를 4로 나눈 추정값이다. 위 표는 저자 보고값으로 인용하며, 직접 재현할 때는 실측과 추정을 나누어 기록해야 한다. [공개 코드의 토큰 집계](https://raw.githubusercontent.com/billxbf/ReWOO/main/algos/PWS.py)

### 12.5. 이 결과로 어디까지 말할 수 있는가?

이 실험이 확인하는 것은 **같은 종류의 문제와 도구를 쓰더라도, 계획과 결과를 전달하는 절차를 바꾸면 전체 토큰 부담이 달라진다**는 것이다. 실제 답변 점수까지 함께 재므로, 단순히 작업을 덜 해서 토큰이 줄어든 경우와 구분해 판단할 수 있다.

Runtime Pointer와의 공통점은 실행 결과를 이름으로 연결하는 데 있다. 다만 ReWOO도 마지막 답변 단계에는 실제 근거를 읽힌다. 따라서 표식이 있다는 이유만으로 큰 결과물이 끝까지 입력 밖에 남거나 문맥 한도 초과가 모두 방지된다고 볼 수는 없다. 현재 방식의 효과를 시험하려면 결과의 크기와 도구 연결 단계를 늘리면서 **전체 누적 토큰과 한 번의 호출에 들어간 최대 토큰**을 함께 기록해야 한다. 누적량은 반복 부담을, 최대 단일 입력은 한도 초과 가능성을 보여 준다.

## 13. 이 실험들을 현재 세 포인터 실험과 연결해서 읽는 방법

다섯 논문은 모두 자료를 다루는 방법을 바꾸지만, 성공이라고 판단하는 작업은 다르다. 코드를 작성해 실행한 성적, 문서의 객관식 답을 맞힌 성적, AI 채점자가 대화 답변을 맞다고 판단한 성적을 서로 같은 숫자처럼 비교해서는 안 된다.

현재 실험을 보완할 때 참고할 수 있는 부분은 다음과 같다. 아래는 **후속 실험 설계 제안**이며 아직 실행한 결과가 아니다.

| 현재 방식 | 비교할 실행 절차 | 한 문제를 끝낸 뒤 기록할 것 |
|---|---|---|
| Symbol Index | 같은 질문에 대해 함수 하나로 답하기 / 관련 코드를 더 찾아 답하기 | 선택한 위치, 최종 정답 여부, 추가 호출 수와 누적 입력량 |
| Symbol Index | 외부 코드가 필요한 문제와 불필요한 문제를 섞고, 항상 검색 / 필요 여부를 판단해 검색 | 검색 사용 여부, 잘못 생략한 문제 수, 정답 여부와 응답 시간 |
| Source Pointer | 여러 절에 걸친 같은 질문에 대해 한 절 / 여러 원문 절 / 요약 포함 자료를 같은 입력 예산으로 제공 | 필요한 근거가 들어왔는지, 최종 답이 맞는지, 숫자·조건이 원문과 같은지 |
| Source Pointer·Runtime Pointer | 같은 전체 자료에서 한 번 조회하는 문제와 여러 자료를 이어 조회하는 문제를 구성 | 각 단계의 조회 성공 여부, 최종값의 정확성, 단계 수에 따른 비용 |
| Runtime Pointer | 같은 도구 결과를 매 단계 본문으로 누적 / 식별자로 연결하고 필요한 부분을 전달 | 최종 정답, 전체 누적 토큰, 최대 단일 입력, 한도 초과 여부와 전체 시간 |

평가 기록은 ‘방식 A가 빠르다’에서 끝내지 않고, **어떤 문제에서 어떤 자료를 받아 어떤 답을 냈으며, 그 답을 어떤 규칙으로 맞다고 판단했는지**까지 남기는 것이 중요하다. 색인이나 요약을 미리 만든 시간은 질문 처리 시간과 구분하고, 질문 처리 비용에는 검색·추출·도구 실행·모든 AI 호출을 포함한다. 이렇게 기록해야 자료를 잘 찾아서 성공한 것인지, 쉬운 문제만 검색을 생략해서 빨라진 것인지, 채점 기준이 느슨해서 높은 점수가 나온 것인지 확인할 수 있다.
