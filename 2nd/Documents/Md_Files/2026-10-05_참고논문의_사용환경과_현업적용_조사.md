## 3. 논문의 사용 환경: Solving Context Window Overflow in AI Agents

### 3.1 어떤 문제를 어떻게 해결했는가

AI가 도구를 실행했는데 결과가 너무 크면, 그 결과를 AI의 입력에 모두 넣는 과정에서 한도를 넘을 수 있다. 이 논문은 **큰 결과를 AI 입력 바깥에 보관하고, AI에는 그 결과를 가리키는 짧은 번호표를 주는 방법**을 제안한다. 다음 도구를 실행할 때는 중간 프로그램이 번호표를 실제 자료로 바꾸어 전달한다. [P1](</Users/oscar/Desktop/SecureCode/1st/Documents/Paper/1_Solving Context Window Overflow in AI Agents.pdf>) (2절·2~3쪽)

예를 들어 분자 계산 결과에 숫자가 200만 개 들어 있다면, AI가 그 숫자를 모두 읽고 다시 출력할 필요 없이 ‘분자 계산 결과 A’를 다음 도구에 넘기게 한다. 큰 자료 자체는 보존되며, 실제 계산 도구가 그 자료를 사용한다. **자료가 손실 없이 전달된다는 것과 AI가 자료 전체를 직접 읽고 이해했다는 것은 구별해야 한다.**

### 3.3 실제로 무엇을 시험했는가

**실험 A: 비슷한 분자 찾기**

분자를 문자열로 표현한 SMILES를 입력받아, 첫 도구가 분자의 전자적 특성을 나타내는 3차원 격자 자료를 만든다. 두 번째 도구는 그 격자를 받아 유사한 분자들을 찾는다. 격자는 `128 × 128 × 128`이며, `float32` 숫자 **2,097,152개**로 구성된다. 같은 사용자·시스템 입력으로 50회 반복했다. 큰 결과를 그대로 전달하는 기존 방식은 중간에 실패했지만, 포인터 방식은 작업을 완료했다. [P1](</Users/oscar/Desktop/SecureCode/1st/Documents/Paper/1_Solving Context Window Overflow in AI Agents.pdf>) (3.1절·3~4쪽)

논문이 제시한 포인터 방식의 평균은 33.87초와 1,234.04토큰이다. 반면 기존 방식의 약 2,082만 토큰은 실패 전까지의 입력량을 **사후에 추정한 값**이다. 기존 방식이 그 토큰을 실제로 모두 처리한 측정 결과로 설명하면 안 된다. 또한 50회는 50종류의 서로 다른 분자 문제를 평가했다는 의미가 아니다. [P1](</Users/oscar/Desktop/SecureCode/1st/Documents/Paper/1_Solving Context Window Overflow in AI Agents.pdf>) (4쪽)

**실험 B: 안전자료에서 성분 찾기**

화학제품 안전자료인 SDS PDF에서 텍스트를 추출하고, 그 텍스트를 다음 도구에 넘겨 성분을 찾았다. 두 방식 모두 처리 가능한 크기의 자료를 사용했으며, 각 방식에 대해 50회 수행했다. 논문 보고 평균은 기존 방식 6,411.36토큰·43.05초, 포인터 방식 841.66토큰·11.05초다. [P1](</Users/oscar/Desktop/SecureCode/1st/Documents/Paper/1_Solving Context Window Overflow in AI Agents.pdf>) (3.2절·4쪽)

이 숫자는 논문이 보고한 조건의 결과다. 장비·접속 조건이 충분히 공개되지 않았으므로, 다른 컴퓨터에서도 같은 실행 시간이 나온다고 볼 수는 없다.

| 항목 | 조사 결과 |

### 3.5 환경 정보를 보완하는 외부 적용 사례

#### 사례 A: Flow AI의 상품 데이터 처리

Flow AI는 2026-02-04 게시한 자체 기술 글에서, 수천 개 상품이 있는 데이터베이스를 대상으로 가격 변경을 계획·실행하는 에이전트를 설명했다. 상품 ID 목록 전체를 AI에 넘기는 대신, 상품 묶음을 저장하고 `productSetId`를 넘긴다. AI에는 개수·일부 예시·통계도 함께 제공하며, 후속 실행 도구가 ID를 실제 상품 목록으로 바꿔 사용한다. 회사는 IBM 논문과 독립적으로 같은 원리에 도달했다고 설명한다. [S1](https://flow-ai.com/blog/solving-long-context-for-data-agents)

이는 **기업이 공개한 자체 적용·제품화 사례**다. 글에는 고객과 제품화 중이라는 설명이 있으므로, 특정 고객사의 대규모 상용 운영이 검증되었다고 확대해서 적지는 않는다. AI 모델, GPU, 운영체제, 데이터베이스 제품명은 해당 글만으로 알 수 없다. IBM 논문의 정확한 구현을 그대로 도입한 사례도 아니다. [S1](https://flow-ai.com/blog/solving-long-context-for-data-agents)

#### 사례 B: AWS의 공개 개발 예제

`aws-samples/sample-why-agents-fail` 저장소에는 이 IBM 논문을 참고한 큰 로그 처리 예제가 있다. **Python 3.9 이상, Strands Agents, 기본 모델 GPT-4o-mini의 API 연결**을 안내한다. 큰 로그를 `agent.state`에 저장하고 포인터를 넘기는 방식과, 별도 처리기가 큰 결과를 메모리 또는 로컬 파일로 옮기는 방식을 제시한다. [S2](https://github.com/aws-samples/sample-why-agents-fail/tree/main/stop-ai-agents-wasting-tokens/01-context-overflow-demo)

여기서 확인되는 환경은 ‘로컬 프로그램이 AI API와 연결되고, 자료는 프로그램 쪽 메모리나 파일에 보관되는 구성’이다. **개발·교육용 예제이므로 특정 회사의 실제 운영 실적과는 구별한다.** 정확한 CPU·GPU·운영체제는 이 예제에서도 특정하지 않는다. [S2](https://github.com/aws-samples/sample-why-agents-fail/tree/main/stop-ai-agents-wasting-tokens/01-context-overflow-demo)

## 4. 자신의 세 가지 방식과 연결해서 설명하기

아래 연결은 논문에 세 가지 방식이 모두 그대로 제안되어 있다는 뜻이 아니다. 보관된 연구 설명과 논문의 작동 원리를 대조한 **해석**이다. 자체 방식의 의미는 기존 발표 대본도 참고했다. [L1](</Users/oscar/Desktop/SecureCode/1st/midterm_presentation/presentation_script_ko.md>)

| 자신의 방식 | 쉬운 설명 | 논문과의 관계 |
| --- | --- | --- |
| `runtime_pointer` | 실행 도중 생성된 큰 결과에 번호표를 붙여 재사용 | 논문의 ‘도구 결과를 임시 저장하고 포인터로 전달’하는 방법과 가장 직접적으로 연결됨 |
| `source_pointer` | 이미 존재하는 파일에 번호표를 붙여 필요한 내용을 읽음 | 논문의 참조 방식과 공통 원리가 있지만, 저장 대상이 실행 결과가 아니라 기존 파일이라는 차이가 있음 |
| `symbol_index` | 함수·클래스 등 코드 조각의 주소록을 만들고 필요한 부분을 선택 | 작은 목록을 통해 큰 원문에 접근한다는 공통점이 있음. 논문이 이 코드 주소록 방식을 직접 제안하거나 평가한 것은 아님 |

환경 관점에서 논문의 포인터 방식을 적용하려면, **자료를 보관할 공간과 번호표를 실제 자료로 바꿔 줄 도구**가 필요하다. AI 서비스를 API로 호출하는 구성에서는 포인터 처리를 호출 프로그램 쪽에 둘 수 있다. 이는 논문의 구조와 외부 적용 사례에서 도출한 해석이다. ### 교수님께 구두로 설명할 수 있는 문장

> 이 논문은 재료과학 도구가 만들어 낸 큰 자료를 AI에 모두 읽히는 대신, 자료는 보관하고 번호표만 전달하도록 했습니다. Llama 4와 BeeAI로 분자 검색과 문서 성분 추출을 시험했지만, 컴퓨터 사양과 운영체제는 공개 자료로 확인되지 않았습니다. 이 원리는 제가 만든 runtime pointer와 가장 직접적으로 연결됩니다.
