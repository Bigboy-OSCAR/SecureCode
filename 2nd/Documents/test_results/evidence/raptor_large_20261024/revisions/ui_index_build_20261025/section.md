## 2. UI에서 ‘현재 프로젝트 색인 생성’을 누르면 누가 무엇을 만드는가?

**사용자는 생성 시점과 대상 프로젝트를 정하고, UI는 요청을 전달하며, 백엔드의 색인 생성 작업이 파일 읽기·파싱·자료 구성·저장을 수행한다.** RF·RH를 사용할 때는 이 작업이 LLM 서버에 요약을 요청한다. C는 RH의 자료를 공유한다.

여기서 **백엔드**는 화면 뒤에서 실제 파일 처리를 실행하는 프로그램이다. 데스크톱 앱이라면 사용자 컴퓨터의 로컬 프로세스로 둘 수 있다. 현재 확인한 구현은 Python으로 실행하는 **실험용 구축 코드**다. 아래에서 파싱·참조 연결·요약 생성 알고리즘은 실제 코드에 근거하며, **UI 요청 연결·백그라운드 작업·진행 표시·완료된 버전으로 교체하는 절차는 제품에 연결할 설계**다. 이 절을 추가하면서 UI 기능을 구현하거나 새 실험을 실행한 것은 아니다.

### 2.1 만드는 주체와 역할

| 주체 | 맡는 일 | 직접 만들어 내는 것 |
|---|---|---|
| 사용자 | 현재 프로젝트에서 생성 버튼을 누름. 사용할 방식은 사용자 선택 또는 앱 설정을 따름 | 생성 요청 |
| UI | 프로젝트 식별 정보와 방식을 백엔드에 전달하고 진행·완료·오류를 표시 | 요청과 상태 화면 |
| 백엔드의 색인 생성 작업 | 파일 목록을 정하고 읽기, 파싱, 검색 자료 구성, 필요한 LLM 호출, 저장 순서를 관리 | 프로젝트별 색인 버전과 저장 자료 |
| 파서와 분석·검색 코드 | `ast.parse`로 문법 구조를 읽고 이름·위치·참조를 추출. 원문 묶음과 TF-IDF 가중치를 계산 | 주소록, 참조 관계, 원문 후보, 검색용 수치 |
| LLM 서버 | 백엔드가 보낸 원문 묶음 또는 하위 요약을 읽고 설명 문장을 생성 | RF의 함수 요약, RH의 파일·프로젝트 요약 본문 |

파서와 분석 코드는 백엔드가 호출하는 프로그램 구성요소다. **LLM이 쓰는 것은 요약 본문이며, 파일 경로·함수 주소·줄 번호·요약의 부모/자식 연결은 프로그램이 붙인다.** 이번 실험에서는 Python 클라이언트가 로컬 Qwen 모델 서버에 요청하고 응답 텍스트를 받아 저장했다. 색인을 만드는 단계에서 대상 프로젝트의 함수를 실행해 계산 결과를 구하는 것은 아니다.

### 2.2 버튼 클릭부터 ‘사용 가능’까지의 처리 순서

다음은 현재 구축 로직을 하나의 버튼 작업으로 연결하는 흐름이다. **기본 입력은 디스크에 저장된 현재 프로젝트 파일**로 잡는다. 편집기의 미저장 내용까지 포함하려면 그 내용을 백엔드에 전달하는 연동을 별도로 넣어야 한다.

| 순서 | 실행 주체 | 처리하는 내용과 다음 단계로 넘기는 결과 |
|---|---|---|
| 1. 요청 접수 | UI → 백엔드 | 프로젝트 경로·방식·요약 모델 설정을 전달한다. 백엔드는 작업 ID를 만들고 UI에는 작업 시작 상태를 돌려준다. |
| 2. 대상 파일 확정 | 백엔드 | 프로젝트 파일을 수집하고, 이번 생성에 사용할 파일 내용과 버전을 고정한다. 현재 파서는 Python 파일을 대상으로 한다. 제외 폴더와 지원 언어는 앱의 수집 규칙으로 정한다. |
| 3. 코드 구조 읽기 | 파서 + 분석 코드 | 파일을 AST로 읽는다. A에는 함수·클래스 등의 이름·경로·줄·URI를, B 이후의 참조 자료에는 함수·상수 원문·import·참조 이름을 만든다. |
| 4. 연결과 원문 후보 구성 | 분석 코드 | `from … import …` 등으로 프로젝트 안의 참조 대상을 연결한다. R0·RF·RH·C에는 함수와 관련 코드를 묶은 후보와 단일 원문 후보를 만든다. |
| 5. 필요한 요약 생성 | 백엔드 → LLM 서버 → 백엔드 | RF·RH·C일 때 함수별 원문 묶음을 요약한다. RH·C는 그 요약들을 파일별로 재요약하고, 파일 요약들을 프로젝트 요약으로 만든다. A·B·R0에는 이 단계가 없다. |
| 6. 저장과 검색 준비 | 백엔드 + 검색 코드 | 원문·주소·참조·요약을 저장하고 연결 정보를 점검한다. R0·RF·RH·C는 후보를 비교할 단어 가중치와 벡터를 준비한다. 디스크 저장과 메모리 준비의 현재 구현 차이는 2.4절에 설명한다. |
| 7. 완료 버전 반영 | 백엔드 → UI | 검증된 결과를 현재 프로젝트의 사용 가능한 색인으로 지정한다. UI는 처리한 파일·함수·요약 수, 완료 시각과 실패 항목을 보여 준다. |

UI는 장시간 작업의 결과를 기다리며 화면을 멈추게 하기보다, 백엔드 작업의 상태를 받아 표시하도록 연결한다. 파일 파싱·함수 요약·파일 요약처럼 **현재 단계와 처리 개수**를 보여 주면 무엇을 하고 있는지 알 수 있다. 실험의 요약 시간은 5.5절에 있지만, 그것을 사용자의 현재 프로젝트에 대한 예상 완료 시간으로 그대로 사용할 수는 없다.

### 2.3 선택한 방식에 따라 어디까지 만들어야 하나?

| 방식 | 버튼 작업에서 준비할 자료 | 준비 단계의 요약 LLM 호출 |
|---|---|---|
| **A — 현재 색인** | 함수 등의 이름·파일·줄 위치·URI 주소록 | 없음 |
| **B — 파일 간 확장** | A 주소록 + 함수·상수 원문 + import와 파일 간 참조 관계 | 없음 |
| **R0 — 원문 검색** | 참조 관계 + 단일 원문·관련 코드 묶음 후보 + 검색용 가중치 | 없음 |
| **RF — 함수 요약** | R0 자료 + 함수별 원문 묶음의 요약과 출처 연결 + 요약 후보의 검색 준비 | 함수 요약 생성 시 호출 |
| **RH — 계층 요약** | RF 자료 + 파일·프로젝트 요약과 부모/자식 연결 + 상위 요약의 검색 준비 | 함수 요약 후 파일·프로젝트 요약 생성 시 호출 |
| **C — 계층 요약 정리** | RH와 같은 자료를 공유 | RH 구축 비용을 공유하며 C를 위해 새로 요약하지 않음 |
| **파일 전체** | 검색 전용 색인 불필요 | 없음 |

예를 들어 A만 사용한다면 전체 요약 트리를 만들 필요가 없다. RF와 RH를 함께 비교한다면 함수 요약은 한 번 만들고 공유할 수 있다. 실험의 `assets.json`에는 여러 방식을 비교할 자료가 함께 들어 있지만, UI에서 한 방식만 사용할 때 모든 방식의 자료를 반드시 만들 필요는 없다.

**질문이 들어온 뒤에만 하는 작업도 있다.** A·B의 ‘질문에 맞는 출발 함수를 LLM으로 선택’, B의 ‘선택 함수에서 참조 확장’, R0·RF·RH·C의 ‘질문과 후보의 점수 비교·토큰 한도 안 선택’은 버튼을 누를 때 완료할 수 없다. 특히 **C의 중복 제거는 RH가 그 질문에서 고른 자료에 적용하는 처리**다. 별도의 ‘C 압축 색인’을 생성하는 단계가 아니다.

### 2.4 실제 코드는 무엇을 저장하고, 무엇을 메모리에 준비하나?

| 자료 | 실제 구현에서 만드는 곳 | 현재 저장 또는 사용 형태 |
|---|---|---|
| A의 주소록 | `build_index(root)`가 파일을 파싱하여 객체 반환 | 반환만으로 파일이 생기지는 않는다. `write_index(root, output)`가 JSON으로 저장하며 기본 파일명은 `symbol_index.json`이다. |
| 원문·참조·원문 후보 | `source_nodes(root)` → `raw_items(nodes)` | 큰 파일 실험은 `index`, `nodes`, `raw`를 묶어 `assets.json`에 저장한다. |
| 함수·파일·프로젝트 요약 | 큰 파일 요약 빌더가 원문 후보 또는 하위 요약을 LLM에 전달 | 생성 중에는 `summary_nodes.jsonl`에 기록하고, 프로젝트별 `assets/<project>.json`과 전체 `assets.json`에 요약을 합친다. 호출·출처·자식 ID도 보존한다. |
| 생성 완료 내역 | 요약 빌더 | `build_manifest.json`에 생성 수·토큰·시간·자료 해시를 기록한다. 이는 현재 실험의 기록 형식이다. |
| TF-IDF 가중치와 후보 벡터 | `Retriever` 검색 코드 | 현재는 평가 실행 시작 시 메모리에 계산하고 질문들에 재사용한다. 위 JSON에 가중치·벡터를 영구 저장하는 구현은 아니다. |

큰 파일 RF·RH·C 실험은 앞선 원문 구축 결과를 `base_assets.json`으로 가져와 요약을 추가했다. **UI에서는 ‘원문 구축 → 필요한 요약 → 검색 준비’를 하나의 작업으로 연결하면 된다.** 앱을 다시 켤 때 저장 자료를 읽고 메모리의 검색 준비를 다시 수행하거나, 별도의 검색 저장 형식을 구현할 수 있다. 어떤 경우든 ‘저장 완료’와 ‘바로 검색 가능한 상태’를 구분해야 한다.

1.2절의 세 파일 예제로 보면, 백엔드가 `service.py`에서 `remaining`의 위치를 얻고, 참조 분석으로 `rules.py`의 `sellable`, `policy.py`의 `SAFETY_STOCK = 3`까지 연결한다. RF를 쓰면 **이 연결된 원문 묶음과 요약 지시문을 백엔드가 LLM에 보내고**, 응답 문장을 출처 목록과 함께 저장한다. RH를 쓰면 **백엔드가 파일별 묶음을 정하고 LLM이 그 묶음의 설명을 작성**한다. 사용자는 이 과정의 시작과 완료를 UI에서 확인한다.

### 2.5 코드가 바뀌거나 생성이 실패했을 때

사용자가 원하는 시점에 다시 생성하려면 **어떤 프로젝트의 어느 파일 내용으로 만든 색인인지**를 함께 관리해야 한다. A는 줄 위치가 바뀌면 다른 원문을 읽을 수 있고, B·R0는 저장한 원문이 오래될 수 있으며, RF·RH·C는 그 원문에서 만든 요약까지 오래될 수 있다.

제품에 연결할 때의 첫 구현은 버튼을 누를 때 선택 방식의 자료를 새 버전으로 만들고, **완성된 결과만 현재 색인으로 교체**하는 흐름으로 정할 수 있다. 생성 중 파일이 바뀌면 같은 버전의 파일 복사본을 끝까지 쓰거나 작업을 다시 시작하는 규칙이 필요하다. 변경된 부분만 갱신하는 기능을 추가한다면 바뀐 함수뿐 아니라 그 함수를 포함한 원문 묶음과 상위 요약도 갱신 대상이다.

파싱 오류·파일 읽기 실패·LLM 호출 실패는 작업 상태에 남기고, 실패한 결과로 마지막 정상 색인을 조용히 교체하지 않도록 한다. 일부만 사용할 경우에는 ‘부분 완료’와 빠진 항목을 표시하는 정책을 정해야 한다. 현재 실험에는 파일 해시와 요약 요청 해시를 확인하는 로직이 있지만, **UI의 자동 변경 감지·증분 갱신·취소·완료 버전 전환이 구현됐다는 뜻은 아니다.** 실험의 요약 출력 한도 처리 규칙은 3.3절과 5.5절에 별도로 보존했다.

현재 파서는 Python 중심이고, 파일 간 연결도 코드에서 읽어 낸 제한적인 정적 참조 분석이다. 다른 언어나 복잡한 import·동적 호출을 지원하려면 해당 분석기를 추가해야 한다. 또한 A 주소록과 참조 분석의 현재 파일 수집 규칙이 완전히 같지는 않으므로, UI 작업에서는 동일한 대상 파일 목록을 쓰도록 맞춰야 한다.
