**누락은 원문 1,024토큰 포장에 앞선 목록·선택 단계에서 주로 생겼다.** 지정한 원문을 길이 때문에 제외한 실행은 0회였다. 반면 목록에 없는 기준 항목은 전체 288회에서 1,587건이었다. 질문×반복×기준 항목별로 센 발생 횟수이며, 서로 다른 질문에서 같은 함수가 다시 필요하면 각각 센다.

| 기준 항목이 H 목록에 없던 이유 | 발생 횟수 | 의미 |
|---|---:|---|
| 해당 항목의 검색 점수가 0 | 765 | 다른 함수가 이 항목을 참조해도, 자신의 단독·출발 묶음 점수가 0이면 후보 목록에서 제외됨 |
| 양수 점수지만 상위 24개 밖 | 774 | 필요한 참조 항목이어도 자체 순위가 낮아 목록 검토 대상에서 빠짐 |
| 상위 24개 안이지만 목록 512토큰 초과 | 48 | 목록의 길이 제한에서 제외됨 |

따라서 목록 길이만 늘린다고 앞의 두 원인이 자동으로 해결되지는 않는다. **검색된 함수가 참조하는 항목을 번호가 있는 행으로 보존하는 설계**를 따로 검토해야 한다.

또한 96문제 중 **62문제의 사전 기준 원문 목록은 8개를 넘는다.** H는 함수·상수 합계 8개 제한이므로 이 문제들에서 기준 원문 100% 포함은 구조적으로 불가능하다. B의 제한은 함수 최대 8개이고 상수는 별도로 모으므로 H와 다르다. 기준 목록은 질문별 실행 경로의 최소 코드 집합을 증명한 것이 아니므로, 이를 ‘62문제 모두 정답 불가능’으로 해석하지는 않는다. 다만 이번 H의 포함률을 제한하는 설계임은 분명하다.

선택 실패 66회(22.9%)의 실제 이유는 다음과 같다. 출력 길이 초과나 통신 오류는 없었다.

| 선택 응답의 문제 | 실행 수 / 288 | 서로 다른 문제 수 / 96 |
|---|---:|---:|
| 허용한 8개보다 많이 지정 | 36 | 12 |
| 목록에 없는 번호를 지정 | 18 | 6 |
| 빈 목록을 반환 | 12 | 4 |

예를 들어 `can_edit_own('u1',['document:write'],100,3700)` 질문에서 선택 응답은 다음과 같았다.

```json
{"read":[1,2,3,4,6,7,9,10,11,12,13,19]}
```

모두 표시된 번호였지만 **12개를 골라 8개 상한을 어겼다.** 프로그램은 앞의 8개로 임의 수정하지 않고 선택 실패로 처리했다. 그래서 답변용 원문은 0토큰이었고, 두 호출의 입력 802토큰은 그대로 비용에 포함됐다. 이것은 함수 의미를 잘못 읽은 답변 오류와 구분되는 선택 절차의 실패다.

**실패가 절감률에 준 영향도 따로 확인했다.** 아래는 실행 후 원인을 살펴본 사후 기술 분석이며, 각 행의 H와 R0는 같은 질문·반복끼리 비교했다.

| H의 선택 상태 | 실행 수 | H 누적 입력 평균 | 같은 실행의 R0 누적 입력 평균 | 절감률 |
|---|---:|---:|---:|---:|
| 전체 | 288 | 1016.6 | 1164.7 | 12.7% |
| 선택 규칙을 지킴 | 222 | 1072.6 | 1162.7 | 7.7% |
| 선택 규칙 위반 또는 빈 선택 | 66 | 828.3 | 1171.5 | 29.3% |

선택 실패 때는 원문을 보내지 않아 입력이 특히 작았다. 따라서 전체 12.7% 절감을 모두 성공적인 원문 선별의 효과로 설명할 수 없다. 규칙을 지킨 74문제에서는 H와 R0가 각각 19문제를 맞혔지만, **H가 성공적으로 선택한 질문만 사후에 남긴 부분집합**이다. 이를 전체 문제에서 정확도를 유지했다는 증거로 쓰지 않는다. 전체 성적은 여전히 H 19/96, R0 25/96이다. [실패 분류와 조건부 비용 원자료](evidence/hybrid_index_20261027/diagnostics_posthoc.json)에 계산을 보존했다.

### 8.6 같은 질문에서 좋아진 사례와 나빠진 사례

아래는 **1회차의 실제 응답**이다. H만 R0보다 맞힌 경우와, R0만 H보다 맞힌 경우를 각각 질문 ID 순서상 첫 사례로 골랐다. 전체 평균을 대표하는 예시는 아니며, 같은 자료를 적게 보낸다고 정답이 자동으로 유지되지는 않는다는 점을 보여 준다.

| 실제 질문 | 기준 답 | B의 답 / 총 입력 | R0의 답 / 총 입력 | H의 답 / 총 입력 |
|---|---|---|---|---|
| `cache_ttl(-1, False)`의 반환값은? | `0` | `30` 오답 / 478 | `300` 오답 / 1145 | `0` 정답 / 868 |
| `authorize`가 직접 호출하는 프로젝트 함수들을 정렬해서 나열하라 | `role_allows`, `scope_allows`, `session_valid` | 세 함수 모두 정답 / 791 | 세 함수 모두 정답 / 1154 | `session_valid`를 빠뜨림 / 927 |

첫 사례에서 H의 선택용 LLM은 `{"read":[1]}`을 반환했다. 프로그램이 목록 1번 `cache_ttl`의 원문만 읽어 보내자, 답변용 원문은 **87토큰**이었다. R0의 원문은 **1,021토큰**이었다. 하지만 H에는 계산에 참조되는 상수의 **이름만 있고 값은 없었다.** 사전에 지정한 원문 4개 중 함수 1개만 포함해 지표는 25%였다. H가 정답을 출력했다는 사실만으로 필요한 근거를 충분히 확보했다거나, 짧은 입력이 정답의 원인이라고 해석할 수는 없다.

두 번째 사례에서도 H는 목록 1번 `authorize`만 읽었다. 아래 코드는 **실제 H 입력에 들어 있던 내용**으로, 세 함수의 호출이 모두 나타난다.

```python
from policy import ALLOW_REASON, DENY_REASON
from rules import session_valid, role_allows, scope_allows
def authorize(user, owner, role, scopes, action, created_at, now, revoked):
    if not session_valid(created_at, now, revoked):
        return {"allowed": False, "reason": "session"}
    granted = role_allows(role, owner, user) and scope_allows(scopes, action)
    return {"allowed": granted, "reason": ALLOW_REASON if granted else DENY_REASON}
```

H의 원문은 122토큰으로 R0의 1,017토큰보다 짧았고, 이 질문의 기준 원문인 `authorize`도 포함했다. 그런데 답변 LLM은 보이는 `session_valid`를 목록에서 빠뜨렸다. **이 오답을 ‘필요한 원문이 없어서’라고 설명하면 틀린다.** 정답 여부는 최종 답변까지 확인해야 한다. [두 사례의 목록·선택·입력·답변 기록](evidence/hybrid_index_20261027/report_examples.json)에서 대조할 수 있다.

### 8.7 이번 결과로 무엇을 선택할 수 있나?

**결합은 가능하고 R0보다 입력을 줄였지만, 이번 H 구현에서 정확도까지 보존한 개선을 확인하지는 못했다.** 원문을 단독 항목으로 골라 보내는 만큼 참조 정보가 빠질 수 있고, 선택 호출 자체에도 비용이 들었다.

| 판단 기준 | 이번 표본에서 확인한 결과 |
|---|---|
| 파일 하나 전체보다 입력을 적게 보내기 | H는 기존 파일 전체 입력보다 누적 토큰을 76.2% 줄였다. 다만 관련 파일의 일부를 고르는 H와 대상 파일 하나를 모두 넣는 방식은 전달 정보의 범위가 다르다. |
| R0보다 한 번의 컨텍스트를 작게 쓰기 | H는 최대 호출 입력의 평균을 1164.7→671.8토큰으로 42.3% 줄였다. 누적 입력 절감은 선택 비용을 포함하면 12.7%, 선택 규칙을 지킨 부분집합에서는 7.7%였다. |
| B를 대체할 이점 | H는 B보다 누적 입력 32.1%, 최대 호출 입력 평균 13.6%, 시간 34.3%가 더 컸고 관측 정답은 20→19개였다. 이번 표본에서 B를 대체할 뚜렷한 이점을 확인하지 못했다. |
| R0의 정답률을 유지하면서 절약하기 | 관측 정답은 25→19개로 줄었다. 차이의 구간은 넓지만, 정확도 유지·개선을 입증한 결과도 아니다. |

따라서 **이번 H를 그대로 권장하기보다는, 목록에서 참조 항목을 보존하고 선택 규칙을 안정적으로 지키게 하는 설계를 먼저 보완하는 편이 타당하다.** 특히 본문을 생략한 색인에도 필요한 함수·상수를 모두 찾을 수 있는 연결은 남아야 한다. 이번 결과가 TF-IDF와 색인을 결합하는 모든 방식의 성능을 대표하지는 않는다.

후속 비교에서는 **검색된 묶음의 구성원들을 본문 없이 목록에 보존하는 방식**, **함수 개수 제한과 작은 상수의 처리를 분리하는 방식**, **허용된 번호·개수를 지키도록 선택 출력을 제한하는 방식**을 분리해 시험할 수 있다. 추가 읽기나 재시도를 허용한다면 그 호출의 토큰·시간도 모두 더해야 한다. 이 보완안들은 이번에 실행한 결과가 아니며, 개선 폭을 예상값으로 채우지 않았다.
