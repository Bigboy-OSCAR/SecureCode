### 1.11 H — TF-IDF로 찾고, 작은 색인으로 읽을 원문을 고른다

**H는 이번에 시험한 결합 방식의 이름이다.** R0의 단어 검색과 A·B의 ‘먼저 목록을 보고 원문을 고르는 절차’를 결합했다. H라는 이름의 기존 논문 알고리즘을 재현한 것은 아니며, RAPTOR 요약도 만들지 않는다. 핵심은 **검색할 때 참고하는 원문과 LLM에 실제로 전달할 원문을 구분**하는 것이다.

여기서 ‘작은 색인’은 **LLM에게 보여 줄 함수·상수 주소록**을 뜻한다. R0의 TF-IDF 검색 자료에 이 주소록을 추가해, 프로그램의 검색과 LLM의 원문 선택에 서로 다른 형태의 자료를 사용한다.

R0는 TF-IDF 점수가 높은 원문 후보를 길이 제한 안에서 답변 LLM에 직접 보낸다. H는 같은 점수를 **작은 함수·상수 목록을 추리는 데** 사용한다. LLM이 그 목록에서 읽을 항목을 지정하면, 프로그램이 지정한 항목의 원문만 꺼내 두 번째 호출에 보낸다. 이름과 위치만으로 실제 계산을 알아낼 수는 없으므로, 최종 답변 단계에는 선택한 코드 본문이 필요하다.

아래는 이 방식을 UI에 연결할 때의 처리 구분이다. **이번에는 실험 스크립트로 실행했으며 UI 버튼이나 제품의 색인 갱신 기능을 구현한 것은 아니다.** 기존 큰 파일의 R0 원문·참조 자료를 그대로 재사용하고, 작은 목록과 검색 벡터를 준비했다.

| 시점 | 처리 주체 | 하는 일과 저장·전달 자료 |
|---|---|---|
| 사용자가 색인 생성을 요청할 때 | 프로그램의 파서 | 전체 프로젝트를 읽어 함수·상수 원문, 위치, 파일 간 참조를 준비한다. 별도로 이름·인자 이름·줄 범위·직접 참조만 담은 작은 목록을 만든다. |
| 검색 준비 | 프로그램의 TF-IDF 계산기 | R0와 같은 단일 원문·최대 3단계 참조 묶음에서 단어 가중치를 계산한다. 이 원문과 벡터는 로컬 검색 자료이며, 전부 LLM에 보내지 않는다. |
| 질문이 들어올 때 | 프로그램의 검색기 | 질문도 같은 규칙으로 단어·벡터로 변환한다. 원문 후보와의 유사도를 계산하고, 관련 함수·상수의 **본문 없는 목록**을 추린다. |
| 첫 번째 LLM 호출 | 선택용 LLM | 원래 질문과 추린 목록을 읽고, 읽어야 할 항목 번호를 반환한다. **TF-IDF 가중치나 원문 본문은 이 호출에 보내지 않는다.** |
| 두 번째 LLM 호출 | 프로그램 → 답변용 LLM | 프로그램이 지정된 항목의 원문을 읽어 원래 질문과 함께 전달하고, 같은 LLM 모델이 답한다. 선택 호출의 대화 전체를 이어 붙이지 않는 별도 호출이다. |

1.2절의 예제를 H의 목록 형식으로 나타내면 다음과 같다. **번호와 순서는 이해를 위한 예시이며, 아래 선택 응답은 가정이다.** 실제 96문제의 목록·선택 응답·정답은 8절에서 따로 검증한다.

```text
1. function service.py:3-4 remaining(on_hand, held) -> rules.py::sellable
2. function rules.py:3-4 sellable(on_hand, held) -> policy.py::SAFETY_STOCK
3. constant policy.py:1-1 SAFETY_STOCK -> -
```

여기서 `->` 오른쪽은 이 항목이 직접 참조하는 다른 항목의 주소다. `remaining`의 계산식이나 `SAFETY_STOCK = 3`의 **값 3은 목록에 없다.** 함수가 2줄이든 200줄이든 이 목록에는 본문을 복사하지 않는다. 저장된 한 항목은 다음처럼 생겼다.

```json
{
  "uri": "memory://symbol/rules.py::sellable",
  "kind": "function",
  "signature": "sellable(on_hand, held)",
  "path": "rules.py",
  "start": 3,
  "end": 4,
  "deps": ["memory://symbol/policy.py::SAFETY_STOCK"]
}
```

이때 선택용 LLM이 `{"read":[1,2,3]}`을 반환했다면, 프로그램은 세 항목의 **각 원문 본문**을 읽는다. 답변 LLM은 그제야 `remaining → sellable` 호출, `max(0, on_hand - held - SAFETY_STOCK)` 계산식, 상수 값 `3`을 모두 볼 수 있다. 반대로 `{"read":[2]}`라면 **`sellable`의 원문만** 읽는다. `sellable`을 점수화할 때 참조 묶음을 사용했더라도, 그 묶음 전체가 자동으로 전달되는 것은 아니다. `import`문은 포함되지만 다른 파일의 정의까지 대신하지는 않는다.

**검색 순위와 전달 범위를 분리한 규칙은 다음과 같다.** 함수 하나에 단독 원문 후보와 ‘그 함수를 출발점으로 한 참조 묶음’이 있으면 두 검색 점수 중 큰 값을 그 함수의 순위 점수로 쓴다. 예를 들어 `f0` 묶음의 높은 점수를 묶음에 들어 있는 `f1·f2·f3` 모두에게 나눠 주지는 않는다. 각 항목은 자기 단독 후보 또는 자기 출발 묶음으로 순위가 정해진다.

양수 점수의 상위 24개 항목을 검토하고, 목록 **본문 512토큰** 안에 들어가는 행만 보낸다. 선택용 LLM은 그 안에서 **함수와 상수를 합해 최대 8개**를 지정한다. 프로그램은 지정 순서대로 원문 **1,024토큰** 안에 담으며, 넘치는 항목은 통째로 건너뛴다. 남은 공간을 다른 함수로 채우거나, 빠진 의존 함수를 자동 추가하거나, 추가 LLM 호출로 재선택하지 않는다. 선택 응답이 형식·번호·개수 규칙을 어기거나 비면 재시도하지 않고 오답으로 평가한다.

**화살표 뒤에 참조 주소가 보이는 것과 그 항목을 읽을 수 있는 것은 별개다.** 그 항목 자체가 번호를 가진 행으로 목록에 들어와야 선택할 수 있다. 예를 들어 `sellable -> SAFETY_STOCK`이 보여도 `SAFETY_STOCK` 행이 검색 순위나 목록 길이 제한 때문에 빠졌다면, 이 구현의 LLM은 상수 원문을 요청할 수 없다. 8절에서는 이런 목록 단계의 누락과, 목록에 있었는데 선택하지 않은 경우를 나눠 확인한다.

이 설계는 **작은 목록을 보여 주는 비용을 더 지불해서, 필요 이상의 원문 전달을 줄일 수 있는지** 시험한다. 목록 512토큰은 기존 원문 한도 1,024토큰에 추가되는 별도 한도이며, 두 호출의 질문·지시문·입력을 모두 비용에 포함한다. 목록 크기는 본 실험 전에 고정한 선택이고 최적값을 찾은 결과가 아니다. 함수 본문 자체가 매우 길면 H도 그 함수 전체를 읽어야 하므로, 함수 내부를 잘라 읽는 방식까지 검증한 것은 아니다.
