## 구현 범위

- 계약 타입 기반 `RunClient`와 fixture 전용 adapter를 분리하고, `RunController`, `RunCommands`, `RunViewState`로 요청·이벤트 구독·화면 상태를 나눴다.
- 세션/워크스페이스/run scope, event ID, sequence, terminal snapshot을 검사한다. sequence 누락·역순 이벤트에서는 authoritative snapshot을 다시 읽고, terminal 상태는 늦은 이벤트로 되돌리지 않는다.
- idempotency key를 실행별로 생성하고 중복 제출 요청은 기존 요청과 합친다. 승인 결정은 계약의 `input_digest`를 전달하며, 응답 timeout/만료에는 결정을 재전송하지 않고 상태 snapshot을 재조회한다.
- 취소는 서버의 terminal snapshot 확인 전 terminal 상태로 바꾸지 않는다. 연결 끊김에는 mutation을 차단하고 재연결 시 snapshot 및 이벤트 구독을 복구한다. 세션 교체·화면 종료 후 늦은 응답과 구독을 정리한다.
- project, connection, approval, pointer read/registration, PDF 입력 동작을 기능별 hooks/model로 분리했다. run API 교체 경계는 `RunClient`이며, feature action hook은 UI 컴포넌트의 요청 handler를 담당한다.
- 답변과 원문은 제한된 preview만 표시한다. UI 소스에 `localStorage`, `sessionStorage`, 숨은 HTML 본문 삽입이 없다. 등록 해제와 Runtime 삭제는 서로 다른 작업/확인으로 구분하며 원본 파일 삭제 기능은 없다.
- 정상 완료·실패·거절·취소·재연결, 승인 timeout/만료, 중복 제출/이벤트, 역순 sequence, 이전 run의 늦은 이벤트, 세션 교체, dispose 이후 응답을 시험한다.
- Fixture 기반 구현이며 실제 HTTP/SSE/Host SDK 요청은 발생시키지 않는다.

## 인수 근거 및 다음 작업 연결

- 완료/실패 snapshot의 화면 표시 시험, 거절 후 실행 상태 보존, 취소 terminal 확인, disconnect/reconnect snapshot 복구 시험이 통과했다.
- 중복 제출은 한 번의 요청과 같은 idempotency key를 공유한다. 중복 event ID/sequence는 답변을 중복 반영하지 않고, sequence 역전은 snapshot 복구를 유도한다. 이전 run 이벤트와 이전 세션의 생성 응답은 현재 상태를 변경하지 않는다.
- 1.4는 [runClient.ts](../../apps/ui/src/api/runClient.ts)의 `RunClient` 메서드(`createRun`, `getRun`, `cancelRun`, `decideApproval`, `subscribe`)를 실제 HTTP/SSE adapter로 구현하고 `useRunController`에 주입하면 된다. 현재 화면과 controller를 바꾸지 않고 fixture adapter를 대체하는 것이 handoff 경계다.
- 2.3은 화면/행동 시험과 feature hooks를 이어 받아 화면 상태 통합을 검증할 수 있다. 화면 표시 명세 변경 요청은 없다.
- 본 기록의 UI·계약 검증은 fixture 기반이다. 실제 API/SSE/SDK live 연동은 미검증이며 1.4에서 수행한다.
