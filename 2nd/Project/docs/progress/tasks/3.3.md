## 구조

`services/context-service/src/securecode_context/symbols/`를 로드맵 0.5의 `symbols/{parser,index,graph}`로 나눴다. 기존 파서 파일은 `git mv`로 옮겨 내용을 유지했다.

| 패키지 | 책임 |
| --- | --- |
| `parser/` | 확장자·구문 트리로 언어를 판별하는 `dispatch.py`와 Python·C/C++·Java·JavaScript 파서, `Declaration`/`Reference` 모델 |
| `graph/` | 파일·스코프 키로 유일한 대상만 연결하는 `SourceGraph`와 단일 원문·깊이 3 R0 후보 |
| `index/` | 제외 규칙 탐색(`walker`), 안전한 파일 읽기(`source_reader`), 스캔(`scanner`), 루트 정책(`roots`), manifest 차이(`changes`), 디스크 변경 감지(`freshness`), revision 기록·저장(`records`, `revision_store`), 상태 응답(`status`), 조립(`service`), Source 등록부 포트(`ports`) |

`index/service.py`의 `SymbolIndexService`는 다음 순서로 동작한다.

1. `build()`는 작업 공간 전체를 다시 스캔한다.
2. 새 revision 파일을 완성한 뒤 `current.json`을 rename으로 교체한다.
3. 읽는 쪽은 `current.json`이 가리키는 완성 파일만 읽는다. 따라서 이전 revision과 새 자료가 섞이지 않는다.

빌드가 실패하면 이전 revision을 계속 제공하고 상태만 `failed`로 둔다. 같은 작업 공간에서 빌드가 진행 중이면 두 번째 요청은 새 빌드를 시작하지 않고 `indexing`과 `pending_revision`을 돌려준다.

## 인수 근거

**조건 1 — 다섯 언어의 원문·정적 참조·출처/hash와 파일별 격리**

- `test_single_language_project[python|c|cpp|java|javascript]`: 언어마다 단독 프로젝트를 색인했다. 모든 심볼의 바이트 범위 원문, 시작·끝 줄, 파일 SHA-256이 디스크와 같고, 다른 파일을 거치는 bundle 구성이 고정 값과 같다. 언어별 bundle은 다음과 같다.
  - Python: `compute→scale→RATE`, decorator `traced`
  - C: `run→clamp→MAX_ITEMS`, `box`
  - C++: `total→geo::Shape`
  - Java: `Main→Limits`(명시 import)
  - JavaScript: `run→double(별칭 import)→BASE`
- `test_python_decorator_alias_and_dynamic_reference`: decorator 줄(8)부터 원문을 시작한다. 상대 import의 별칭 `R`을 상수로 연결하고, `getattr()` 동적 호출은 `unresolved_reference`로 남긴다.
- `test_mixed_project_keeps_languages_apart`: 혼합 프로젝트에서 다음을 확인했다.
  - 같은 이름 `helper`는 Python·C·JS에서 각자 자기 언어 파일로만 연결된다.
  - Python 순환 `ping↔pong`은 무한 반복 없이 bundle 2개 심볼로 끝난다.
  - 깨진 Python·C·Java·JS 파일은 각각 `syntax_error`, TypeScript는 `unsupported_language`로 기록된다.
  - `.git`, `.securecode`, `node_modules`, `venv`, `build`, `generated` 아래 파일은 색인되지 않는다.
- `test_failures_are_isolated_per_file`: 인코딩 오류·1 MiB 초과·구문 오류 파일 옆의 정상 JS 파일은 모두 색인된다.
- `test_windows_junction_escape_is_rejected`: 루트 밖을 가리키는 NTFS 정션은 `path_rejected`이고 외부 원문을 읽지 않는다.
- symlink 파일·디렉터리 시험(`test_symlink_escape_is_rejected`, 기존 `test_file_isolation`)은 이 PC에서 권한이 없어 skip됐다. 같은 경로 검사(`lstat`의 일반 파일 확인과 링크 거부)는 정션 시험이 통과시킨다.

**조건 2 — 변경/삭제/이동 시 원자 전환과 stale 거부**

- `test_modify_delete_move_switch_revisions`: 수정·이동·삭제 각각에서 다음 동작을 확인했다.
  - `status()`가 `stale`을 보고한다.
  - `build()`가 revision 2→3→4로 전환하고, `parent_revision`과 `changes`(modified/moved/deleted)가 정확하다.
  - 상수 수정 시 그 상수를 포함한 `compute` bundle이 `stale_candidate_ids`에 들어간다.
  - 이전 revision 1 요청은 `SOURCE_CHANGED`(`index_revision_superseded`)로 거부된다.
- `test_stale_source_is_not_returned`: 재색인 전에 파일을 바꾸면 `verified_symbol()`이 원문 대신 `SOURCE_CHANGED`(`content_changed`)를 반환한다. fixture 등록부의 `pointer`를 붙인 출처는 `SourceProvenance` 계약을 통과하고, 미등록 파일의 `pointer`는 null이다.
- `test_failed_publish_keeps_previous_revision`: `current.json` 교체 직전 실패나 용량 초과 뒤에도 새 프로세스는 revision 1만 읽는다. 임시 파일은 남지 않고, 다음 게시는 번호를 재사용하지 않는다.
- `test_touch_without_content_change_is_not_stale`: 수정 시각만 바뀐 파일은 다시 해시해서 stale로 보지 않는다. 새 지원 파일은 stale, 미지원 파일은 무시한다.
- `test_concurrent_build_reports_indexing`, `test_store_rejects_bad_ids_and_mixed_records`, `test_cli_publishes_revisions`가 다음을 검증한다.

  - 최근 2개 revision만 남긴다.

## 3.4 입력 계약

`securecode_context.symbols.index`에서 다음을 import한다.

- `SymbolIndexService.current(workspace_id)`: `IndexRevisionRecord`를 돌려주고, 색인이 없으면 `INDEX_NOT_READY`다. 기록 필드는 `index_revision`, `nodes`(심볼별 원문·위치·해시·deps·unresolved), `raw`(단일 원문과 깊이 3 후보), `manifest`, `changes`(`stale_candidate_ids`, `idf_recompute_required`), `retrieval.state="pending"`이다.
- `SymbolIndexService.require_revision(workspace_id, index_revision)`: revision이 다르면 `SOURCE_CHANGED`다.
- `SymbolIndexService.verified_symbol(workspace_id, root, index_revision, symbol_id)`: 원문을 내보내기 직전에 revision과 디스크 해시를 다시 확인하고, `SourceProvenance`를 포함한 `VerifiedSymbol`을 돌려준다.
- `SourceRegistryPort.lookup(workspace_id, relative_path, content_sha256)`: 기본값 `UnregisteredSourceRegistry`는 **fixture**이며 항상 미등록(null)을 답한다. symbols는 pointers 패키지를 import하지 않는다.

## 제한

- revision의 `retrieval.state`는 `pending`이다. 검색 벡터가 없으므로 상태는 `parsed`, `searchable=false`다. `ready`·`partial` 전환은 3.4가 TF-IDF 준비 후 수행한다.
- 갱신은 MVP 정책에 따라 매번 전체를 다시 스캔한다. 변경 파일·영향 후보·IDF 재계산 필요성은 기록만 하고 증분 재계산은 하지 않는다.
- 빌드는 호출 스레드에서 동기 실행한다. `indexing`·`failed` 상태는 프로세스 메모리에만 있어 재시작하면 사라진다. 게시된 revision은 디스크에 남는다. 작업 공간 ID→루트 매핑과 HTTP `POST|GET /workspaces/:id/index`는 3.5/3.6 범위다.
- Windows에서 다른 프로세스가 `current.json`을 연 채로 있으면 `os.replace`가 실패할 수 있다. 이 경우 빌드는 `failed`가 되고 이전 revision이 유지된다(재시도는 하지 않음).
- `status()`의 stale 감지는 지원 파일 전체를 `lstat`으로 확인한다. 크기나 수정 시각이 바뀐 파일과 새 파일만 다시 해시한다.
- C 함수가 같은 파일에서 정의되고 포함한 헤더에 원형이 있는 경우에만 구현에 연결한다. 그 밖의 다중 후보는 계속 `unresolved_reference`다.
