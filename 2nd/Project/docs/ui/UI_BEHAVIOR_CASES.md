## 1. 사용 규칙

각 행은 **사전 상황 → 사용자 조작 또는 서버 응답 → 예상 화면·버튼·메시지**다. 아래 fixture ID는 `contracts/fixtures/` 아래의 실제 파일 경로이며 `.json`까지 정확하게 적는다. scenario는 대표 사례 하나를 가리킨다. 같은 응답이 여러 화면에 쓰일 때는 각 행에 다시 인용한다. 한 fixture의 존재는 해당 사용자 흐름 전체가 검증됐다는 뜻이 아니다.

`valid`의 `data`는 렌더 입력, `invalid`는 경계 검증에서 거절할 입력이다. 여러 payload를 조합하는 지연/유실/역순 시험은 김민지 1.3이 구현한다. fixture를 복제해 새로운 wire 타입·상태·이벤트를 만들지 않는다. 승인 시계는 fixture의 requested_at과 expires_at 사이로 고정한다. 실제 현재 날짜를 쓰면 과거 fixture는 이미 만료된 사례다. scope가 다른 fixture는 명시적 교차 세션 시험 외에는 한 흐름으로 섞지 않는다.

## 3. 인계와 사용 예

- UI-23에서 직접 선택할 수 있는 값은 반환된 selection이다. 원문이 잘리면 응답의 바이트 범위만 검토한다. UI-24의 원본 변경 시 선택과 미리보기 확인을 폐기한다. UI-30의 preview-plan-request는 UI-23에서 본 “한글” 6바이트의 포인터·해시·범위를 사용한다. preview-plan-response의 실제 원문과 포함·중복 이유를 확인한 뒤, run-create-from-preview는 같은 질문·선택과 응답의 preview_digest를 전송한다.
- UI-27의 정상 흐름은 parse 요청 → queued/running → ready → 페이지 읽기다. UI-28의 partial에서는 제외된 페이지 번호만 비활성화한다. UI-29의 stale에서는 기존 읽기·선택을 막고 새 revision으로 재처리한다.
- UI-12는 실행 중 단절 → 재구독 범위 초과 → snapshot 재조회 순서로 검토한다. UI-13~15는 고정된 시험 시각, run·approval ID, digest로 구별한다. 승인 요청이 대기 목록에서 사라져도 최종 승인 기록을 확인하기 전에는 성공으로 표시하지 않는다.
- 화면 표현은 1.2, 중복·지연·유실 시의 행동 시험은 1.3에서 수행한다. PDF 추출, 도구 실행 횟수, 실파일 보존, SSE와 모델 요청의 원문 차단은 별도 운영 검증 대상이다.
