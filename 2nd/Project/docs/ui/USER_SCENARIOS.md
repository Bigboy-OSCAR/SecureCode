# 화면 인수 시나리오 초안

> 작업: 2.1 · 담당: 김찬우 · 작성일: 2026-10-30 (Asia/Seoul)
>
> 기준: [화면 설계](SCREEN_SPEC.md), [계약 요구](../handoffs/2.1-ui-contract-requirements.md)

아래 시나리오는 설계 인수 범위이며 실행 시험 결과가 아니다. ID는 2.2의 표시 명세, 2.3의 `ACCEPTANCE.md`, 1.2/1.3/1.6의 시험에 그대로 이어서 사용한다. API·이벤트·오류 fixture는 3.2/4.2가 생성한다. 이 문서의 예시 데이터는 fixture 요구이며 아직 존재하는 fixture ID로 간주하지 않는다.

## 1. 공통 준비와 검증 단계

- Python 프로젝트: 최상위 함수→다른 파일 helper→상수, async 함수, 클래스·메서드, 해결 불가 동적 참조, 구문 오류 파일, 다수 무관 심볼, TypeScript/JavaScript 파일을 포함하는 공개 시험용 자료를 준비한다.
- 자료: 큰 한글 텍스트, 8 MiB 이하/초과 JSON, 다중 페이지 한글 텍스트 PDF, 스캔·빈·손상·암호화 PDF와 상한 초과 자료를 준비한다. 개인 원문·절대 개인 경로·비밀값을 증거에 저장하지 않는다.
- 실행: 승인 가능한 무해한 fixture 명령과 코드 수정, 짧은 출력/16 KiB 초과 출력, 저장 실패, 모델 실패, 거절·취소·만료, 서로 다른 두 세션을 준비한다.
- 계수: 동일 tokenizer·동일 응답 예산으로 요청별 수치를 비교하고 미검증 값을 exact라고 표시하지 않는다. 이 설계 단계에서 실험 수치를 제품 성능으로 옮기지 않는다.

1. **설계 점검(2.1):** 모든 화면의 입력·출력·정상/실패·계약 요구와 시나리오 연결을 검토한다.
2. **계약 fixture 검증(1.2/1.3, 검토 2.3):** 렌더·버튼·중복/역순 이벤트·접근성을 검증한다. fixture 통과를 실제 모델 실행으로 기록하지 않는다.
3. **실서비스 검증(1.4/1.5/1.6, 3.6/4.10/3.8):** 실제 서비스의 상태·원문 보존·승인 결과·범위 I/O·요청 예산과 대조한다. provider/history/SSE 경계는 통합 증거가 필요하다.

표의 구현 작업은 김민지의 UI 작업을 뜻한다. 백엔드 계약·구현 책임은 H 번호와 화면 설계의 기능 대응표를 따른다. 모든 행은 최종적으로 1.6/3.8에서 확인한다.

## 6. 후속 작업의 증거 요구

1.2/1.3은 위 ID별 fixture와 실제 조작 결과를 기록한다. 2.3은 표시·문구·행동 차이와 재현 순서를 남기고, 1.6은 두 화면 폭과 정상/실패 흐름을 실서비스에서 확인한다. 실제 실행하지 않은 항목은 미검증으로 남긴다.

UI-13/UI-14/UI-15는 “승인됨” 문구만으로 통과하지 않는다. 실제 도구 실행 횟수와 거절·만료 시 실행 0회를 확인한다. UI-23/UI-24는 서버의 bounded I/O와 revision 검증 증거가 필요하다. UI-27은 실제 PDF 도구·Skill 연결, UI-31은 최종 outbound 예산 차단, UI-34는 실제 SDK·provider/history/SSE 경계를 확인해야 한다. 이 검증은 3.6/4.10/3.8과 연결하며 UI 작업 하나로 대체하지 않는다.
