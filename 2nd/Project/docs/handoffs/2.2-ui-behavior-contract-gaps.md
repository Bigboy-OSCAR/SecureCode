# 2.2 화면 명세의 계약 보완 및 인계

김찬우 · 2026-11-05 (Asia/Seoul)

9개 화면을 공개 API와 대조하면서 발견한 G-01~G-08의 처리 기록이다. 아래 계약은 화면 구성과 예시 검증에 사용한다. 운영 호스트가 501을 반환하면 화면은 “이 기능은 아직 준비 중입니다”를 표시한다. [상세 명세](../ui/UI_BEHAVIOR.md) · [34개 사례와 시험 데이터](../ui/UI_BEHAVIOR_CASES.md) · [실행한 검증](../progress/tasks/2.2.md)

### G-01 · 사용자가 확인한 범위를 실행에 전달

읽기 응답의 `provenance.selection`을 미리보기와 실행의 명시적 포인터 참조에 그대로 넣는다. revision, 원본 SHA-256, 실제 UTF-8 시작·끝 위치가 고정되며 PDF에는 페이지와 파서 버전도 들어간다. 구형 포인터만 남은 기록은 표시할 수 있지만 재전송 전 다시 읽어야 한다. UI-23→UI-30에서 “한글” 6바이트의 읽기·선택·미리보기·실행을 같은 값으로 비교했다. ### G-02 · 자료 등록·목록·갱신·삭제

Source 등록과 갱신은 같은 POST에서 operation을 구분한다. 디렉터리 일부만 성공하면 등록 결과와 파일별 실패를 함께 보여 준다. 목록은 자료 종류·세션 범위와 cursor로 조회하며 각 항목의 표시 이름·지원 선택자를 사용한다. DELETE의 성공 효과는 Source 등록 해제와 Runtime 결과 삭제로 나뉜다. 제출 응답을 잃으면 같은 키·본문으로 결과를 확인한다. [생명주기 계약](../../contracts/pointers/lifecycle.schema.json) · [부분 등록 예시](../../contracts/fixtures/pointers/source-register-partial.valid.json)

### G-03 · 반환 범위와 PDF 원문 출처

요청자가 지정한 범위와 실제 읽어 온 범위를 구분한다. 텍스트는 원본의 바이트, PDF는 한 페이지의 추출 텍스트 안에서의 바이트를 쓴다. 검색 결과에서도 서버가 확인한 조각만 선택한다. 내용이 없거나 실제 범위를 확인할 수 없는 구형 응답에서는 선택 버튼을 잠근다. ### G-04 · 미리보기 입력·관련 코드·예산 표시

공개 POST /context/preview가 operation에 따라 검색, 원문 묶음, 전달 계획을 구분한다. 화면은 후보의 origin, 실제 포함 조각의 provenance, 중복·예산 제외 이유, budget.costs를 사용한다. 사용자가 질문이나 범위를 바꾸면 다시 확인한다. 서버가 미리보기 만료를 알리면 새 실행을 만들지 않고 미리보기를 갱신한다. ### G-05 · PDF 상태·재처리·지원 범위

등록한 Source의 버전에 대해 파싱을 요청하고 job_id로 상태를 복구한다. 대기·처리 중·완료·일부 제외·미지원·실패·변경의 7가지 응답을 구분한다. partial은 제외 페이지와 사유를 반환한다. stale은 기존 페이지 열람·전달을 잠그고 재처리를 안내한다. 이번에 검증한 자료는 화면용 JSON이며 PDF 파일 추출과 파서 실행은 별도 구현 작업에 속한다. ### G-06 · 단위·승인·설정·cursor

포인터 읽기·검색은 16,384바이트와 32,768토큰, R0 묶음은 최대 32 KiB다. 검증기가 UTF-8 바이트를 세어 preview 512바이트·승인 내용 16,384바이트 경계와 잘못된 유니코드를 거절한다. 잘린 내용은 검토 불가다. limits의 키 이름으로 바이트·토큰·초·페이지를 구분하고 없는 값은 “제공되지 않음”으로 표시한다. 다른 범위의 cursor는 INVALID_POINTER, 변경된 Source 버전은 SOURCE_CHANGED로 구분한다. [설정 예시](../../contracts/fixtures/api/settings-effective-limits.valid.json) · [포인터 계약](../contracts/POINTERS.md)

### G-07 · 재연결 후 출처와 승인 결정 복구

run snapshot은 답변 출처, 미결 승인, 최종 승인 이력을 구분한다. 두 이력은 각각 같은 snapshot에 묶인 cursor로 추가 조회할 수 있다. 기존 SSE의 Last-Event-ID로 복구하지 못했을 때 snapshot을 읽으며, 재접속 과정에서 같은 명령이나 승인을 새로 요청하지 않는다. 구형 snapshot에서 이력이 생략됐다면 “정보 없음”으로 표시한다. [복구 예시](../../contracts/fixtures/api/run-snapshot-recovered-evidence.valid.json) · [이벤트 복구 규칙](../contracts/EVENTS.md)

### G-08 · 사례 번호와 예시 연결

각 JSON의 UI 번호는 하나의 대표 사례를 식별한다. 승인 요청은 UI-13, 거절 이벤트는 UI-14, 만료 결정은 UI-15, 취소 snapshot은 UI-11, replay 범위 초과는 UI-12, 프로젝트 등록은 UI-03에 연결했다. 여러 사례에 재사용하는 예시는 각 행에 직접 인용한다. 접근성 사례 UI-33은 같은 응답을 다른 화면 폭·키보드 입력으로 확인한다. 인계 검사는 예시의 존재와 대표 번호가 가리키는 사례 행까지 대조한다. [화면 사례표](../ui/UI_BEHAVIOR_CASES.md)

## 후속 담당자가 사용할 자료

1. 화면 필드·입력·버튼·오류·복구·접근성은 UI_BEHAVIOR의 SC-01~SC-09에서 확인한다.
2. 정상 화면은 valid 예시의 data로 구성하고 invalid 예시는 경계에서 거절한다. 같은 요청을 재현할 때는 workspace·session·revision·digest를 고정한다.
3. 이번 인계의 범위는 설계·공개 데이터 계약이다. UI 상태 관리, 실행 화면 시험, 실제 파싱·자료 저장·SSE·모델 연결의 완료 판정은 각 구현 작업에서 수행한다.
