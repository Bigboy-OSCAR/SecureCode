## 1. 판정과 소유권

선행 2.1·3.2·4.2는 로드맵 체크와 기록·산출물이 존재한다. 그러나 실제 계약을 상세 화면 요구와 대조하니 필수 기능에 빠진 부분이 있다. 로드맵 0.8은 “완료 항목의 회귀는 원래 담당자가 자기 체크를 다시 열고 … 다른 담당자는 재현 자료를 인계하고 자신의 의존 작업을 BLOCKED로 유지”하도록 정한다. 2.2 프롬프트도 계약 결함은 소유자에게 인계하도록 한다. 따라서 다른 담당의 스키마·fixture·생성 타입·완료 체크는 수정하지 않는다.

UI 문서에는 현재 표시 가능한 필드와 보완 전 비활성 행동을 모두 명시했다. 이는 기존 제품 요구를 삭제하거나 축소한 것이 아니다. 전체 UI 구현 입력이 준비됐다고 판정하려면 아래 필수 계약이 먼저 보완돼야 한다. 1.1의 독립 착수 조건(2.1+3.2)에는 이번 2.2 완료가 포함되지 않는다.

## 2. 결함·재현·수용 기준

### G-01 · 선택한 포인터 범위를 실행에 전달할 수 없음 · 필수

- **근거:** [run schema](../../contracts/api/run.schema.json)의 `PointerContextRef`는 kind·pointer만 허용하고 additionalProperties=false다. `RunCreateRequest.context_refs`와 ContextPlan의 ref가 이 정의를 재사용한다. `PointerSelector`는 읽기 요청에만 있다.
- **재현:** `context/context-plan.valid.json`의 runtime ref 또는 RunCreateRequest의 pointer ref에 selector를 붙이면 현재 스키마가 허용하지 않는다. selector 없이 보내면 사용자가 확인한 부분 범위를 고정할 방법이 없다. 읽기 화면의 반환 범위 자체도 G-03으로 빠져 있다.
- **영향:** UI-23/UI-24/UI-27/UI-29/UI-30/UI-31. SC-07의 “현재 범위를 전달할 자료에 선택”과 그 선택의 run 전송을 비활성으로 명세했다. 포인터 전체를 보내는 대체 동작은 금지한다.
- **소유자:** 임우형 4.2 + 박준형 공통 run 계약(3.2/3.5), 소비 4.7/4.8/1.5.
- **해제 조건:** range·revision에 고정된 explicit ref의 공개 계약과 의미, cap에 잘린 실제 범위 선택 규칙, ContextPlan/run 전달 방식, 유효/거부 fixture, 생성 타입·양 언어 계약 검증. 필드명은 소유자가 확정한다.

### G-02 · 자료 등록·목록·삭제·갱신의 공개 계약 누락 · 필수

- **근거:** [pointer schema](../../contracts/pointers/pointer.schema.json)는 PointerDescriptor/SourceRegistration/**내부** RuntimePutRequest를 제공한다. 공개 등록 요청, 목록 요청/응답, DELETE의 scope body/성공 응답, Source 갱신 요청은 없다. `SourceRegistration`은 fingerprint·pointer가 있는 등록 결과이며 사용자 경로 입력 DTO가 아니다.
- **추가 누락:** descriptor에 안전한 자료명/상대경로가 없고 provenance는 created_at/origin/truncated_before_storage만 있다. available_operations는 read/search일 뿐 지원 selector 목록이 아니다. 외부 디렉토리 등록 범위·부분 실패·idempotency·상태 복구 방식도 미정이다.
- **재현:** contracts 전체 definitions 및 생성 타입에서 관련 입력·목록·삭제 정의를 확인할 수 없다. API.md의 route 존재·501 응답만으로 입력/출력 payload를 결정할 수 없다.
- **영향:** UI-18~UI-21/UI-24/UI-25/UI-27. 등록/해제/삭제는 실제 제출 비활성, 목록 row는 기존 descriptor fixture만 설계 검토에 사용한다. 필터 파라미터와 성공 판정을 UI에서 만들지 않는다.
- **소유자:** 임우형 4.2/4.3/4.5/4.6, 공개 route 박준형 3.6.
- **해제 조건:** 등록·목록·삭제·갱신의 요청/응답과 scope·pagination·정확한 삭제 의미, 매체별 selector 지원·section/JSON path 문법, 안전한 표시명, 오류/응답 유실 복구 fixture를 확정한다. 원본 파일 보존을 시험한다.

### G-03 · 실제 반환 범위와 PDF 출처가 응답에 없음 · 필수

- **근거:** [read schema](../../contracts/pointers/read.schema.json)의 PointerReadResult.provenance에는 media_type/byte_size/revision만 있다. 반환 줄/byte/page 범위, 상대 파일, 원본 hash, parser version이 없다. 검색 응답에도 revision·hash가 없다. `read-result-truncated.valid.json`은 content가 짧지만 byte_size=90000이므로 이를 반환량/범위로 해석할 수도 없다.
- **재현:** 잘린 범위 두 개 또는 PDF 페이지 두 개가 같은 provenance 모양을 가지며 UI가 실제 범위를 판별할 수 없다. ContextFragment에도 provenance가 없고 ref는 G-01의 범위 없는 형태다.
- **영향:** UI-23/UI-24/UI-26/UI-27/UI-29/UI-30. UI는 요청 범위와 실제 범위를 구별하며 실제 범위 확인 불가 상태에서 범위 선택을 막는다. pointer URI를 파싱해 부족한 필드를 추정하지 않는다.
- **소유자:** 임우형 4.2/4.6/4.8/4.9, 심볼 Source 경계 박준형 3.3/3.4.
- **해제 조건:** 실제 반환 범위·원본/파생 버전·hash·PDF page/parser provenance와 byte_size 의미를 정의한다. UTF-8 경계 잘림·cursor 다음 부분·원본 변경·PDF 페이지/캐시 변경 fixture로 표현과 선택 고정을 검증한다.

### G-04 · 공개 미리보기 입력·R0 연결·선택 설명 부족 · 필수

- **근거:** [context schema](../../contracts/context/context.schema.json)는 응답 ContextPlan만 있고 `/context/preview` 요청이 없다. [symbol schema](../../contracts/symbols/symbol.schema.json)의 검색/bundle 입력·출력은 존재하지만 API.md에서 브라우저 공개 검색 경로는 preview 연결로만 남아 있다. 내부 symbols API를 UI가 직접 사용할 수 없다.
- **표시 차이:** ContextPlan의 used_tokens/count_mode는 budget 안에 있다(명세에서 바로잡음). omission reason은 no_match/stale/unauthorized/over_budget뿐이며 중복 제외 근거는 없다. selected.explicit=false만으로 이번 작업 자료와 R0를 구분할 수 없다. 고정 입력·이력·도구·overhead 비용, 선택 범위 provenance, 현재 입력과 plan의 대응도 없다. arrays/content의 명시적 크기 한도도 필요하다.
- **재현:** `context-plan.valid.json`에서 runtime candidate는 selected에 있지만 해당 fragment는 없다. UI는 “선택 후보”와 “실제 포함된 원문”을 구분해야 하며 선택된 후보의 전체 본문이 전송됐다고 추정할 수 없다. duplicate reason을 추가하면 현재 enum에서 거절된다.
- **영향:** UI-09/UI-16/UI-17/UI-30/UI-31. 후보/plan fixture 렌더는 가능하지만 검색·preview의 실요청 연결과 세부 예산/중복 설명은 막힌다.
- **소유자:** 임우형 4.2/4.7/4.8 + 박준형 3.4/3.6.
- **해제 조건:** 질문·scope·명시 선택·revision을 받는 공개 preview 계약, 후보/bundle 조회 연결, priority·중복/부분 포함 이유·예산 비용 내역과 크기 상한, 입력 변경 후 plan 유효성 규칙을 확정한다. 요청·빈값·중복·초과·stale·계수 실패 fixture 및 생성 타입 검증이 필요하다.

### G-05 · PDF job·지원 상태·오류 상세 계약 없음 · 필수

- **근거:** `/pdf/parse`와 `/pdf/jobs/:job_id`는 API.md에 있지만 schemas에 PDF parse/job 정의가 없다. pdf_page selector만 있으며 PDF fixture 묶음도 없다. `error-parse-failed.valid.json`은 reason=parse_error라는 일반 오류일 뿐이다.
- **영향:** UI-27~UI-29. 등록→파싱, 작업 복구/중복 억제, 진행/부분 성공/빈 페이지, 스캔/손상/암호화/크기/페이지 초과를 실제 서버 필드에 대응할 수 없다. UI 문구는 작성하되 wire enum/필드명은 만들지 않았다.
- **소유자:** 임우형 4.2/4.9, 공개 route 박준형 3.6.
- **해제 조건:** parse 요청·작업 응답·조회·중복 처리·재시도·캐시 revision·페이지 진단·지원 상태/오류 이유의 계약과 fixture. 부분 성공을 보장하지 못하는 경우 전체 실패 의미를 명시한다. G-03의 페이지 provenance와 함께 확인한다.

### G-06 · 크기 단위·설정 한도·cursor 오류의 불일치 · 필수 표시 기준 보완

| 근거 | 현재 UI의 적용 | 소유자에게 필요한 결정 |
| --- | --- | --- |
| 로드맵 0.7 read 32 KiB, read/search schema의 max_bytes 최대 16384 | 현 요청은 16 KiB 이내. 초과를 허용하거나 32 KiB 사용 가능으로 표시하지 않음 | 4.2/4.6: 제품 정책과 스키마를 한 값으로 맞추거나 이유를 명시. token cap 32768은 bytes가 아님 |
| POINTERS.md preview 최대 512 UTF-8 bytes, schema는 maxLength=512자 | 한글 512자는 byte 한도보다 큼. 계약/서비스의 byte 검사 근거 전 제한 준수 성공으로 판정하지 않음 | 4.2/4.3/4.5: 다국어 byte 상한 fixture·의미 검사 |
| API.md의 승인 검토 16 KiB, ApprovalReview.content maxLength=16384자 | schema의 문자 길이와 reviewable/content_truncated를 사용; 승인 내용 일부면 승인 불가 | 3.2/3.5: 실제 byte/문자 상한·검토 가능 조건을 일치시키고 fixture 보완 |
| SettingsResponse.limits는 임의 정수 map, 이름·단위·필수 키 없음 | 저장·PDF·read·TTL 값을 임의 키로 읽거나 로드맵 상수를 실제 설정으로 표시하지 않음 | 3.2/3.5 + 4.2/4.8: 명명된 한도와 단위/기본값/검증 규칙 |
| POINTERS.md의 다른 scope/query cursor=INVALID_POINTER, API.md pagination은 INVALID_SELECTOR/SOURCE_CHANGED | 두 오류 모두 cursor 폐기·유효 자료/범위 재선택; wire 오류를 재정의하지 않음 | 4.2/4.6 + 3.2: 오류 우선순위 통일 및 fixture |
| 초기 16 KiB 도구 출력 임계값과 SDK 8000자 잘림의 불일치가 3.2 인계 D-2에 남아 있음 | UI는 서버 descriptor의 truncated_before_storage를 표시, 임계값을 별도 상수로 복제하지 않음 | 4.4/3.6: 저장 전 잘림 없는 threshold·범위·실제 통합 증거 |

Source descriptor는 문서상 expires_at이 없지만 현 schema는 이를 금지하지 않는다. 원본 수명과 Runtime TTL의 혼동을 피하도록 4.2가 스키마/fixture를 정리해야 한다. 이 항목은 source의 만료 값을 UI에서 새 정책으로 해석할 근거가 되지 않는다.

### G-07 · 실행 복구 후 출처·승인 이력·재구독 연결 부족 · 필수 복구 범위 보완

- **출처:** RunSnapshot.answer는 text/truncated만 있고 구조화된 출처·ContextPlan 참조가 없다. run.context_planned는 개수·예산뿐이다. 임의 Markdown 경로나 pointer 문자열을 답변의 검증된 출처 링크로 승격할 수 없다. 짧은 도구 원문도 ToolCallSummary에 없으므로 현재 명세는 summary만 표시한다.
- **승인 이력:** snapshot에는 pending_approvals만 있다. replay가 보존 기간을 넘은 뒤에는 이미 승인/거절/만료된 요청의 최종 상태를 복구할 공개 조회가 없다. 카드가 사라졌다는 이유로 승인됨을 표시하지 않는다.
- **SSE 재구독 구현 인계:** 기존 연결의 자동 재연결과 새 구독을 구분한다. 새 구독은 같은 origin cookie의 fetch 기반 SSE 소비에서 기존 Last-Event-ID 헤더로 이어 갈 수 있으므로 새 cursor query 계약은 필요하지 않다. UI_BEHAVIOR 5절에 정리했고 라이브러리·수명·snapshot 경합 검증은 1.3/1.4가 담당한다. 이 구현 선택 자체를 API 누락 차단 사유로 삼지 않는다.
- **영향:** UI-07/UI-09/UI-12/UI-15/UI-16/UI-34. 출력·종료·대기 승인은 현 snapshot으로 복구 가능하지만 전체 출처/결정 이력은 부족하다.
- **소유자:** 박준형 3.2/3.5/3.6, ContextPlan 참조 임우형 4.8, 구독 구현 김민지 1.3/1.4.
- **해제 조건:** 제한된 구조화 출처·최종 결정 이력의 조회/복구 계약과 fixture. 실제 재구독의 손실·중복 검증은 후속 1.3/1.4 행동 시험으로 넘긴다. 전체 원문 SSE 전송으로 해결하지 않는다.

### G-08 · fixture scenario 메타데이터가 2.1 ID와 불일치 · 추적성 보완

현재 schema 검사는 scenario가 UI-숫자 형식인지 확인할 뿐 의미를 대조하지 않는다. 예를 들어 approval-request-command는 UI-11(원래 취소)로, run-snapshot-cancelled는 UI-13(원래 승인)으로, stream-replay-unavailable는 UI-14(원래 거절)로 되어 있다. workspace.valid도 UI-02(원래 연결 오류)로 표시돼 있다.

- **조치:** 이 작업은 실제 파일명·payload로 사례를 연결하고 올바른 UI ID를 UI_BEHAVIOR_CASES에 명시했다. 공통 fixture를 직접 수정하지 않았다.
- **소유자:** 박준형 3.2(공통 fixture), 임우형 4.2(포인터/Context fixture), 소비 김민지 1.2/1.3.
- **해제 조건:** USER_SCENARIOS와 메타데이터를 일치시키고 coverage 집계가 형식 검사만 통과해 누락을 숨기지 않는지 확인한다. PDF/삭제 fixture 부재는 G-02/G-05의 기능 누락이며 이 메타데이터 문제와 별개다.

## 3. 문서에서 이미 해결한 대응 차이

| 기존 설계 표현 | 상세 명세에서 확정한 대응 |
| --- | --- |
| 최상위 ContextPlan.used_tokens/count_mode | ContextPlan.budget 안에 위치. run.context_planned 이벤트의 최상위 수치와 구분 |
| 최상위 ReadResult.revision | PointerReadResult.provenance.revision |
| 모든 목록/검색이 page 객체 사용 | pointer 검색은 최상위 limit/cursor·matches/truncated/next_cursor, 일반 목록·symbol 검색은 page 사용 |
| available_operations가 selector 종류 제공 | 현 값은 read/search뿐. selector 지원 매체 조합은 G-02 |
| SymbolCandidate에 원문/누락 존재 | candidate는 메타데이터, 실제 원문/누락은 SymbolBundle. estimated_tokens/token_count는 TokenCountSummary 객체 |
| 색인 ready면 검색 가능 | searchable와 확정 revision을 확인. zero-files fixture의 ready+false를 지원 |
| NO_MATCH가 항상 오류 응답 | HTTP 200. symbol은 no_match 객체, pointer 검색은 matches=[]; 새 필드를 추가하지 않음 |
| event_id를 Last-Event-ID로 사용 | SSE id는 run sequence의 10진수, JSON event_id는 별도 고유 ID. replay 제어 이벤트는 중복 제거 예외 |
| PDF 진행도 AppEvent로 전달 | 현재 공개 이벤트는 run 범위뿐. 색인·PDF는 GET 상태 조회 |
| exact면 전체 요청 예산 검증 완료 | 본문 계수·최종 gate·요청별/누적 사용량을 구분. provider_estimate를 한도 보장으로 표시하지 않음 |

## 4. 재개 순서

1. 각 소유자가 G-01~G-07의 필수 계약·의미·fixture·생성 타입을 보완하고 자기 작업 기록에 재검증 증거를 남긴다. G-08의 추적성도 정리한다. 계약 변경은 API.md의 변경 절차를 따른다.
2. 김찬우 2.2가 이 인계의 각 항목을 수정 파일·명령·결과로 닫고 상세 명세/사례의 “보완 대기”를 확정 매핑으로 교체한다. 전체 필드·화면·오류·fixture 대응을 다시 확인한다.
3. 그 뒤에만 2.2의 완료 조건·대표 체크를 갱신한다. 김민지 1.2는 추가로 1.1 완료도 필요하고, 1.3은 1.2 완료 후 시작한다. 2.3은 1.3+2.2 완료 후 실제 화면을 검토한다.

현재 산출물은 읽기·설계 검토 및 계약 보완에 바로 사용할 수 있다. 제품 UI의 완성, 실제 API 연결, 자동 행동 시험 통과를 의미하지 않는다.
