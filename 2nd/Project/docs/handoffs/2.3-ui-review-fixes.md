## UI23-01 현재 상태와 예시 상태가 섞여 표시됨

- 재현: 첫 화면의 관련 코드·자료 목록·부분 읽기 패널을 확인한다.
- 실제: `load_config` 결과와 NO_MATCH가 함께 보인다. 자료 `설계.md`가 있는데 “등록 자료가 없습니다”도 보인다. 정상 `한글` 읽기와 만료·원본 변경·예산 초과·입력 오류가 동시에 보인다.
- 기대: 현재 요청의 상태만 현재 결과로 표현한다. 설계 검토용 다른 상태는 “예시” 영역/선택기로 명확히 구분한다. 오류를 목록이 빈 상태로 바꾸거나 반대로 빈 목록을 오류로 표시하지 않는다.
- 근거: `ContextPanel.tsx`, `PointerPanel.tsx`, `PointerReadPanel.tsx`; 실제 브라우저에서 재현. [부분 읽기 증거](../progress/evidence/2.3/pointer-read-1280.jpg).
- 종료 검증: 동일 데이터에 정상/빈값/실패/만료/변경 응답을 각각 주어, 현재 결과와 상태가 모순 없이 한 조합으로 표시되는지 AC-09/17/18/22/24/30/31에서 확인한다.

## UI23-02 검색·범위·선택·미리보기와 목록 조작 누락

- 재현: 관련 코드에서 검색 입력/선택/원문 열기를 찾는다. 부분 읽기에서 `다음 부분`을 누르고 범위 변경·검색·질문에 선택을 시도한다. 자료 목록의 탭/필터/다음 페이지를 확인한다.
- 실제: 관련 코드·ContextPlan은 고정 표시다. 부분 읽기는 “다음 부분 fixture 응답이 없어 추가 내용을 표시하지 않았습니다”만 출력한다. 범위 타입/버전은 있지만 start/end, byte_size, token_count/count_mode가 없고 검색·범위 선택도 없다. 목록은 단일 표본이며 등록/해제/삭제는 의도 확인 안내만 한다.
- 기대: 유효 cursor가 있을 때만 다음 조회, 정확한 반환 범위/버전/해시/계수 표시, 승인된 범위만 context_refs로 선택하고 질문·선택 변경 시 preview를 무효화한다. token과 byte 상한을 보존하며 자동 전체 읽기는 금지한다. 목록의 scope/페이지/필터와 성공·실패에 따른 선택 무효화를 구현한다.
- 근거: `ContextPanel.tsx`, `PointerReadPanel.tsx`, `usePointerReadWorkflow.ts`, `PointerPanel.tsx`; browser 직접 클릭. 원본 변경/만료 안내 표본은 존재하지만 실제 API 동작은 검증되지 않았다.
- 종료 검증: AC-16/18~21/23/25/26/30/31/34의 제한된 조회→범위 선택→preview→같은 범위 run 전달과 해제 후 선택 무효화를 1.5 실제 서비스에서 실행한다.

## UI23-03 PDF 상태와 복구 안내 불일치

- 재현: PDF 계약 상태의 `완료`, `실패`, `지원하지 않는 PDF`를 각각 선택한다.
- 실제: 모든 7개 상태에서 “원본이 변경되어 이전 추출을 사용할 수 없습니다”가 상시 표시된다. 실패/미지원도 “페이지 정보를 확인하는 중”으로 표시된다. ready/partial에서도 페이지 선택·읽기, parser_version/hash 출처가 없다.
- 기대: 현재 job.state와 reason에 맞게 확정 상태를 보여 준다. 실패/미지원은 계속 처리 중으로 표시하지 않는다. ready/partial에만 유효 페이지의 bounded read를 제공하고 제외 페이지는 선택하지 못하게 한다. stale이면 이전 결과 선택을 무효화한다.
- 근거: `PdfParsePanel.tsx`, [7개 상태 실제 표시](../progress/evidence/2.3/pdf-states.json), [미지원 표시](../progress/evidence/2.3/pdf-unsupported-1280.jpg).
- 종료 검증: AC-27~29를 실제 job과 텍스트/한글/부분 실패/스캔/손상/암호화 자료로 실행한다. UI 상태 버튼 전환을 실제 PDF 처리 통과로 계산하지 않는다.

## UI23-04 승인 검토 메타데이터와 대화상자 초기 초점·복귀

- 재현: 질문 실행→승인 대기→`승인 검토`를 키보드 Enter로 연다. 닫기 또는 Escape로 닫는다.
- 실제: summary/content는 표시되지만 kind/target_paths/expires_at가 없다. 최초 초점은 `닫기`에 놓여 자동 승인 위험은 없지만, 기존 명세의 제목/검토 내용 초기 초점 요구에는 미충족이다. Escape로 닫은 뒤 DOM activeElement는 BODY가 되고 시작 버튼으로 돌아가지 않는다.
- 기대: 검토할 대상·명령/변경 종류·만료시각을 표시한다. 승인 상세의 최초 초점은 제목/검토 내용, 등록 해제·삭제 확인창의 최초 초점은 설명/돌아가기에 두며 확정 버튼을 기본 선택하지 않는다. 닫기/Escape는 결정하지 않고 시작점으로 복귀한다. 승인 ID/digest 바인딩은 유지한다.
- 근거: `ApprovalCard.tsx`, `Modal.tsx`(open=false에서 dialog 제거), browser 키보드 확인. [승인창](../progress/evidence/2.3/approval-1280.jpg).
- 종료 검증: AC-13~15/20/21/33에서 Tab/Shift+Tab, Escape, 닫기/돌아가기, 만료된 요청, 확인 중 요청 교체를 검사한다. 버튼이 제거된 경우에는 관련 카드의 안전한 위치로 초점을 옮긴다.

## UI23-05 도구 상태·저장 사실·답변 출처 표현 부족

- 재현: 질문 전후 도구 이력을 보고 `ConversationPanel`에 전달되는 tool_calls/answer.citations와 비교한다.
- 실제: phase를 표시하지 않으며 output_pointer 여부와 관계없이 `${output_bytes ?? 0} bytes 저장`을 표시한다. 질문 전에도 예시 저장 이력이 보인다. run.answer.citations는 렌더하지 않아 답변 출처 진입점이 없다.
- 기대: requested/awaiting_approval/running/completed/failed/cancelled 상태를 현재 run별로 표시한다. 크기 없음은 미확인이고 0으로 만들지 않는다. 저장 성공은 실제 pointer/이벤트로 확인한다. 답변 출처는 서버가 준 ref/location으로만 연결한다.
- 근거: `ConversationPanel.tsx`와 실제 첫 화면. phase/없는 bytes의 모든 변형은 정적 코드 검토이며 브라우저 전체 변형 시험을 했다고 주장하지 않는다.
- 종료 검증: AC-07/09/12/16/34에서 각 도구 상태·포인터 유무·누락 bytes·출처 없는 답변·복구된 citations의 페이지 이동을 확인한다.

## UI23-06 좁은 폭 패널 전환과 상태 접근성

- 재현: 실제 CSS viewport 1280×900 및 768×900에서 탐색·대화·출처 영역을 확인한다.
- 실제: 두 폭 모두 페이지 가로 넘침은 없다. 768에서는 좌우 패널을 접는 메뉴가 없이 프로젝트→대화→출처 전체가 긴 한 열로 이어진다. 승인 카드로 이동하려면 긴 스크롤이 필요하다.
- 기대: 1024 미만에서는 프로젝트/메뉴와 출처/자료 패널을 필요할 때 하나씩 열고 닫도록 한다. 활성 실행·승인·오류 상태를 계속 확인할 수 있어야 한다. 탐색은 키보드로 접근할 수 있다.
- 근거: [768 실측](../progress/evidence/2.3/layout-768.json), [768 화면](../progress/evidence/2.3/layout-768.jpg), [1280 실측](../progress/evidence/2.3/layout-1280.json), `app.css`.

## UI23-07 연결·색인·모델/보호 준비 조건과 실제 API 연결

- 재현: 로컬 서비스 연결 전 또는 `빈 색인` 선택 후 질문 전송 버튼을 확인한다. 모델 설정 패널은 “모델 미설정/입력 한도 검증 전”이다.
- 실제: 질문 fixture 실행은 가능하다. 인증/프로젝트 등록/PDF 등록은 입력 형식만 확인하며 실제 요청은 없다고 안내한다. 프로젝트 선택·세션 생성·색인 갱신·health 재조회 흐름이 연결되지 않았다.
- 기대: 실 adapter에서는 인증·scope·searchable·모델 설정·필수 보호 상태·예산 확인으로 실행 가능 여부를 결정한다. 코드 형식 확인을 인증 성공으로 표시하지 않는다. 연결 끊김·갱신 실패에서는 상태 복구 전 mutation을 차단한다.
- 근거: App의 독립 feature fixture 구조, `RunCommands.canSubmitRun`, 빈 색인에서 버튼 활성 browser 관측. fixture임을 표시하므로 현재 실제 모델 실행 우회가 발생했다는 의미는 아니다.
- 종료 검증: AC-01~08/10/12/17/32를 1.4 및 1.5에서 실제 HTTP/SSE로 검증하고 1.6에서 인수한다. 로그/URL/번들/저장소의 비밀값 검사도 포함한다.

## UI23-08 답변 표시 자체 잘림과 과도한 실시간 알림

- 재현: `ConversationPanel.tsx`의 `boundedPreview(streamText, 280)`과 `answer.truncated`, `aria-live="polite"`를 비교한다.
- 실제: 서버 truncated=false라도 280자 이후 UI에서 자르며 자체 잘림 안내/후속 탐색은 없다. 답변 본문 전체가 live region에 있어 매 delta 갱신이 낭독될 수 있다.
- 기대: 서버 반환 잘림과 UI 미리보기 잘림을 구별하고 임의로 내용을 잃은 것처럼 숨기지 않는다. 원문을 무제한 렌더하지 않되 제한된 다음 내용/출처 진입을 제공한다. 보조기기에는 실행·연결·종료를 알리고 토큰마다 전체 답변을 다시 알리지 않는다.
- 근거: 정적 코드/SSR 검토. 스크린리더 실제 과다 낭독은 미실행이므로 위험 및 검증 요청으로 기록한다.
- 종료 검증: AC-07/11/33/34에서 280자 초과 답변, 서버 truncated 조합, 긴 한글 및 실제 스크린리더 낭독을 검증한다.

## UI23-09 취소 fixture가 현재 질문·승인 이력을 대체함

- 재현: 기본 질문과 다른 `load_config의 실패 원인을 확인해줘`를 입력→실행→거절 확정(또는 승인 확정)→취소 요청.
- 실제: 동일 run의 질문이 기본 `테스트를 실행해 실패 원인을 찾아줘`로 바뀌고 이미 처리한 승인 이력이 사라진다. 취소 상태 확정 자체는 정상 표시된다.
- 기대: 취소는 현재 run의 질문·답변·도구/승인 이력을 보존하고 상태/종료 정보만 갱신한다. 실 서비스에서도 id/session/workspace 및 sequence가 맞는 snapshot으로만 복구한다.
- 근거: `FixtureRunClient.cancelRun()`이 현재 snapshot 대신 cancelledFixture를 펼친다. [취소 전후 텍스트](../progress/evidence/2.3/cancel-observation.json), [취소 화면](../progress/evidence/2.3/cancelled-1280.jpg).
- 종료 검증: AC-11/14/15에서 다른 질문·이미 결정된 승인·중단 전 답변을 가진 취소 회귀를 추가한다. 기존 controller 시험만으로 실제 앱 fixture adapter의 이력 보존을 보장하지 않는다.

## 인수와 후속 처리

9개 요청 모두 영향 화면·재현·실제/기대·심각도·담당·종료 검증을 갖춘다. 현재 fixture를 실행하고 설계 검토하는 것 자체를 막는 차단 결함은 없다. UI23-09는 1.3 담당의 fixture 회귀 보완 입력이며 2.3에서 상태 코드를 변경하지 않는다. 제품 최종 통과는 김민지 1.6, 전체 제품 인수는 박준형 3.8에서 판단한다. 요구를 낮추거나 미해결 구현을 PASS로 표시하지 않는다. commit/push는 하지 않았다.
